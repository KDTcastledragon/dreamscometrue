#1 판정 — 의도는 어디에 반영됐나

castleChat 은 plan.md 1순위 원칙이 “대용량 트래픽에 대응 가능한 설계” 였다. 그 의도가 실제 코드의 어디에 남았고 어디서 갈라졌는지 전수로 확인한 기록.

1 — 되돌릴 수 있나로 나눠 본다

“대규모 지향 설계” 의 핵심은 지금 빠른가가 아니라 나중에 빠르게 만들 수 있는가다. 그래서 결정을 되돌릴 수 있는 것과 없는 것으로 나눠 봐야 한다.

되돌릴 수 없는 결정
ID 채번 방식 O Snowflake 53bit
데이터 흐름 O Kafka 이벤트
파티셔닝 키 O key = roomId
연결 모델 O 유저당 1연결 멀티플렉싱
소비 모델 O 멱등 소비 (at-least-once 전제)
되돌릴 수 있는 결정
Kafka .get() 제거 X — 한 줄이면 바뀐다
replicas 늘리기 X — 상태만 밖으로 빼면 된다
캐시 추가 X — 기존 패턴 복사
로그 레벨 X — 설정값
Kafka producer 튜닝 X — properties 몇 줄
한 줄 정리

되돌릴 수 없는 결정 다섯 개를 전부 맞췄고, 못 한 것은 전부 되돌릴 수 있는 것들이다.

AUTO_INCREMENT 로 시작했으면 지금 Snowflake 로 못 바꾼다. 기존 ID 체계가 통째로 꼬인다. 동기 INSERT 로 짰으면 Kafka 를 끼워 넣는 게 재작성 수준이다.

반대로 .get() 은 한 줄이고, replicas 는 설정이고, 캐시는 반나절이다. 순서를 맞게 잡았다는 뜻이다.

그래도 선을 그을 것

이건 “대규모를 처리한다” 가 아니라 “대규모로 가는 길을 막지 않았다” 는 뜻이다.

#2 잘 설계한 부분

공통점이 하나 있다. 지금 규모에는 전혀 필요 없는데 일부러 한 것들이다. 동시접속 열 명짜리 프로젝트에 이게 왜 있냐는 질문의 답이 “의도” 다.

2 — Snowflake 분산 채번

messageId = timestamp(41) | workerId(5) | sequence(7)   = 53bit

epoch  2024-01-01
53bit 인 이유 : JS Number 안전 정수 한계가 2^53-1
                프론트에서 정밀도 손실 없이 다룰 수 있는 최대

왜 대규모 지향인가

  • 중앙 병목이 없다. DB 가 ID 를 발급하면 쓰기를 나눌 때 그게 병목이 된다
  • DB 에 넣기 전에 PK 가 확정된다. 그래서 응답을 메모리에서 조립할 수 있고, DB 쓰기를 비동기로 뺄 수 있다
  • 중복 소비가 자동으로 걸러진다. 같은 메시지가 두 번 와도 PK 충돌로 0행이 된다
  • 시간순 단조증가라 기존 정렬 · 페이징 로직을 그대로 쓴다
복붙이 아니라는 증거 
if (currentTimestampMs < lastTimestampMs) {
    // 시계 역행(NTP 보정 등).
    // 마지막 발급 시각까지 대기하여 단조증가 보장.
    currentTimestampMs = waitUntil(lastTimestampMs);
}

NTP 보정으로 시계가 뒤로 갈 수 있다는 걸 알고 처리했다. 그리고 같은 ms 안에서 sequence 를 다 쓰면 다음 ms 까지 기다린다. 대부분의 복붙 구현이 이 두 가지를 빼먹는다.

3 — Kafka 유실 방지 파이프라인

장치 실제 설정 막는 것
acks=all spring.kafka.producer.acks=all ISR 전부가 받기 전엔 성공으로 안 본다
idempotence enable.idempotence=true 재시도로 인한 브로커 측 중복 적재
동기 확인 send().get(timeout) 저장 확인 전에 성공이라 말하는 것. 실패하면 사용자에게 실패를 돌려준다
재시도 + DLT FixedBackOff(500ms, 10회)
→ <topic>.dlt		 소비 실패 건을 버리지 않고 격리. 파티션 번호까지 유지한다
멱등 소비 inserted == 0 이면 정상 종료 at-least-once 재전달로 인한 중복 저장
key = roomId 파티션 6개 파티션을 늘려도 방 안의 순서가 유지된다
멱등 소비가 왜 중요한가 
int inserted = chatMapper.insertChatMessage(msg);

if (inserted == 0) {
    log.info("이미 저장된 메시지. msgId={}", event.getMessageId());
    return;              // 예외를 던지지 않는다
}

Kafka 는 최소 한 번 전달이라 같은 메시지가 두 번 올 수 있다. 리밸런싱이 일어나거나 오프셋 커밋 전에 워커가 죽으면 그렇다.

여기서 예외를 던졌다면 재시도 10회 후 DLT 로 갔을 것이다. 정상으로 처리하고 넘기는 게 맞다. Snowflake 로 ID 를 미리 확정했기 때문에 가능한 처리다.

4 — Redis 캐시 두 가지

cache-aside — 방 멤버 
roomMemberCache.getOrLoadRoomMembers(
    roomId,
    () -> chatMapper.findAllActiveMemberIdsInRoom(roomId))

메시지마다 멤버 목록이 필요한데 거의 안 바뀌는 값이다. Redis Set 에 두고 미스일 때만 DB 를 친다.

write-behind — 읽음 위치 
roomReadPositionCache.updateIfGreater(
    roomId, userId, messageId, ...)

읽음 위치는 항상 커지기만 하는 값이라 중간값을 전부 DB 에 쓸 이유가 없다.

안 그러면 쓰기가 사용자 수 × 스크롤 횟수만큼 터진다. 쓰기 증폭은 규모가 커져야 생기는 문제라, 이걸 미리 막은 게 의도의 증거다.

5 — 연결 비용과 전송량을 줄인 설계

1

WS 멀티플렉싱

“방 하나 = 연결 하나” 로 만들면 유저가 방 10개를 열 때 서버 비용이 10배가 된다.

연결은 유저당 하나만 두고 봉투의 wsType 과 roomId 로 갈래를 나눈다. 방이 몇 개든 유저당 1연결로 고정된다.

연결당 커널 버퍼 수십 KB 를 아낀다
2

중복 전송 제거

targetUserIds.removeAll(
  getViewingUserIds(roomId));

메시지 1건에 전송이 세 번 나간다 (MSG_CREATED · 방 목록 갱신 · 알림).

세 집합이 겹치지 않게 보고 있는 사람을 빼준다. 안 그러면 fan-out 이 3배가 된다.

fan-out 자체를 줄인 설계
3

입구 필터

핸들러에서 roomId 와 내용 유무를 먼저 본다.

주석 그대로 “깨진 패킷을 굳이 내부 서비스까지 보내지 않기 위한 입구 필터” 다. gRPC 홉과 DB 조회를 아낀다.

경계에서 막는다

6 — 조회를 O(1) 로 만든 세션 레지스트리

Map<WebSocketSession, SessionUserDTO>        wsSessionsToConnectedUser
Map<Long, WebSocketSession>                 userIdToWsSessions
Map<String, WebSocketSession>               publicIdToWsSessions
Map<Long, Map<Long, WebSocketSession>>      roomSessions      (방 -> 유저 -> 세션)

같은 데이터를 네 가지 방향으로 미리 색인해 뒀다. 세션으로 유저를 찾는 것, 유저로 세션을 찾는 것, 방으로 세션 목록을 찾는 것이 전부 O(1) 이다.

전부 ConcurrentHashMap 이라 락 없이 동시 접근이 된다. 브로드캐스트가 가장 뜨거운 경로라 여기가 느리면 전부 느려진다.

7 — 서비스 분리와 그 한계를 같이 적어둔 것

프로세스 5개로 나눈 것 자체는 처리량을 올리지 않는다. 오히려 메서드 호출(수십 ns)이 gRPC 호출(0.5~2ms)로 바뀌어 건당 지연은 늘었다.

나눠서 얻은 건 배포 독립성 · 장애 격리 · 스케일 단위 분리다. 처리량은 각각을 여러 개로 늘릴 때 올라간다.

매니페스트 주석이 자산이다 
# websocket-gateway
# WsGateSessionRegistry가 JVM 메모리(ConcurrentHashMap)라
# 브로드캐스트가 자기 파드에만 닿는다.
replicas: 1

# domain-service
# 첨부가 이 파드 볼륨에만 있어 2개 이상 불가.
# S3 이전이 선행되어야 함
replicas: 1

모르고 1인 게 아니라 알고 1이다. “왜 안 늘렸나” 에 대한 답이 코드에 이미 적혀 있다.

#3 그렇지 못한 부분

셋으로 갈린다. 의식적 트레이드오프, 그냥 놓친 것, 기본값으로 남겨둔 것. 성격이 다르므로 말하는 방식도 달라야 한다.

8 — 사용자 경로가 전 구간 동기다

비동기로 뺀 것은 DB 쓰기 하나뿐이다. 사용자가 기다리는 구간은 처음부터 끝까지 동기 블로킹이다.

Kafka .get() 이 배치를 죽인다

Kafka 가 빠른 이유는 배치다. linger.ms 동안 레코드를 모아 batch.size 만큼 한 번에 보낸다.

건건이 .get() 하면 배치 크기가 사실상 1 이 된다.

배치 전송        수십만 건/s
건당 동기 대기    수천 건/s     <- 10~100 배 차이
그래도 이건 트레이드오프다

.get() 을 빼면 “성공했습니다” 라고 말한 뒤 유실될 수 있다.

주석에도 durable save 라고 적혀 있다. 처리량 대신 확실성을 산 것이고, 채팅에서는 맞는 선택이다.

말할 때도 “못 했다” 가 아니라 “무엇을 포기하고 무엇을 얻었다” 로 말한다.

9 — fan-out — 진짜 벽

채팅 서버의 부하는 “몇 명이 보내냐” 가 아니라 “한 건이 몇 명에게 퍼지냐” 로 정해진다.

10 — 수평 확장이 막혀 있다

대상 막는 것 풀려면
websocket-gateway 세션 레지스트리가 JVM 메모리 Redis pub/sub 팬아웃. 단, 파드가 많아지면 wsgate 간 트래픽이 또 폭발한다
channel-engine CHAT_SNOWFLAKE_WORKER_ID: "0" 하드코딩 StatefulSet 전환 → 파드 번호를 workerId 로
domain-service 첨부가 로컬 EBS. RWO 라 1파드 S3 이전
event-persist-worker 파티션 6개를 혼자 소비 replicas 를 올리면 바로 된다 (여기는 이미 준비돼 있다)
Kafka 브로커 1대, RF 1 브로커 3대 + RF 3 + min.insync.replicas=2
제일 날카로운 지적 — acks=all 인데 브로커가 1대다

ISR 이 1개라 사실상 acks=1 과 같다. 설정은 올바른 값이지만 내구성 보장이 실질적으로 없다. 그 브로커의 디스크가 날아가면 유실이다.

먼저 인정하고 넘어가는 게 맞다. chatKafka.md 에 이미 “운영에서는 브로커 3대 이상, RF 3, min.insync.replicas 2” 라고 적어뒀다. 그대로 말하면 된다.

11 — 그냥 놓친 것 두 개

1 — 캐시 없이 매번 DB 를 친다 
List<Long> notificationTargetUserIds =
  chatMapper.findChatMessageNotificationTargetUserIds(
      cmd.getRoomId(), cmd.getSenderUserId());

roomMemberCache 는 캐시를 타는데 이건 안 탄다. 매 메시지마다 DB 직행이다.

초당 1만 건이면 초당 1만 쿼리다. 이것 하나만으로도 처리량이 막힌다.

트레이드오프가 아니라 누락이다. roomMemberCache 패턴을 그대로 복사하면 되고 반나절이면 끝난다.

2 — 측정 수단이 없다 
// WsGateOutboundWriter.java
//	private final ChatMetrics chatMetrics;   <- 주석 처리됨

메트릭을 넣으려다 주석으로 남겨둔 흔적이 있다. 지금은 처리량도 지연도 측정할 수단이 없다.

그래서 “몇 건 되나” 에 답을 못 한다. 이게 숫자를 못 대는 근본 원인이다.

Micrometer + Actuator 로 건당 지연과 fan-out 크기만 찍어도 대화가 완전히 달라진다.

12 — 기본값으로 남겨둔 것

항목 현재 영향
Kafka producer 튜닝 acks 와 idempotence 만 설정. linger.ms · batch.size · compression 은 기본값 linger.ms=0 이라 모으지 않는다. .get() 과 겹쳐 배치가 완전히 죽는다
Tomcat 스레드 설정 없음 → 기본 200 동기 모델의 천장이 200 / 건당지연 으로 고정된다
로그 레벨 핫패스에 log.info 건당 4줄 초당 1만 건이면 초당 4만 줄. 동기 appender 면 디스크 I/O 가 요청 경로에 들어온다
JVM MaxRAMPercentage=70 + UseG1GC 만 힙 크기 · 리전 크기 · GC 목표는 전부 기본값

셋 다 설정만 바꾸면 되는 것들이다. 구조 문제가 아니다. “운영 전환할 때 할 일” 로 분류하는 게 맞다.

13 — 세부 비용 — 작지만 핫패스에 있는 것들

1

nextMessageId() 가 synchronized

if (sequence == 0) {
  waitUntil(lastTimestampMs + 1);
}  // 락을 쥔 채 대기

channel-engine 전체의 단일 직렬화 지점이다. 평소엔 빠르지만 ms 당 128건을 넘기면 락을 쥔 채 스핀해서 전체가 멈춘다.

Twitter 원본도 synchronized 다. 틀린 코드는 아니다
2

송신마다 맵 조회 + 모니터

synchronized (
  getSessionSendLock(session)) {
  session.sendMessage(...);
}

송신 10만 건/s 면 computeIfAbsent 10만 회 + 모니터 획득 10만 회다.

TEXT_PARTIAL_WRITING 을 막는 필요한 락이다
3

느린 클라이언트가 스레드를 잡는다

session.sendMessage() 는 TCP 송신 버퍼가 차면 블로킹된다. 그걸 세션 락을 쥔 채 한다.

네트워크가 느린 사용자 하나가 브로드캐스트 스레드를 붙잡을 수 있다. 백프레셔 장치가 없다.

ConcurrentWebSocketSessionDecorator 로 상한을 둘 수 있다

셋 다 “틀린 코드” 가 아니라 “규모가 커지면 드러나는 비용” 이다.
특히 2번은 실제로 TEXT_PARTIAL_WRITING 을 겪고 고친 흔적이라 버그가 아니라 버그를 잡은 것이다.

확인해보니 문제가 아니었던 것

처음에 targetUserIds.removeAll(getViewingUserIds(roomId)) 가 O(n×m) 일 거라고 의심했다.

public Set<Long> getViewingUserIds(Long roomId) {
    ...
    return new HashSet<>(sessions.keySet());   // Set 을 돌려준다
}

ArrayList.removeAll(c) 는 c 가 Set 이면 O(n) 이다. 문제가 아니었다. 다만 호출마다 HashSet 을 새로 복사하고 건당 2회 호출되므로 할당 압력은 있다.

#4 용어와 메커니즘 — 왜 못 늘리는지의 실제 이유

앞에서 “fan-out”, “Redis pub/sub 팬아웃”, “방 단위 샤딩” 이라고만 적고 넘어간 것들을 풀어 쓴다. 이 셋을 모르면 replicas 를 왜 못 올리는지 설명이 안 된다.

14 — fan-out

하나가 여러 개로 퍼지는 것. 선풍기(fan) 날개처럼 펼쳐진다는 뜻이다. 채팅에서는 메시지 1건을 받아 방 멤버 N 명에게 보내는 것이다.

코드에 그대로 있다

// WsGateOutboundWriter.broadcastToRoom()
for (WebSocketSession sess : sessions.values()) {
    dispatchSerializedToSession(sess, payload);
}
//  ↑ 이 for 루프가 fan-out 이다

방 멤버가 10명이면 10번, 50명이면 50번 돈다. 루프 안에서 세션 락을 잡고 소켓에 쓴다.

그래서 부하의 기준이 바뀐다 
초당 1만 건 × 10인 방 = 송신 10만 건/s
초당 1만 건 × 50인 방 = 송신 50만 건/s
                        ↑ 같은 1만 건인데 5배

“몇 명이 보내냐” 가 아니라 “한 건이 몇 명에게 퍼지냐” 로 한계가 정해진다. 이게 채팅 서버가 다른 웹 서비스와 다른 지점이다.

15 — wsgate 를 늘리면 메시지가 사라진다

세션 명부가 그 파드의 JVM 메모리 안에만 있기 때문이다.

// WsGateSessionRegistry
private final Map<Long, Map<Long, WebSocketSession>> roomSessions = new ConcurrentHashMap<>();
//                                                    그냥 자바 객체다. 이 파드 안에만 존재한다
pub/sub 이 뭔가 — 라디오다 
PUBLISH    방송을 쏜다
SUBSCRIBE  주파수를 맞춰놓고 듣는다

보내는 쪽은 누가 듣는지 모른다. 그게 장점이다 — A 가 영희의 존재를 알 필요가 없다.

그리고 저장하지 않는다. 그 순간 듣고 있던 구독자에게만 간다. Kafka 와 다른 점이다.

왜 Redis 가 한계가 되나 
초당 1만 건 × 45 파드 = 45만 전달/s
Redis pub/sub 실용 한계 ≈ 10만/s

게다가 Redis 는 단일 스레드다. CPU 를 더 줘도 안 빨라진다.

“세션을 Redis 로 빼면 된다” 는 해법 자체가 그 규모에서는 병목이 된다. 그래서 다음 단계가 샤딩이다.

16 — 샤딩 — 나눠 담기

“이건 네 담당, 저건 내 담당” 으로 미리 정해두는 것이다. 나눠두면 서로 물어볼 일이 없어진다.

방 샤딩 — 위 문제를 없앤다

roomId % wsgate_개수 = 담당 wsgate

방 5번  ->  5 % 3 = 2  ->  wsgate 2 전담
방 6번  ->  6 % 3 = 0  ->  wsgate 0 전담
방 7번  ->  7 % 3 = 1  ->  wsgate 1 전담

같은 방 사람은 무조건 같은 wsgate 로 붙인다

  철수(방5) ->  wsgate 2
  영희(방5) ->  wsgate 2

  -> 명부에 둘 다 있다
  -> ★ pub/sub 이 필요 없어진다

DB 샤딩 — 쓰기를 나눈다

roomId % 4

방 1, 5,  9 ...  ->  DB-1
방 2, 6, 10 ...  ->  DB-2
방 3, 7, 11 ...  ->  DB-3
방 4, 8, 12 ...  ->  DB-0

초당 1만 INSERT
  -> DB 하나당 2,500 INSERT
  ★ 4배로 나눠진다

worker 를 늘려도 DB 가 하나면 소용없다. 쓰기를 진짜로 나누려면 DB 를 나눠야 한다.

샤딩의 대가 — 공짜가 아니다

wsgate 개수가 바뀌면 % N 의 결과가 전부 달라진다. 파드를 3개에서 4개로 늘리는 순간 거의 모든 방의 담당이 바뀌고, 접속자 전원이 재배치돼야 한다. 그래서 실무에서는 consistent hashing 을 쓴다.

DB 샤딩은 “여러 방을 한 번에 조회” 가 어려워진다. 4개 DB 를 전부 뒤져서 애플리케이션에서 합쳐야 한다. JOIN 도 트랜잭션도 샤드를 넘지 못한다.

그래서 샤딩은 마지막 수단이다. 캐시 · 읽기 복제 · 수직 확장을 먼저 해보고 그래도 안 되면 간다.

17 — replicas 를 7~8 로 올리면 무슨 일이 생기나

서비스마다 결과가 전혀 다르다. 그리고 제일 위험한 건 에러가 안 나는 쪽이다.

서비스 결과 이유 알아챌 수 있나
event-persist-worker 된다 Kafka 파티션 6개를 나눠 먹는다. 단, 7개 이상은 의미 없다 — 남는 컨슈머는 할당받을 파티션이 없어 논다 —
domain-service 파드가 안 뜬다 EBS 는 ReadWriteOnce 라 2번째 파드가 볼륨을 못 잡는다 즉시. Pending 에서 멈춘다
channel-engine ID 가 겹친다 CHAT_SNOWFLAKE_WORKER_ID: "0" 이 모든 파드에 똑같이 들어간다 → messageId 중복 곧. DB PK 충돌 에러
websocket-gateway 조용히 고장난다 위 15번 그대로. 다른 파드에 붙은 사람에게 안 간다 ★ 못 알아챈다
조용한 고장이 제일 나쁘다 
domain-service      Pending 에서 멈춤   -> 바로 안다
channel-engine      PK 충돌 에러       -> 바로 안다
websocket-gateway   아무 일도 안 일어남  -> ★ 모른다

wsgate 는 파드가 멀쩡히 뜨고, 로그도 깨끗하고, readinessProbe 도 통과한다. 그런데 메시지만 사라진다.

보낸 사람 화면에는 정상으로 보인다. “상대가 답이 없네” 라고만 느낀다. 그래서 replicas: 1 로 묶고 주석을 달아둔 것이다.

한 줄씩 
fan-out     1건 받아서 N명에게 보내는 것. for 루프가 그거다

pub/sub     wsgate 가 여러 개면 서로의 세션을 모른다
            Redis 로 "방송" 해서 알려준다
            -> 파드가 많아지면 Redis 가 먼저 터진다

샤딩         "이 방은 네 담당" 으로 미리 나눠두는 것
            나눠두면 방송이 필요 없어진다
            대신 재배치와 조회가 어려워진다

replicas    worker 만 된다 (파티션 수인 6까지)
            나머지 셋은 안 되고, wsgate 는 조용히 고장난다

#5 지금 어디까지 되고, 올리려면 무슨 순서인가

18 — 현재 상한 — 전부 추정이다

먼저 말할 것

부하 측정을 한 적이 없다. 아래는 리소스 설정에서 역산한 값이고 실측이 아니다. 숫자를 단정해서 말하면 거짓이 된다.

[ 동시 접속 ]  wsgate 1파드, memory limit 768Mi
  heap = 768 x 0.7 = 약 537MB
  Spring + Tomcat 상주 = 150~250MB
  연결 1개당 (힙 기준) 20~40KB
    Tomcat WsSession 입출력 버퍼 8KB + 8KB
    + Spring 래퍼 + 레지스트리 엔트리 4개
  -> 산술 상한 약 10,000.  현실적으로 3,000~5,000
  (커널 소켓 버퍼는 힙 밖에서 추가로 든다)

[ 처리량 ]  cpu limit 1코어, fan-out 이 지배적
   2인 방   약 1,000 msg/s
  10인 방   약   450 msg/s
  50인 방   약   110 msg/s
 200인 방   약    30 msg/s

[ 지연 ]  한가할 때
  gRPC 1ms + Redis 0.5ms + DB 2~5ms + Kafka 5~15ms  =  10~25ms

[ 숨은 함정 ]
  t3.medium 은 burstable. 지속 가능한 건 baseline 20%
  CPU 크레딧이 떨어지면 성능이 1/5 로 주저앉는다
  -> 부하를 길게 주면 몇십 분 뒤 숫자가 급락한다
규모를 환산하면 
가입자 30,000
  -> DAU 10~20%        =  3,000 ~ 6,000
     -> 피크 CCU 5~15%  =    300 ~   900 명

가입자 3만 명의 실제 서버 부하는 동시 접속 수백 명이다. 그 정도면 처리량은 지금 구성으로도 된다.

먼저 터지는 건 처리량이 아니라 첨부 저장소 20Gi → RDS db.t4g.micro → 가용성(replicas 1) 순이다.

숫자를 말할 땐 반드시 단위를 붙인다. “가입자 기준으로” 다섯 글자가 사실과 과장을 가른다.

19 — 올리는 순서 — 싼 것부터

반나절 알림 대상 캐싱 건당 DB 조회 1회 제거
roomMemberCache 패턴 복사
1시간 로그 레벨 · 비동기 appender 핫패스 info 를 debug 로
초당 4만 줄이 사라진다
1~2일 메트릭 추가 주석 처리된 ChatMetrics 복구
건당 지연 · fan-out 크기
설계 변경 .get() 제거 배치가 살아난다
"언제 성공이라 할지" 재설계 필요
설계 변경 fan-out 분리 전용 브로드캐스트 레이어
또는 방 단위 샤딩
마지막 수평 확장 세션 Redis · workerId 파드번호
S3 · Kafka 3대 · 컨슈머 N개
순서가 중요하다

앞의 세 개는 지금 당장 할 수 있고 구조를 안 건드린다. 특히 메트릭이 먼저다. 측정 없이 뒤의 것들을 하면 무엇이 좋아졌는지 알 수가 없다.

그리고 수평 확장이 제일 마지막이다. 상태를 밖으로 빼지 않은 상태에서 replicas 를 올리면 장애를 자동화하는 것이다.

#6 정리

20 — 한 줄 정리

맞는 표현
  • “나중에 바꾸기 어려운 것부터 맞췄다”
  • “비동기로 뺀 건 DB 쓰기뿐이고 사용자 경로는 전 구간 동기다”
  • “처리량 대신 확실성을 택했다”
  • “병목은 처리량이 아니라 fan-out 이다”
  • “측정을 안 해서 숫자는 말씀드릴 수 없다”
쓰면 안 되는 표현
  • “대규모 트래픽을 처리한다”
  • “초당 N 건이 나온다” — 측정 안 했다
  • “동시접속 2~3만을 고려했다” — 가입자면 맞고 동시접속이면 틀리다
  • “노드당 초당 12.8만 건 처리” — 그건 ID 발급 상한이지 처리량이 아니다

21 — 자주 나오는 질문

어디가 대규모 지향인가요?
  -> 나중에 바꾸기 어려운 것부터 맞췄다
     ID 채번(Snowflake) · 데이터 흐름(Kafka) · 파티셔닝 키(roomId)
     · 연결 모델(멀티플렉싱) · 소비 모델(멱등)
     전부 지금 규모엔 필요 없는데 일부러 넣은 것들이다

그래서 초당 몇 건 되나요?
  -> 측정 안 했다고 먼저 말한다
     "병목은 처리량이 아니라 fan-out 이라고 봅니다.
      수신 1건이 방 인원만큼 송신으로 늘어나서,
      50명 방이면 1건이 50건이 됩니다"

★ acks=all 쓰셨다는데 브로커가 몇 대죠?
  -> 1대다. ISR 이 1개라 사실상 acks=1 이다
     "설정은 올바른 값이지만 내구성 보장은 실질적으로 없습니다.
      운영이면 브로커 3대 + RF 3 + min.insync.replicas 2 여야 합니다"

비동기 처리했다면서 왜 느린가요?
  -> 비동기로 뺀 건 DB 쓰기 하나뿐이다
     gRPC 도 Kafka 도 동기로 기다린다. 사용자 경로는 전부 동기다

프로세스를 5개로 나눴는데 왜 처리량이 안 늘었나요?
  -> 나눈다고 병렬이 되는 게 아니다. 1건은 여전히 직렬로 지나간다
     오히려 메서드 호출이 gRPC 호출로 바뀌어 건당 지연은 늘었다
     나눠서 얻은 건 배포 독립성 · 장애 격리 · 스케일 단위 분리다

왜 replicas 를 안 늘렸나요?
  -> 늘릴 수 있는 게 frontend 밖에 없었다
     wsgate 는 세션이 JVM 메모리, domain-service 는 파일이 로컬 EBS
     "준비 안 된 상태에서 늘리는 건 장애를 자동화하는 것"

부하 테스트는 왜 안 하셨나요?
  -> 비용. t3.medium 이 burstable 이라 지속 부하를 주면
     CPU 크레딧이 떨어져 숫자가 의미를 잃는다
     그리고 메트릭 자체가 없다(ChatMetrics 주석 처리)
     "안 한 게 맞고, 그래서 숫자를 말씀드리지 못합니다"
마지막 — 이 문서의 결론

프로젝트가 나쁜 게 아니라, 프로젝트에 대한 이해가 올라간 것이다. 코드는 어제와 똑같다.

“Kafka 써봤습니다” 로 끝나는 것과 “.get() 을 붙이면 배치가 죽는데, 처리량 대신 확실성을 택한 겁니다” 는 다른 얘기다.

진짜 고칠 것은 두 개다 — 알림 대상 캐싱과 메트릭 복구. 나머지는 트레이드오프이거나, 정상이거나, 운영 전환 때 할 일이다.
