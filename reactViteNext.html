#1 위치 관계 한눈에

넷 중 React 는 React 하나뿐이다. CRA 와 Vite 는 React 코드를 브라우저용으로 바꿔 주는 빌드 도구이고, Next.js 는 React 를 안에 품고 기능을 더 얹은 프레임워크다. 셋은 서로 다른 층에 있다.

넷의 정체와 역할

이름 정체 하는 일 배포 결과물에 Spring 으로 치면
React 라이브러리 화면을 컴포넌트로 나눠 그리고, 상태가 바뀌면 다시 그린다. 남는다. JS 파일 안에 들어간다. Spring Framework 의 핵심 기능.
CRA 빌드 도구 프로젝트 틀 · 개발 서버 · 빌드를 해 준다. 2025-02-14 지원 종료. 남지 않는다. Spring Initializr + Gradle.
Vite 빌드 도구 CRA 와 같은 일을 훨씬 빠르게 한다. 지금의 표준이다. 남지 않는다. Spring Initializr + Gradle.
Next.js 프레임워크 React + 라우팅 + 서버 렌더링 + 간단한 백엔드 + 자체 빌드 도구를 한 틀로 묶었다. 남는다. Node 서버로 계속 돈다. Spring Boot.
한 줄 정리

React 는 재료, CRA · Vite 는 그 재료를 브라우저용으로 굽는 도구, Next.js 는 React 를 품고 굽는 도구까지 들고 있는 틀이다.

짚을 점 — “셋 다 React 아니냐”

아니다. CRA 와 Vite 는 React 가 아니라 React 코드를 다루는 도구다. 그래서 CRA 에서 Vite 로 바꿔도 컴포넌트 코드는 그대로다. Gradle 을 Maven 으로 바꿔도 Java 코드가 그대로인 것과 같다.

Next.js 는 React 를 대신하는 것이 아니라 감싸는 것이다. Next.js 프로젝트의 컴포넌트도 그냥 React 컴포넌트다.

#2 React — 화면을 그리는 라이브러리

React 가 하는 일은 “화면을 어떻게 그릴지” 하나다. 화면을 컴포넌트로 나누고, useState 같은 상태가 바뀌면 그 부분을 다시 그린다. castleChat 의 ChatBox.jsx 안에서 쓴 JSX · useState · useEffect 가 전부 React 다.

2 — React 가 하지 않는 일

React 는 범위가 좁다. 나머지는 다른 라이브러리나 도구가 맡는다.

필요한 일 누가 맡나 castleChat · castleMind 에서
주소마다 다른 화면 react-router-dom RouteBody.jsx 의 <Route> 다.
서버에 HTTP 요청 axios (또는 브라우저 내장 fetch) userApi.js 다.
서버 데이터 캐시 TanStack Query castleChat 의 useMe · useFriendList 다.
화면 전체 공용 상태 Redux Toolkit + react-redux castleChat 의 chatWindowsSlice 다.
JSX 를 브라우저용 JS 로 변환 · 개발 서버 · 빌드 CRA 또는 Vite castleChat 은 CRA, castleMind 도 지금은 CRA 다.
서버에서 미리 화면 그리기 Next.js 둘 다 쓰지 않는다.

2 — 왜 빌드 도구가 꼭 필요한가

브라우저는 <div> 를 JS 안에 섞어 쓰는 JSX 문법을 이해하지 못한다. import React from 'react' 처럼 node_modules 안의 패키지를 이름으로 불러오는 것도 그대로는 못 한다. 그래서 내가 쓴 코드를 브라우저가 읽는 평범한 JS 로 바꿔 주는 단계가 반드시 필요하고, 그 일을 하는 것이 CRA 와 Vite 다.

라이브러리와 프레임워크를 가르는 기준

기준은 누가 누구를 부르느냐다. 라이브러리는 내가 필요할 때 불러 쓴다. 프레임워크는 정해진 틀에 내 코드를 끼워 넣으면 프레임워크가 내 코드를 부른다(제어의 역전).

Spring 이 @Controller 메서드를 부르는 것이 프레임워크다. React 는 스스로를 라이브러리라고 부르고, Next.js 와 Spring 은 프레임워크다.

#3 CRA 와 Vite — React 코드를 다루는 빌드 도구

CRA 와 Vite 는 완전히 같은 자리에 있다. 하는 일은 세 가지다.

  • 프로젝트 틀 만들기 — 폴더 구조와 package.json 을 한 번에 만든다.
  • 개발 서버 — npm start · npm run dev 로 띄우고, 저장하면 화면을 바로 갱신한다.
  • 빌드 — JSX 를 JS 로 바꾸고 파일을 묶어서 배포용 결과물을 만든다.

둘 다 프레임워크가 아니다. 앱이 어떻게 돌아가는지에는 관여하지 않고, 빌드가 끝나면 결과물 안에 남지도 않는다. Spring 으로 치면 Gradle 쪽이다.

3 — CRA 와 Vite 비교

CRA (react-scripts) Vite
상태 2025-02-14 지원 종료. 마지막 버전 5.0.1 은 2022년에 멈춰 있다. 계속 개발 중이고, 지금 React 프로젝트의 표준이다.
개발 서버 webpack 이 전체를 먼저 묶은 뒤에 연다. 파일이 늘수록 느려진다. 묶지 않고 브라우저가 요청한 파일만 그때그때 변환한다. 거의 바로 켜진다.
빌드 webpack + babel 이라 느리다. 더 빠르다.
설정 숨겨져 있다. 바꾸려면 되돌릴 수 없는 eject 를 해야 한다. vite.config.js 하나에 필요한 것만 적는다.
TypeScript 5 TypeScript 4 까지만 받아들이도록 묶여 있어 충돌한다. 문제없다.
결과물 폴더 build/ dist/
환경변수 process.env.REACT_APP_xxx import.meta.env.VITE_xxx
CRA 에서 Vite 로 옮기면 무엇이 바뀌나

React 코드(컴포넌트 · JSX · useState)는 그대로다. 도구와 약속한 부분만 손본다.

  • JSX 가 들어 있는 .js 파일을 .jsx 로 바꾼다. 내용은 그대로다.
  • process.env.NODE_ENV 같은 환경변수 코드를 import.meta.env 로 바꾼다. castleChat 은 wsClient.js · aiAssistApi.js 두 곳이다.
  • public/index.html 을 맨 위로 옮기고 시작 스크립트를 직접 적는다.
  • package.json 의 "proxy" 를 vite.config.js 로 옮긴다.
  • 배포라면 Dockerfile 의 build 폴더 경로를 dist 로 바꾼다.
짚을 점 — 새 프로젝트에 CRA 를 쓰지 않는 이유

패치가 더는 나오지 않아 npm audit 경고가 계속 쌓인다. TypeScript 5 와 충돌한다. 개발 서버와 빌드가 느리고 설정을 고치기 어렵다. React 공식 문서도 더 이상 CRA 를 안내하지 않는다.

다만 이미 잘 돌고 있는 CRA 프로젝트가 당장 깨지는 것은 아니다. 배포되는 결과물은 빌드된 정적 파일이라, 실제로 나가는 코드의 보안은 내 코드와 react · axios 같은 런타임 라이브러리에 달려 있다.

#4 Next.js — React 위에 지은 프레임워크

Next.js 는 React 를 고치거나 새로 만든 것이 아니다. React 를 의존성으로 그대로 쓰고, 그 위에 “화면을 언제 어디서 그릴지 · 주소를 어떻게 연결할지 · 데이터를 어디서 가져올지”를 정해 주는 틀을 얹었다.

React 가 Spring Framework 라면 Next.js 는 Spring Boot다. Spring Boot 는 Spring 을 그대로 쓰면서 자동 설정 · 내장 서버 · 정해진 규칙을 얹었다. Spring 을 알면 Boot 가 쉽지만 Boot 만의 규칙은 따로 익혀야 하는 것처럼, Next.js 도 React 를 그대로 가져가고 그 위의 규칙을 더 배운다.

4 — React + Vite 와 Next.js 는 무엇이 다른가

React + Vite Next.js
주소 연결 react-router-dom 의 <Route> 로 직접 연결한다. 파일 위치가 곧 주소다. app/ladder/page.jsx 가 /ladder 가 된다.
컴포넌트가 도는 곳 전부 브라우저에서 돈다. 기본이 서버다. useState · onClick 이 필요한 파일은 맨 위에 "use client" 를 적어야 브라우저에서 돈다.
데이터 가져오기 화면이 뜬 뒤 useEffect + axios 로 가져온다. 서버 컴포넌트 안에서 바로 await 로 DB 나 API 를 부른다.
첫 화면 빈 HTML 이 먼저 오고, JS 가 실행된 뒤에 그려진다. 서버에서 그린 HTML 이 바로 온다. 첫 화면이 빠르고 검색 엔진에 잘 잡힌다.
백엔드 Express 같은 서버를 따로 둔다. Route Handler · Server Action 으로 간단한 API 를 같은 프로젝트에 둔다.
빌드 도구 Vite. Next.js 가 자체적으로 들고 있다. CRA · Vite 자리를 대신한다.
배포 정적 파일을 NGINX 에 올리면 끝난다. 서버 기능을 쓰면 Node 서버로 계속 띄워 둬야 한다.
배우는 입장에서는 “확장” 에 가깝다

JSX · props · useState · useEffect 같은 React 기본기는 100% 그대로 가져간다. 파일 라우팅과 API 기능은 금방 익힌다.

진짜 학습량은 서버 컴포넌트와 클라이언트 컴포넌트의 구분, 서버에서 데이터를 가져오는 흐름, 렌더링 방식과 캐시 규칙이다. 지금까지 쓴 React 는 전부 브라우저에서만 돌았기 때문에 이 감각이 새롭다.

#5 정리 — 무엇을 쓰나

  • castleMind — React + Vite + Express 가 맞다. Express 와 WebSocket 서버를 따로 만들기 때문에 Next.js 의 서버 기능은 Express 와 역할이 겹친다. 프론트가 아직 작아서 CRA 에서 Vite 로 옮기는 비용도 지금이 가장 싸다.
  • castleChat — CRA 로 만들어져 배포되어 있다. 당장 깨지지 않으니 여유 있을 때 Vite 로 옮기면 된다.
  • 다른 프로젝트 — 어떤 도구를 쓰는지는 package.json 을 보면 바로 안다.

package.json 에서 찾는 이름

"react-scripts"   <- CRA
"vite"            <- Vite
"next"            <- Next.js
"react"           <- React itself. always there

castleMind 프론트 — CRA 에서 Vite 로 변경

React 코드(컴포넌트 · userApi.js · CSS)는 한 줄도 바뀌지 않았다. 도구와 약속한 부분만 바꿨다. Java 코드는 그대로 두고 build.gradle 만 다른 빌드 도구 설정으로 갈아 끼운 것과 같다.

1 — 바뀐 대상

대상 무엇을 어떻게
index.html 앱의 시작 HTML public/index.html 을 프로젝트 맨 위로 옮겼다. CRA 전용 표기 %PUBLIC_URL% 와 CRA 안내 주석을 지우고, <script type="module" src="/src/index.jsx"> 를 직접 적었다. CRA 가 몰래 해 주던 “JS 끼워 넣기” 를 Vite 에서는 HTML 에 명시한다.
src/index.js 앱 시작 파일 index.jsx 로 확장자를 바꿨다. Vite 는 JSX 가 든 파일이 .jsx 여야 한다. CRA 성능 측정 코드 reportWebVitals() 호출도 지웠다.
src/App.js 최상위 컴포넌트 App.jsx 로 확장자만 바꿨다. 내용은 그대로다.
vite.config.js Vite 설정 (새 파일) React 플러그인을 등록하고, 개발 서버 포트를 3000 으로 두고, /user 요청을 Express(4000)로 넘기는 proxy 를 넣었다. CRA 때 package.json 의 "proxy" 가 하던 일이다.
package.json 실행 명령과 설정 scripts 를 dev · build · preview · lint 로 바꿨다. "type": "module" 을 넣었다.
eslint.config.js 코드 검사 설정 (새 파일) CRA 의 react-scripts 안에 숨어 있던 ESLint 를 Vite 공식 템플릿과 같은 구성으로 다시 붙였다. JS 기본 규칙 · Hook 규칙 · Vite 화면 갱신 규칙을 쓰고, npm run lint 로 실행한다.
.gitignore 빌드 결과 폴더 /dist 를 추가했다. CRA 는 build/, Vite 는 dist/ 에 결과물을 만든다.

2 — 설치한 것

패키지 역할
vite 개발 서버 · 빌드 도구 본체다. -D 로 설치해서 devDependencies 에 들어가고 배포 결과물에는 들어가지 않는다.
@vitejs/plugin-react Vite 가 JSX 를 변환하고, 저장하면 화면 상태를 유지한 채 바로 갱신하게 해 준다. 역시 -D 로 설치한다.
eslint 코드 검사 도구 본체다. -D 로 설치한다.
@eslint/js JS 기본 규칙 묶음이다. 안 쓰는 변수, 선언 안 된 변수 같은 실수를 잡는다. -D 로 설치한다.
globals window · document 같은 브라우저 전역 변수를 “선언 안 된 변수” 로 오해하지 않게 알려 준다. -D 로 설치한다.
eslint-plugin-react-hooks Hook 규칙을 검사한다. 조건문 안의 Hook, useEffect 의존성 배열 누락을 잡는다. -D 로 설치한다.
eslint-plugin-react-refresh Vite 의 화면 즉시 갱신이 깨지는 export 방식을 경고한다. -D 로 설치한다.

3 — 삭제한 것

  • package.json 의 eslintConfig · browserslist · proxy 설정을 지웠다. 셋 다 CRA(react-scripts)가 읽던 설정이라 Vite 에서는 쓰이지 않는다. proxy 는 vite.config.js 로 옮겼다.
  • CRA 와 함께 깔려 있던 패키지 6개(react-scripts · web-vitals · @testing-library 4개)를 지웠다. CRA 에 내장되어 있던 ESLint 도 react-scripts 와 함께 빠졌고, 새로 설치한 ESLint 와 eslint.config.js 로 대신한다.
  • CRA 기본 파일 4개를 지웠다. 어디서도 쓰지 않던 견본 파일이라 앱 동작에는 영향이 없다. reportWebVitals.js(성능 측정 견본) · setupTests.js(Jest 테스트 설정) · App.test.js(견본 테스트) · logo.svg(CRA 로고 그림).
  • public/index.html 은 지운 것이 아니라 프로젝트 맨 위로 옮긴 것이다. public/ 의 favicon · 아이콘 · manifest.json 은 그대로 쓴다.

4 — 실행한 명령어

모두 castle_mind_front 에서 실행했다.

삭제 — CRA 와 함께 깔려 있던 패키지

npm uninstall react-scripts
npm uninstall web-vitals
npm uninstall @testing-library/dom
npm uninstall @testing-library/jest-dom
npm uninstall @testing-library/react
npm uninstall @testing-library/user-event

삭제 — CRA 기본 파일

del src\reportWebVitals.js
del src\setupTests.js
del src\App.test.js
del src\logo.svg

설치 — Vite · ESLint

npm install -D vite
npm install -D @vitejs/plugin-react
npm install -D eslint
npm install -D @eslint/js
npm install -D globals
npm install -D eslint-plugin-react-hooks
npm install -D eslint-plugin-react-refresh
실행 명령이 바뀌었다

프론트 개발 서버는 npm start 대신 npm run dev 로 띄운다. Vite 프로젝트의 표준 이름이고, express_server 의 npm run dev 와 이름도 맞춰진다. 주소는 그대로 http://localhost:3000 이다.
