Q1 — 다른 프로그램도 많은데 Kafka 를 선택한 이유가 뭔가요

핵심 이유 — DB 쓰기를 응답 경로에서 뺐다

가장 먼저 말할 것은 이것이다. “메시지를 보낸 사람에게 언제 성공이라고 답할 것인가” 의 문제다. 

[ DB 동기 ]   메시지 수신 -> DB INSERT 완료까지 대기 -> 성공 응답
[ Kafka  ]   메시지 수신 -> Kafka 가 받았다고 할 때까지 대기 -> 성공 응답
                                                            DB INSERT 는 worker 가 나중에

원래 sendMessage 경로에 있던 DB 쓰기

출처는 z_md_Files/chatKafka.md A절이다. 기존 흐름은 이랬다.

ChatCommandService.createChatMessage()
  -> DB insert (동기) -> auto_increment 로 messageId 발급
  -> response 조립 -> client 응답          <== prpr 3 위반
쿼리 하는 일 지금은
1 insertChatMessage chat_messages 에 메시지 본문 INSERT. 예전엔 여기서 auto_increment 로 messageId 를 받았다 worker 가 Kafka 소비 후. INSERT IGNORE + messageId 명시(멱등)
2 updateChatMessageAttachments 첨부 row 를 TEMP → ATTACHED 로 바꾸고 messageId 를 박는다. 첨부 있을 때만 worker
3 updateLastReadMessageId 보낸 사람 본인의 읽음 위치(lrm)를 자기 메시지까지 올린다 Redis write-behind. ReadPositionFlushWorker 가 5초마다 모아서 DB 에 반영
3번은 Kafka 때문에 바뀐 게 아니다

설계 문서에 “Redis lrm updateIfGreater (sender 본인 읽음위치. 기존과 동일)” 라고 적혀 있다.

읽음 위치는 prpr 4번 원칙 때문에 처음부터 write-behind 였고, Kafka 도입으로 옮긴 건 1번과 2번이다. 이 구분을 섞어 말하면 꼬인다.

진짜 이점은 부하가 걸렸을 때 나온다

DB 동기 INSERT Kafka
작업 성격 INSERT + 첨부 UPDATE + 인덱스 갱신 + 트랜잭션 + 행 잠금 로그 끝에 순차 append 만. 인덱스도 락도 없다
부하가 오르면 락 경합으로 급격히 나빠진다 거의 선형으로 버틴다
읽기에 주는 영향 ★ 같은 DB 라 채팅방 열기 · 이전 메시지 조회까지 같이 느려진다 읽기 경로와 완전히 분리된다
커넥션 풀 Hikari 5개. 쓰기가 밀리면 읽기 요청도 대기한다 DB 커넥션을 쓰지 않는다
순간 몰릴 때 몰린 만큼 그대로 사용자 지연이 된다 쌓아두고 worker 가 자기 속도로 소화한다
DB 가 잠깐 죽으면 메시지를 아예 못 보낸다 송수신은 계속된다. 밀린 건 나중에 따라잡는다

위 표에 나온 말들 — 구체적으로

① 락 경합 — 누가 무엇을 두고 다투나

여러 트랜잭션이 같은 자원을 동시에 건드리려 할 때 하나만 들어가고 나머지는 줄 서서 기다리는 것이다. 채팅 메시지 INSERT 한 건에서 실제로 다투는 자원은 이렇다.

자원 왜 다투나
인덱스 리프 페이지
제일 큰 원인		 messageId 가 Snowflake 라 시간순으로 계속 커진다. 그래서 모든 INSERT 가 B+트리의 맨 오른쪽 페이지 한 곳으로 몰린다. 동시에 열 건이 들어오면 그 한 페이지를 열 트랜잭션이 번갈아 잠근다
행 잠금
row lock		 첨부 연결 UPDATE 처럼 기존 행을 고칠 때 그 행에 배타 잠금이 걸린다. 같은 행을 건드리는 다른 트랜잭션은 대기
redo 로그 · fsync 커밋할 때마다 디스크에 기록을 확정해야 한다. 디스크 쓰기는 한 번에 하나라 커밋이 몰리면 여기서 줄을 선다
커넥션 풀 Hikari 가 5개뿐이라 6번째 요청은 누가 반납할 때까지 기다린다. 이것도 경합이다

InnoDB 가 뭔가 — 스토리지 엔진

MySQL / MariaDB 에서 “실제로 디스크에 어떻게 저장하고 읽을지” 를 담당하는 부품이다. SQL 을 해석하는 부분과 저장하는 부분이 나뉘어 있다.

SQL 파서 · 옵티마이저        SQL 을 해석하고 실행 계획을 짠다
        |
스토리지 엔진 (InnoDB)       ★ 실제 저장 · 읽기 · 잠금 · 트랜잭션
        |
디스크

같은 SQL 을 써도 엔진을 바꾸면 저장 방식이 달라진다
  InnoDB   기본값. 트랜잭션 · 행 잠금 · 외래키 · 크래시 복구
  MyISAM   옛 기본값. 트랜잭션 없음. 테이블 전체를 잠근다
  Memory   메모리에만 둔다. 재시작하면 사라진다
InnoDB 의 성질 뜻
클러스터형 인덱스 테이블 자체가 PK 로 정렬된 B+트리다. 인덱스가 테이블 옆에 따로 있는 게 아니라 행 데이터가 PK 순서대로 디스크에 줄 서 있다
행 잠금 테이블 전체가 아니라 행 단위로 잠근다. 그래서 동시에 여러 트랜잭션이 다른 행을 고칠 수 있다
트랜잭션 · MVCC 커밋 · 롤백이 되고, 읽기는 쓰기를 기다리지 않는다
버퍼 풀 자주 쓰는 페이지를 메모리에 캐싱한다. 여기 없으면 디스크를 읽어야 한다
페이지 단위 저장 · 읽기 · 잠금이 전부 16KB 페이지 단위로 일어난다

앞에서 말한 16KB 페이지 · redo 로그 · 래치 가 전부 InnoDB 얘기다. MariaDB 의 기본 엔진이라 내 테이블도 InnoDB 다.

그림 — 왜 맨 오른쪽 한 장으로 몰리나

그럼 PK 를 무작위로 하면 되나 — 트레이드오프

순차 PK (Snowflake · AUTO_INCREMENT) 무작위 PK (UUID v4)
들어가는 위치 항상 맨 끝 한 페이지 A, F, K, Z 아무 데나
래치 경합 ★ 한 페이지에 몰린다 흩어진다
페이지 분할 거의 없다. 끝에 붙이기만 한다 ★ 자주 일어난다. 꽉 찬 페이지 중간에 끼우려면 반으로 쪼개야 한다
디스크 I/O 순차 랜덤
버퍼 풀 마지막 페이지만 메모리에 있으면 된다 테이블 전체가 필요하다시피 하다

실무에서는 순차 PK 가 압도적으로 유리하다. 마지막 페이지 경합은 초당 수천 건은 넘어야 눈에 띄지만, 페이지 분할과 랜덤 I/O 는 훨씬 일찍 문제가 된다.

물어보면 이렇게

messageId 가 시간순이라 항상 B+트리 맨 오른쪽 페이지에 들어갑니다. 그래서 동시 INSERT 가 그 한 페이지를 두고 줄을 서게 됩니다.

대신 중간에 페이지가 쪼개지는 일이 없고 디스크를 순차로 씁니다. UUID 같은 무작위 키면 경합은 흩어지지만 페이지 분할과 랜덤 I/O 가 생기는데, 그쪽 비용이 훨씬 커서 순차 키를 택했습니다.

그리고 저는 애초에 PK 를 미리 확정해야 응답을 메모리에서 만들 수 있어서 Snowflake 가 필요했습니다.

짚을 점 — Snowflake 의 그림자

시간순 단조증가는 정렬 · 페이징에는 유리하지만, INSERT 가 한 페이지에 몰린다는 단점이 따라온다. AUTO_INCREMENT 도 똑같은 성질이다.

물어보면 아는 척하지 말고 이렇게 — “시간순이라 맨 끝 페이지에 몰리는 건 맞습니다. 대신 중간에 페이지가 쪼개지지 않아 그쪽 비용은 줄었습니다. 트레이드오프라고 봤습니다.”

② “선형으로 버틴다” — 숫자로

선형     요청이 2배 늘면 건당 시간은 거의 그대로. 전체 처리량만 2배
비선형   요청이 2배 늘면 건당 시간이 3배 · 5배로 튄다
DB 가 비선형인 이유
  • 락을 기다리는 시간이 동시성보다 빠르게 늘어난다. 줄이 길어지면 기다리는 동안 다른 것도 같이 막힌다
  • 버퍼 풀에 없는 페이지를 건드리면 디스크 랜덤 I/O 가 발생한다. 랜덤 쓰기는 순차 쓰기보다 수십 배 느리다
  • 커넥션 풀이 고갈되면 대기 → 타임아웃 → 재시도가 부하를 더 키운다
Kafka 가 선형에 가까운 이유
  • 파일 끝에 붙이기만 한다. 인덱스도 없고 고칠 행도 없다
  • 디스크 머리가 움직이지 않는 순차 쓰기다. 순차는 수백 MB/s, 랜덤은 그보다 훨씬 낮다
  • OS 페이지 캐시에 쓰고 디스크 반영은 OS 가 알아서 한다

그래서 “선형” 보다 “동시 요청이 늘어도 건당 시간이 거의 안 변한다” 라고 말하는 게 덜 추상적이다.

③ Hikari 가 뭔가

HikariCP — DB 커넥션 풀 라이브러리다. Spring Boot 의 기본 커넥션 풀이라 따로 추가하지 않아도 들어 있다.

DB 연결 하나를 새로 만들려면
  TCP 핸드셰이크 + 인증 + 세션 설정  =  수십 ms

요청마다 만들면 너무 느리다
  -> 미리 N개 만들어두고 "빌려주고 돌려받는다"  = 커넥션 풀

SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE: "5"
  -> 커넥션 5개. 6번째 요청은 누가 반납할 때까지 대기한다

5로 잡은 이유는 ConfigMap 주석에 적어뒀다 — RDS db.t4g.micro 의 max_connections 가 약 40인데 DB 를 쓰는 서비스가 5개라, 기본값 10이면 50개가 필요해 Too many connections 가 난다.

④ “DB 커넥션을 쓰지 않는다” — 표현이 모호했다

정확히는 이렇다

channel-engine 도 DB 에 연결되어 있다. 조회를 하니까 당연히 연결돼 있다. 위 표의 말은 “Kafka 에 발행하는 그 동작이 DB 커넥션을 점유하지 않는다” 는 뜻이었다.

메시지 전송 1건에서

DB 커넥션을 쓰는 것
  findAllActiveMemberIdsInRoom          Redis 미스일 때만
  findChatAttachmentsByIds              첨부 있을 때만
  findChatMessageNotificationTargetUserIds   ★ 항상 (캐시 없음)

DB 커넥션을 안 쓰는 것
  kafkaTemplate.send()      Kafka 브로커로 가는 별도 TCP 연결을 쓴다

핵심은 INSERT 가 커넥션을 점유하지 않는다는 것이다. 동기 INSERT 였다면 트랜잭션이 끝날 때까지 커넥션 하나를 계속 쥐고 있어야 한다.

더 중요한 건 “누구의 풀” 이냐다 
channel-engine       Hikari 5개   조회에 쓴다
event-persist-worker Hikari 5개   ★ 별도 프로세스라 풀도 별도다

-> 메시지 쓰기 트랜잭션이 "worker 의 풀" 을 쓴다
-> channel-engine 의 조회용 풀이 쓰기 때문에 고갈되지 않는다

쓰기와 읽기가 서로 다른 커넥션 풀을 쓰게 된 것이 분리에서 얻은 실질적인 이득이다.

⑤ worker 는 초당 몇 건을 처리하나

설정한 적 없다 — 전부 기본값이다 
spring.kafka.listener.concurrency     설정 없음 -> 기본 1  (리스너 스레드 1개)
max.poll.records                      설정 없음 -> 기본 500 (poll 한 번에 최대 500건)
max.poll.interval.ms                  설정 없음 -> 기본 5분

-> 처리 속도는 설정이 정하는 게 아니라 "DB INSERT 속도" 가 정한다
   설정은 상한만 정할 뿐이다
@KafkaHandler
@Transactional                 ★ 레코드 1건당 트랜잭션 1개
public void persistChatMessage(ChatMessageCreatedEventDTO event) { ... }

건당  INSERT + (첨부 있으면) UPDATE + 커밋 fsync   =  대략 2 ~ 10ms
  -> 초당 100 ~ 500건 정도로 추정된다
  ★ 측정한 적 없다. 추정이라고 말해야 한다
제일 싼 개선 — concurrency 
spring.kafka.listener.concurrency=6

파드를 안 늘리고도 한 파드 안에서 컨슈머 스레드를 여러 개 만든다. 파티션이 6개이므로 6까지 의미가 있다.

지금은 1개 스레드가 파티션 6개를 순서대로 처리한다. 설정 한 줄로 6배 병렬이 된다 — DB 가 받아준다는 전제에서.

그 다음 단계는 배치 INSERT 다. BatchListener 로 500건을 받아 INSERT ... VALUES (..),(..) 한 번으로 묶으면 커밋 횟수가 500분의 1이 된다.

덧붙임 — 측정 수단이 아주 없지는 않다 
# worker 의 application.properties 에 이미 있다
management.endpoints.web.exposure.include=health,info,metrics,prometheus
management.prometheus.metrics.export.enabled=true

Micrometer 가 Kafka 컨슈머 메트릭을 자동으로 모은다. 수집기를 붙이면 records-lag(밀린 건수) 를 볼 수 있다.

다만 건당 처리 시간 같은 커스텀 메트릭은 없다 (ChatMetrics 가 주석 처리돼 있다). “얼마나 밀리는지는 볼 수 있지만 왜 느린지는 모른다” 가 정확하다.

그대로 말할 수 있는 문장

평상시 단건 지연은 비슷합니다. 오히려 Kafka 가 조금 느릴 수도 있습니다.

이점은 부하가 걸렸을 때 나타난다고 봤습니다. DB INSERT 는 인덱스 갱신과 행 잠금이 걸려서 동시 쓰기가 늘면 급격히 느려지는데, Kafka 는 로그 끝에 순차로 붙이기만 해서 선형에 가깝게 버팁니다.

그리고 같은 DB 로 채팅방 읽기도 하고 있어서, 쓰기가 밀리면 읽기까지 같이 느려지는 게 더 문제였습니다. Hikari 풀이 5개뿐이라 쓰기가 점유하면 조회가 대기합니다.

UX 에서 중요한 건 평균보다 응답 시간이 튀지 않는 것이라고 생각했습니다.

용어 — “비동기 처리했다” 는 부정확하다

.get() 으로 브로커 응답까지 기다리므로 발행 자체는 동기다. 비동기인 건 worker 쪽이다.

정확한 표현은 “DB 쓰기를 응답 경로에서 뺐다” 다. “비동기로 처리했다” 고 하면 “그럼 유실은요?” 가 바로 온다.

“디스크에 순차로만 쌓는 구조라 처리량이 높고, 소비해도 지우지 않습니다. 그래서 소비자가 죽어도 유실이 없고, 되감아 재처리하거나 소비자를 나중에 붙일 수 있습니다.”

이 한 줄이 Kafka 만의 차이를 짚는다. “빠르다” · “확장된다” 는 어느 메시지 큐나 하는 말이지만, “소비해도 안 지운다” 는 로그 기반이라 가능한 것이고 재처리 · 다중 소비 · 유실 방지가 전부 거기서 나온다.

그리고 다음 질문을 내가 준비한 쪽으로 끌어온다. 아래 둘이 거의 반드시 온다.

꼬리질문 — “재처리는 어떻게 하나요?”

답변

“컨슈머 그룹의 offset 을 되돌리거나, 새 groupId 로 띄우면 됩니다. 브로커가 그룹마다 offset 을 따로 들고 있어서 메시지를 다시 보내달라고 할 필요가 없습니다.”

방법 1 — offset 을 되감는다
  kafka-consumer-groups.sh --reset-offsets       --group event-persist-worker --topic castlechat.chat.message       --to-earliest   (또는 --to-offset N / --to-datetime ...)
  ★ 그 그룹이 멈춰 있어야 한다. 돌고 있으면 거부된다

방법 2 — 새 groupId 로 띄운다
  spring.kafka.consumer.auto-offset-reset=earliest   <- 내 설정에 이미 있다
  -> 처음부터 다시 읽는다. 기존 worker 는 건드리지 않는다

방법 3 — DLT 에 쌓인 것만 다시 넣는다
  castlechat.chat.message.dlt 를 읽어 원본 토픽으로 재발행
★ 재처리가 가능한 진짜 이유 — 멱등하게 짰기 때문 
insertChatMessage 는 INSERT IGNORE + messageId 명시
  -> 이미 있는 건 0행으로 넘어간다
  -> 전체를 다시 읽어도 중복이 안 생긴다

멱등하지 않았다면 재처리가 곧 중복 생성이 된다. “되감으면 된다” 는 소비 쪽이 멱등할 때만 성립하는 말이다. 이걸 같이 말해야 아는 사람으로 보인다.

선을 그을 것

보관 기간(기본 7일) 안의 것만 가능하다. 지난 건 브로커에서 이미 지워졌다.

그리고 재처리 도구나 스크립트를 만들어두진 않았다. “구조상 가능하지만 자동화는 안 해뒀습니다” 가 정확하다.

꼬리질문 — “소비자를 추가한다는 게 무슨 뜻이죠?”

답변

“groupId 가 다른 애플리케이션을 하나 더 띄우면 같은 토픽을 독립적으로 전부 받습니다. 기존 소비자도, 발행하는 쪽도 코드를 건드릴 필요가 없습니다.”

지금
  groupId = event-persist-worker      -> DB 저장

나중에 검색 색인을 붙인다면
  groupId = search-indexer 로 새 앱을 띄운다
  -> 같은 castlechat.chat.message 토픽을 구독
  -> event-persist-worker 는 한 줄도 안 바뀐다
  -> channel-engine 은 그런 게 생긴 줄도 모른다

같은 그룹      파티션을 나눠 먹는다   (일을 분담)
다른 그룹      각자 전부 받는다      (용도가 다름)

가능한 이유는 브로커가 그룹마다 offset 을 따로 관리하기 때문이다. __consumer_offsets 라는 내부 토픽에 저장된다.

대비해서 말하면 더 선명하다

RabbitMQ 라면 exchange 에 큐를 하나 더 매달아야 하고, 그렇게 해도 그 시점 이후 메시지만 받는다.

Kafka 는 auto-offset-reset=earliest 로 띄우면 보관 기간 안의 과거 것부터 전부 받는다. “발행하는 쪽이 구독자를 몰라도 된다” 의 실제 이득이 이것이다.

강점 이유
소비해도
안 지운다		 보관 기간(기본 7일)까지 남는다. 컨슈머는 offset 이라는 번호만 들고 다닌다. 그래서 리플레이(offset 되감기)와 다중 그룹이 가능하다
디스크인데
빠르다		 추가만 하는 로그라 디스크를 순차로만 쓴다. 여기에 OS 페이지 캐시와 zero-copy(커널에서 소켓으로 바로)가 붙는다. 랜덤 I/O 가 없어서 디스크가 병목이 안 된다
파티션으로
수평 확장		 토픽을 파티션으로 쪼개 여러 브로커에 분산한다. 컨슈머도 파티션 수만큼 병렬로 붙는다
배치와 압축 linger.ms 동안 모아 한 번에 보낸다. 건당 네트워크 왕복이 사라져 처리량이 올라간다
복제로
내구성		 파티션마다 리더 + 팔로워. acks=all 이면 ISR 전부가 복제할 때까지 기다린다. 리더가 죽으면 팔로워가 승격
약점도 같이 말하는 게 낫다
  • 운영이 복잡하다. 브로커 대수 · 파티션 수 · RF 를 미리 설계해야 하고, 파티션 수는 나중에 바꾸기 어렵다
  • 단건 삭제도 우선순위도 없다. 로그라서 중간을 건드릴 수 없다
  • 지연이 아주 낮지는 않다. 배치가 전제라 건당 즉시성이 필요하면 안 맞는다
  • at-least-once 다. 중복이 올 수 있어 소비 쪽이 멱등해야 한다

강점만 읊으면 “그럼 단점은요” 가 바로 온다. 먼저 꺼내자.

S

단일 책임		 클래스가 바뀌어야 할 이유는 하나여야 한다. “누가 이 클래스를 고치라고 요구하는가” 가 한 종류여야 한다는 뜻 위반 — 한 클래스가 JSON 파싱 + 인증 + 비즈니스 로직 + 소켓 전송을 다 한다. 전송 방식만 바꿔도 그 거대한 클래스를 건드린다

O
Open-Closed
개방 폐쇄		 확장에는 열려 있고 수정에는 닫혀 있어야 한다. 기능을 추가할 때 기존 코드를 안 고치는 것이 목표 위반 — switch (wsType) 에 새 case 를 계속 추가한다
지킴 — Map<String, Handler> 에 등록해두고 꺼내 쓴다. 새 타입은 새 클래스 하나만 추가하면 된다
L
Liskov Substitution
리스코프 치환		 자식 타입은 부모 자리에 넣어도 프로그램이 깨지지 않아야 한다. “부모가 한 약속을 자식이 어기지 마라” 위반 — 부모 save() 는 항상 저장하는데 자식이 조건에 따라 아무것도 안 하거나 UnsupportedOperationException 을 던진다. 부모 타입으로 쓰던 코드가 터진다
지킴 — 자식이 부모보다 더 까다로운 입력을 요구하지 않고, 더 약한 결과를 돌려주지 않는다
I
Interface Segregation
인터페이스 분리		 안 쓰는 메서드까지 떠안기는 뚱뚱한 인터페이스를 만들지 않는다 위반 — ChatUseCase 하나에 조회 5개 + 쓰기 5개. 읽기만 필요한 쪽도 쓰기 메서드를 다 구현해야 한다

D
Dependency Inversion
의존 역전		 구체가 아니라 추상에 의존한다. 상위 모듈이 하위 모듈의 구현을 몰라야 한다 위반 — 핸들러가 WsGateChatClientGrpc(구현체)를 직접 쥔다. REST 로 바꾸면 핸들러도 고쳐야 한다
지킴 — private final WsGateChatClient(인터페이스). 구현체를 바꿔도 핸들러는 한 줄도 안 바뀐다

SRP   "이 클래스가 하는 일" 이 하나인가     -> 구현체 쪽 이야기
ISP   "이 인터페이스를 구현하는 쪽" 이       -> 사용자/구현자 쪽 이야기
      안 쓰는 메서드까지 떠안는가

SRP 는 만드는 사람 관점, ISP 는 쓰는 사람 관점이다.

보통의 의존 방향
  핸들러(상위)  ->  gRPC 클라이언트(하위)      상위가 하위를 안다

역전시키면
  핸들러(상위)  ->  WsGateChatClient (인터페이스)
                          ^
                    WsGateChatClientGrpc (하위가 인터페이스를 구현)

  ★ 하위가 상위가 정한 규격을 따르게 된다 = 방향이 뒤집혔다

인터페이스를 누가 소유하느냐가 핵심이다. WsGateChatClient 는 게이트웨이 쪽에 있다. gRPC 구현이 거기 맞추는 것이다.

외운 티를 안 내려면

정의만 읊으면 “그래서 어디에 쓰셨나요” 가 바로 온다. 정의 한 줄 + 내 코드 한 줄을 묶어서 말하는 게 낫다.

예 — “DIP 는 구체가 아니라 추상에 의존하라는 건데, 제 WebSocket 핸들러가 gRPC 구현체가 아니라 WsGateChatClient 인터페이스에만 의존합니다.”

Q5 — OOP 5원칙을 프로젝트 어디에 어떻게 적용했나요

DIP — 가장 뚜렷한 사례

// WsGateChatHandler.java:49
private final WsGateChatClient wsGateChatClient;    // ★ 인터페이스에 의존
                ^^^^^^^^^^^^^^^^ 구현체(WsGateChatClientGrpc)를 모른다

WsGateChatClient          (인터페이스)
  └ WsGateChatClientGrpc  (구현체 — chEngineStub 을 들고 gRPC 호출)

핸들러는 “메시지를 만들어 달라” 고만 하고 그게 gRPC 인지 REST 인지 모른다. 통신 방식을 바꿔도 핸들러 코드는 한 줄도 안 바뀐다.

같은 패턴이 인터페이스 · 구현체 쌍 15개에 걸쳐 있다 — WsGateFriendClient, WsGateRoomClient, ChatCommandUseCase, RoomQueryUseCase …

SRP — 역할별로 쪼갰다

클래스 책임
WsGateDispatcher 라우팅만. JSON 을 DTO 로 바꾸고 wsType 으로 담당 핸들러에 넘기는 것까지
WsGateChatHandler 채팅 요청 처리. 친구 · 방 · 연결은 각각 다른 핸들러가 맡는다
WsGateOutboundWriter 내보내는 일만. 직렬화 · 세션 락 · 브로드캐스트
WsGateSessionRegistry 세션 명부만. 비즈니스 로직이 없다
WsGateAuth 세션에서 로그인 유저를 꺼내는 것만

“바뀌어야 할 이유가 하나” 가 실제로 지켜진다 — 전송 방식을 바꾸면 OutboundWriter 만, 새 요청 종류가 생기면 Dispatcher 와 해당 핸들러만 건드린다.

ISP — Command 와 Query 를 갈랐다

domain-service
  ChatCommandUseCase  /  ChatQueryUseCase
  RoomCommandUseCase  /  RoomQueryUseCase
  UserCommandUseCase  /  UserQueryUseCase

chengine.proto
  service ChEngineChat   StartDirectChat · CreateChatMessage · ReadChatMessage ...
  service ChEngineRoom   OpenDirectChatRoom · EnterRoom · InviteMember ...
  ★ 하나의 거대한 service 로 안 묶었다

읽기만 필요한 쪽이 쓰기 메서드까지 떠안지 않는다. proto 도 도메인별로 service 를 나눠 같은 원칙을 지켰다.

캡슐화 — 주석에 의도를 남겼다

// WsGateSessionRegistry
private final Map<Long, Map<Long, WebSocketSession>> roomSessions = new ConcurrentHashMap<>();

// 주석 그대로 :
// "세션 명부의 원본은 하나만 둔다. 그 원본은 아무나 직접 못 만진다.
//  오직 SessionRegistry 내부에 정해진 메서드로만 간접적으로 접근/변경한다."

private final 로 막고 getRoomSessions(), getViewingUserIds() 같은 메서드로만 열어뒀다. 맵을 밖에 노출하면 네 개의 색인이 서로 어긋난다.

상속 · 다형성

public class WsGateDispatcher extends TextWebSocketHandler {
    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) { ... }
}

Spring 은 WebSocketHandler 타입으로만 알고 handleMessage() 를 부른다
  -> 부모가 타입을 보고 분기 -> 내가 재정의한 handleTextMessage() 가 실행된다
  ★ 호출하는 쪽은 내 클래스를 모른다 = 다형성
선을 그을 것 — OCP 와 LSP

OCP 와 LSP 는 뚜렷한 사례가 없다. Dispatcher 의 switch 는 새 타입이 생길 때마다 기존 코드를 고쳐야 하므로 오히려 OCP 위반에 가깝다.

물어보면 솔직하게 말하는 쪽이 낫다 — “switch 가 늘어나는 구조라 OCP 관점에서는 약합니다. 핸들러를 Map<wsType, Handler> 로 등록하는 방식으로 바꾸면 개선될 것 같습니다.”

억지로 다섯 개를 다 채우려 하면 거기서 무너진다. 확실한 셋(DIP · SRP · ISP)만 깊게 말하는 게 낫다.

Q6 — 프로세스 간 통신 방법이 많은데 왜 gRPC 인가요

후보 안 쓴 이유
REST
(JSON/HTTP)		 계약이 빌드에 참여하지 않는다. 명세를 고쳐도 코드는 그대로 컴파일되고, 어긋난 건 런타임에야 드러난다
메시지 큐 응답을 받아야 하는 호출에는 안 맞는다. 메시지 생성 결과(messageId 등)를 바로 돌려받아야 한다
공유 DB 서비스를 나눈 의미가 사라진다. 스키마가 바뀌면 전부 같이 깨진다
핵심은 속도가 아니라 “계약” 이다

“REST 보다 빠릅니다” 만 말하면 약하다. 내부 통신에서 진짜 문제는 속도가 아니라 두 서비스의 약속이 어긋나는 것이다.

gRPC 는 .proto 파일 하나가 양쪽의 단일 진실이고, 거기서 DTO 와 스텁이 자동 생성된다. 약속이 어긋나면 컴파일이 안 된다.

“문서로만 존재한다” 가 무슨 뜻인가

.proto 도 문서다. 차이는 그 문서가 빌드에 참여하느냐다.

[ REST ]
  Swagger · 위키에 "messageText 는 string" 이라고 적혀 있다
    -> 서버 개발자가 DTO 를 손으로 만든다
    -> 클라이언트 개발자도 DTO 를 손으로 만든다
    -> ★ 둘이 같은지 아무도 검사하지 않는다

  서버가 messageText 를 content 로 바꾸면?
    문서를 고쳐도 클라이언트 코드는 그대로 컴파일된다
    -> 런타임에 content 가 null 로 들어온다
    -> 테스트에서 안 걸리면 운영에서 터진다

[ gRPC ]
  chengine.proto 는 "코드를 생성하는 입력" 이다
    -> 빌드할 때 Request/Response 자바 클래스가 생성된다
    -> 서버도 클라이언트도 생성된 "같은 클래스" 를 쓴다

  proto 에서 message_text 를 content 로 바꾸면?
    생성된 클래스에서 getMessageText() 가 사라진다
    -> 그걸 쓰던 코드가 컴파일 에러
    -> ★ 빌드에서 잡힌다

한 줄로 하면 — REST 의 계약은 사람이 읽고 손으로 옮겨 적는 것이고, gRPC 의 계약은 기계가 읽어 코드로 만드는 것이다.

내 구조에서 특히 강한 이유가 하나 더 있다. common-contract 가 공유 Gradle 모듈이라 channel-engine 과 websocket-gateway 가 같은 jar 를 의존한다. 한쪽만 몰래 바꿀 수가 없다.

공정하게 덧붙일 것

REST 도 OpenAPI 명세 + 코드 생성기를 쓰면 비슷하게 할 수 있다. 차이는 gRPC 는 그게 기본 방식이고 REST 는 선택이라는 점이다.

물어보면 이렇게 답하면 된다 — “REST 도 OpenAPI 로 생성하면 됩니다. 다만 그건 팀이 그 규율을 지켜야 유지되고, gRPC 는 안 지키면 빌드가 안 되는 구조라는 게 달랐습니다.”

답변 뼈대

1. 스키마가 곧 계약이다
   chengine.proto 한 벌을 common-contract 모듈에 두고
   channel-engine(서버)과 websocket-gateway(클라이언트)가 같은 걸 쓴다
   -> 필드가 어긋나면 런타임이 아니라 빌드에서 잡힌다

2. 코드 생성
   Request · Response 클래스와 스텁이 자동 생성된다
   -> 양쪽 DTO 를 손으로 동기화할 일이 없다

3. HTTP/2 + protobuf
   바이너리라 작고, 연결을 재사용한다
   -> 내부 통신은 사람이 볼 일이 없으니 JSON 의 가독성이 필요 없다

4. 내부 전용이라는 전제
   외부(브라우저)와는 WebSocket · REST 로 하고
   서비스 사이에서만 gRPC 를 쓴다

속도가 아니라 “깨질 수 있는 지점을 줄였다” 로 말하는 게 실무적으로 들린다.

항목 구체적으로 뭘 하는 건가
사업비 집행 기준
· 증빙 관리		 과제비는 비목(인건비 · 연구재료비 · 연구활동비 등) 별로 쓸 수 있는 범위가 정해져 있다. 돈을 쓸 때마다 세금계산서 · 거래명세서 · 이체증 같은 증빙을 남겨야 하고, 정산 때 전부 제출한다. 증빙이 없거나 기준을 벗어나면 그 돈은 인정 안 된다.
비목별 예산 관리
· 변경 처리		 협약할 때 비목별 금액이 확정된다. 예를 들어 인건비 5천, 재료비 3천. 쓰다 보면 조정이 필요한데 일정 비율을 넘기면 협약변경을 신청해야 한다. 마음대로 옮기면 안 된다.
인건비 계상률
계산기		 연구원 한 명이 여러 과제에 참여하면 참여율을 나눠야 하고 총합이 100%를 넘을 수 없다. 계상률 × 연봉 × 참여개월 이 그 과제에서 받을 수 있는 인건비다. 잘못 계산하면 초과분이 통째로 불인정된다.
불용 · 반려
· 환수 리스크 점검		 불용 = 안 쓰고 남은 돈. 반납해야 하고 많으면 다음 과제 평가에 불리.
반려 = 집행 등록을 올렸는데 기관이 퇴짜 놓는 것.
환수 = 이미 쓴 돈을 부적정으로 판정해 토해내게 하는 것. 제일 무섭다.
연구비 정산
· 현장점검 대응		 과제가 끝나면 정산보고서를 낸다. 전문기관이 서류를 검토하고, 때로는 직접 찾아와 장부와 증빙을 본다.
협약 변경
· 보고서 작성		 연구책임자 교체, 기간 연장, 예산 조정은 전부 협약변경 절차를 거친다. 그리고 연차보고서 · 최종보고서를 쓴다.
선정기업
집행서식 관리		 기관이 정한 엑셀 양식에 집행 내역을 채워 제출한다. 양식이 기관마다 다르고 해마다 바뀐다.
과제 진행 상황

스크립트를 넘기기 전에 VPC/SG 의존관계를 조회해 검증했고, 그래서 채택하지 않았다. 검증 없이 실행했으면 DB 접근 불가 사고가 났다.

AiRecommend 라는 이름에 끌려가지 말 것

내 코드에 AiRecommendController, AiRecommendService 처럼 이름이 박혀 있다. 공고에도 “추천 · 검색 고도화” 가 있으니 “추천 기능이 있네요, 어떤 방식인가요” 정도는 물어볼 수 있다.

이름값에 끌려가 “추천 알고리즘을 구현했다” 로 말하면 꼬인다. 실제로는 최근 메시지를 모아 Gemini 에 넘기고 받아오는 LLM 호출이다.

먼저 선을 긋고, 할 수 있는 얘기(쿼터 · 장애 처리)로 넘긴다.

규모를 과장하지 말 것

사용자 2만명, 연 1,000억 관리 회사다. castleChat 은 실사용자가 없는 개인 프로젝트다.

“트래픽은 안 겪어봤다” 를 먼저 말하고 “대신 구조를 왜 그렇게 짰는지는 설명할 수 있다” 로 간다.

“우리 회사에 왜 지원하셨나요” — 답변

신입이 이 질문에서 제일 많이 하는 실수는 공고를 분석한 티를 내는 것이다. 주어가 “공고” 가 아니라 “회사가 하는 일” 이어야 한다.

이렇게 말하면 건방져 보인다
  • “공고에 OO 가 자격요건에 있는 게 눈에 띄어서…” → 공고를 분석했다는 뜻이 된다
  • “그래서 OO 한 사람이 필요하겠다고 이해했습니다” → 회사의 필요를 내가 판정하는 말이다. 최악
  • “인원이 적으시니까…” → 뒷조사한 티. 사원수 같은 숫자는 절대 입에 올리지 말 것
본 답변 (1분)

회사를 찾아보면서 가장 인상 깊었던 건, 스타트업이 연구에 써야 할 시간을 행정에 뺏기고 있다는 문제를 정면으로 다루고 계신다는 점이었습니다.

사업비 규정이 복잡하고 자주 바뀌다 보니 열심히 연구하고도 서류 하나 때문에 비용을 인정받지 못하는 일이 생긴다는 걸 블로그 글을 보고 알았습니다. 그런 걸 소프트웨어가 대신 챙겨준다면 정말 도움이 되겠다고 생각했습니다.

제가 해본 것 중에 장비 대여를 관리하는 시스템이 있는데, 담당자가 엑셀로 손수 정리하던 걸 일괄등록으로 바꾼 적이 있습니다. 규모는 훨씬 작지만, 사람이 반복하면 꼭 실수가 나는 일을 시스템이 받아주는 게 어떤 의미인지는 조금 느껴봤습니다.

그리고 제가 개발하면서 가장 신경 쓰는 건 “됐다고 믿지 않는 것”입니다. 한번은 계정 200건을 넣었는데 13건이 조용히 빠진 적이 있습니다. 에러도 없었고 성공으로 나왔는데, 끝나고 개수를 세어보고서야 알았습니다. 그 뒤로는 작업이 끝나면 결과를 꼭 확인합니다.

틀리면 고객에게 바로 손해가 가는 일을 하시는 곳이라고 들어서, 이런 습관이 조금이라도 보탬이 될 수 있지 않을까 해서 지원했습니다.

짧은 버전 (30초)

스타트업이 연구에 써야 할 시간을 행정에 뺏기는 문제를 다루고 계신 게 인상 깊었습니다. 규정이 복잡해서 열심히 하고도 서류 하나로 비용을 인정받지 못하는 일이 생긴다는 걸 알게 됐는데, 그걸 소프트웨어가 대신 챙겨준다면 도움이 크겠다고 생각했습니다.

저는 장비 대여 관리 시스템에서 엑셀 수작업을 일괄등록으로 바꿔본 적이 있고, 개발하면서 결과를 꼭 확인하는 습관을 들였습니다. 한번은 200건 중 13건이 조용히 빠진 걸 개수를 세어보고 발견한 적이 있습니다. 틀리면 고객에게 바로 손해가 가는 일이라고 들어서, 그런 습관이 보탬이 될 것 같았습니다.

이 답이 작동하는 이유

부분 무엇을 전하나
연구 시간을 행정에 뺏긴다 회사가 무슨 문제를 푸는지 이해했다. 기능이 아니라 문제를 말하는 게 핵심
블로그 글을 보고 알았습니다 조사했다는 증거를 겸손하게 전달. 아는 척이 아니라 “알게 됐다”
엑셀 수작업 → 일괄등록 도메인이 겹치는 실물 경험. “규모는 훨씬 작지만” 으로 분수를 지킨다
200건 중 13건 실수를 먼저 인정하고 거기서 습관을 끌어냈다. 회사 제품이 오류 탐지라 정확히 닿는다
보탬이 될 수 있지 않을까 기여 관점으로 닫되 단정하지 않는다

말할 때 주의

하지 말 것
  • 공고 문구를 분석하는 말
  • 회사에 뭐가 필요하다고 단정하는 말
  • 사원수 · 매출 같은 숫자
  • 도메인을 아는 척. “~라는 글을 봤습니다” 가 안전하다
  • 외운 티. 숫자만 정확히 기억하고 문장은 그때그때
꼭 할 것
  • 13건, 200건 두 숫자는 정확히. 구체적인 숫자가 신뢰를 만든다
  • “에러도 없었고 성공으로 나왔다” 를 빼먹지 말 것. 조용한 실패라는 게 핵심이다
  • “규모는 훨씬 작지만”, “조금 느껴봤습니다” 같은 완충 표현을 빼지 말 것
클로드 코드는 여기서 꺼내지 말 것

자격요건이긴 하지만 “왜 지원했나” 에서 꺼내면 또 공고 분석이 된다. 따로 물어볼 때 답하는 게 맞다. 그때는 통제 규칙과 검증 사례로 간다.

나올 가능성이 높은 질문

클로드 코드를 어떻게 쓰시나요? 그냥 시키면 되는 거 아닌가요?
  -> 통제 규칙 + 검증 사례 1 2 3

AI 가 짠 코드를 어떻게 믿나요?
  -> 안 믿는다. 테스트 / 측정 / 교차검증. 빌드와 커밋은 직접 한다

추천 기능을 만드셨던데 어떤 알고리즘인가요?
  -> 알고리즘이 아니라 LLM 연동이라고 먼저 선 긋기. 대신 쿼터 · 장애 처리 이야기

B2B/B2G 경험이 있나요?
  -> 외장 장비관리, HPDFS 진단.
     사용자가 불특정 다수가 아니라 정해진 조직인 구조

문서화는 어떻게 하시나요?
  -> prpr / ctxt 규칙. 다음 세션이 다시 추론하지 않게 하려고 만들었다

서버를 1대만 쓴 이유는?
  -> 비용. 분리 시 달라지는 점을 설명

협업 경험은?
  -> (약점) 솔직하게. 대신 문서로 남기는 습관을 강조
