#1 K8S 구조

PC 로 치면 각각 무엇인가

단계 PC 로 치면 실체 개수 관계
1  Image 디스크에 설치된 프로그램 (.exe) 읽기 전용 파일 묶음. 아무것도 돌지 않는다 —
2  Container 실행 중인 프로세스 격리된 프로세스 1개 (또는 몇 개) Image 1개 → Container 여러 개
3  Pod 대응물이 없다. k8s 가 만든 단위 Container 1개 이상 + IP 1개 Pod 1개 → Container 1개 이상
4  Node PC 1대 EC2 1대 (t3.medium) Node 1개 → Pod 여러 개
5  Cluster PC 여러 대를 한 대처럼 쓰는 것 Node 전체 + Control Plane Cluster 1개 → Node 여러 개
Image 와 Container 비유는 끝까지 통한다

같은 .exe 를 두 번 실행하면 프로세스가 2개가 된다. 이미지도 똑같다. 이미지 하나로 Container 를 몇 개든 띄울 수 있다. replicas: 3 이 바로 그것이다 — 이미지는 하나, 실행은 3개.

프로세스를 죽이면 그 안의 메모리가 사라진다. Container 도 똑같다. 지우면 안에서 바뀐 파일이 전부 날아간다. 이미지는 읽기 전용이고 변경분은 휘발성 계층에만 쌓이기 때문이다.

그래서 남아야 하는 것은 밖으로 빼야 한다. 볼륨(PVC) · DB · S3 가 전부 이 한 문장에서 나온다. #4 와 #6 이 이 이야기다.

짚을 점 — Container 는 VM 이 아니다

비유가 “프로세스” 인 것이 정확히 맞다. Container 는 가상 머신이 아니라 Linux 의 namespace 와 cgroup 으로 격리된 그냥 프로세스다.

namespace   "뭘 볼 수 있나" 를 가린다
            PID · 네트워크 · 마운트 · 호스트명을 따로 보게 한다

cgroup      "얼마나 쓸 수 있나" 를 제한한다
            CPU · 메모리 한도. ★ k8s 의 limits 가 결국 이것이다

증거는 간단하다. 노드에서 ps aux 를 치면 컨테이너 안의 프로세스가 그대로 보인다. VM 이라면 호스트에서 안 보인다. 커널도 노드와 공유한다.

그래서 컨테이너는 VM 보다 가볍고 빠르다. OS 를 하나 더 부팅하는 게 아니라 프로세스를 하나 띄우는 것이기 때문이다.

Pod 가 왜 따로 있나 — Container 로 충분할 것 같은데

이유는 네트워크다. 같은 Pod 안의 Container 들은 IP 를 공유하고 서로를 localhost 로 부른다.

로그 수집기나 프록시처럼 앱에 딱 붙어야 하는 보조 프로세스를 같이 묶을 수 있다 (사이드카). 또 스케줄 단위가 Pod 라서 같은 Pod 는 반드시 같은 Node 에 올라간다. 쪼개지지 않는다.

내 경우는 전부 1 Pod = 1 Container 다. 사이드카가 필요 없었기 때문이다. 그림의 Node 2 는 “이렇게도 된다” 를 보여주는 예시다.

1 — Cluster 는 두 부분으로 나뉜다

Cluster 를 “서버 묶음” 이라고만 알면 절반만 아는 것이다. 두뇌가 따로 있고, 그게 Cluster 의 본체에 가깝다.

Control Plane Worker Node
하는 일 명령을 받고 어디에 띄울지 결정한다 실제로 컨테이너를 돌린다
구성 API Server · etcd · Scheduler · Controller Manager kubelet · kube-proxy · containerd
EKS 에서 AWS 가 관리한다. 콘솔에 EC2 로 안 보인다 내 EC2 다. ssh 로 들어갈 수 있다
내가 정하는 것 이름과 리전뿐 인스턴스 타입 · 대수 · 디스크 · 네트워크
비용 $73.0 / 월 — 끌 수 없다 $75.9 / 월 — 0대로 내릴 수 있다
비용 두 줄이 Cluster 의 구조를 그대로 보여준다 
EKS 컨트롤플레인    $73.0   <- 두뇌. AWS 가 관리한다
t3.medium 2대       $75.9   <- 몸. 내 EC2 2대

과금이 두 줄로 나뉘어 있는 이유가 이것이다. 두뇌는 AWS 것이고 몸은 내 것이라서 따로 계산된다.

그래서 down.ps1 로 노드를 0대로 내려도 $73 은 계속 나갔다. 몸을 치워도 두뇌는 돌고 있기 때문이다. “Cluster 가 존재한다” 는 두뇌가 돌고 있다는 뜻이고, Pod 가 0개여도 성립한다.

내 eks-cluster.yaml 이 딱 그 두 개를 적고 있다

metadata:
  name: castlechat            <- 두뇌. 내가 적을 게 이름과 리전뿐이다
  region: ap-northeast-2         etcd 구성도 인증서 발급도 AWS 가 한다

managedNodeGroups:            <- 몸. 여기는 내가 상세히 정한다
  - name: castlechat-workers
    instanceType: t3.medium        어떤 EC2 를
    desiredCapacity: 2             몇 대
    minSize: 1  maxSize: 4
    volumeSize: 40                 디스크 몇 GB
    privateNetworking: true        공인 IP 를 주지 않는다

두뇌 쪽이 세 줄, 몸 쪽이 여덟 줄인 게 “관리형(managed)” 이라는 말의 실제 모습이다. 두뇌를 직접 만들려면 etcd 를 구성하고 인증서를 발급하고 API Server 를 띄워야 하는데, EKS 는 그걸 월 $73 에 대신 해준다.

addons — 빈 Cluster 는 아무것도 못 한다 
vpc-cni                  Pod 에게 IP 를 준다
coredns                  "domain-service" 를 IP 로 바꿔준다
kube-proxy               Service 트래픽을 Pod 로 꽂아준다
eks-pod-identity-agent   Pod 에 IAM Role 을 붙여준다
aws-ebs-csi-driver       PVC 를 EBS 볼륨으로 만들어준다

Cluster 는 “서버 묶음” 이 아니라 “서버 묶음 + 그걸 굴리는 부품들” 이다. addon 이 그 부품이다.

증거는 내 매니페스트 주석에 있다. “aws-ebs-csi-driver — 없으면 PVC 가 Pending 에서 멈추고 파드가 기동되지 않는다”. 부품 하나가 빠지면 그 기능이 조용히 안 될 뿐 에러가 안 난다.

2 — 순서를 바로잡자

흔한 오해 
이미지들을 모아서
  -> Cluster 가 만들어진다

Cluster 는 이미지로 만드는 게 아니다.

실제 
Cluster 가 먼저 있다 (텅 빈 상태)
  -> 그 위에 이미지를 올린다

Cluster 는 빈 서버 묶음이고 이미지는 나중에 올리는 짐이다.

  1. 나 eksctl create cluster — 빈 Cluster 가 생긴다. 15~20분. 이 시점에 내 앱은 하나도 없다. 그래도 $73 은 과금이 시작된다.
  2. 나 docker build + docker push — 레지스트리에 이미지를 쌓는다. Cluster 와 무관한 작업이다.
  3. 나 kubectl apply -k deploy/k8s — Cluster 에게 “이 매니페스트대로 띄워” 라고 시킨다.
  4. Control Plane 어느 Node 에 올릴지 정한다 (Scheduler).
  5. kubelet 레지스트리에서 이미지를 pull 하고 Container 로 실행한다. Pod 가 Running 이 된다.
1번과 2번은 순서가 바뀌어도 된다

서로 모르는 작업이기 때문이다. Cluster 를 다 만들어놓고 며칠 뒤에 이미지를 올려도 되고, 그 반대도 된다.

이미지 주소는 kustomization.yaml 에 문자열로만 적혀 있다. Docker Hub 로 바꿔도 Cluster 는 똑같이 동작한다. 레지스트리는 Cluster 의 일부가 아니다.

그래서 Cluster 를 한 줄로 말하면

한 줄 정리

“여기에 띄워” 라고 말할 수 있는 서버 묶음. 내가 서버를 지목하지 않아도 알아서 배치해주는 것이 Cluster 가 존재하는 이유다.

docker compose   서버 1대 안에서 컨테이너 여러 개를 띄운다
                 -> 그 서버가 죽으면 끝이다

k8s cluster      서버 여러 대를 묶어놓고 "띄워" 라고만 한다
                 -> 서버 1대가 죽으면 남은 서버로 알아서 옮긴다

내가 Lightsail 1대로 내린 것은 이 “알아서 옮기는 기능” 을 포기한 것이다. Node 가 1대면 옮길 곳이 없다. 그 대가로 월 $119 를 아꼈고, 실사용자가 없는 프로젝트에서는 그게 맞는 거래였다.

3 — 매니페스트란 무엇인가

“원하는 상태” 를 적어둔 YAML 파일이다. deploy/k8s/ 안의 모든 .yaml 이 매니페스트다.

명령형 — 동작을 지시한다 
docker run -d --name redis \
  -p 6379:6379 redis:7-alpine

한 번 실행되고 끝이다. 컨테이너가 죽으면 아무 일도 일어나지 않는다. 내가 다시 치지 않으면 그대로 멈춰 있다.

선언형 — 상태를 선언한다 
kubectl apply -f 10-redis.yaml
# "redis 가 1개 떠 있어야 한다"

k8s 가 그 상태를 계속 지킨다. 파드가 죽으면 다시 만들고, 노드가 날아가면 다른 노드에 올린다. 내가 다시 명령하지 않아도.

모든 매니페스트는 필드 4개가 뼈대다

apiVersion: apps/v1          이 문법의 버전. kind 마다 다르다
kind: Deployment             무슨 종류의 것인가
metadata:
  name: domain-service       이름. 같은 이름에 apply 하면 "수정" 이 된다
spec:                        ★ 원하는 상태. 여기가 본문이다
  replicas: 1
  template: ...
apply 는 “만들어라” 가 아니다

kubectl apply 는 “이 상태로 맞춰라” 다. 그래서 같은 파일을 백 번 apply 해도 결과가 같다 (멱등).

이것이 인프라를 Git 에 넣을 수 있는 이유다. YAML 이 곧 인프라의 정의이고, Git 이력이 곧 변경 이력이 된다.

apply 를 하면 안에서 이렇게 돈다

핵심 — 이 루프가 Kubernetes 의 전부다

“원하는 상태 · 현재 상태 · 차이를 메우는 루프”. 이 세 단어로 거의 모든 동작이 설명된다.

파드가 죽어서 다시 뜨는 것도, 배포할 때 새 파드가 뜨고 옛 파드가 내려가는 것도, 노드가 빠질 때 다른 노드로 옮겨가는 것도 전부 같은 루프다. 따로 외울 기능이 아니다.

Service 는 “불러주는 사람이 있을 때” 만 필요하다. 받을 게 없으면 안 만드는 게 맞다.

4 — Pod · Deployment · ReplicaSet

세 개가 계층이다. 내가 쓰는 건 Deployment 하나뿐이고 나머지는 자동으로 생긴다.

Pod 가 컨테이너와 다른 점

  • Pod 는 컨테이너 1개 이상을 담는 묶음이다. 같은 Pod 안의 컨테이너는 IP 와 네트워크를 공유한다. 서로를 localhost 로 부를 수 있다.
  • 스케줄 단위가 컨테이너가 아니라 Pod 다. 한 Pod 는 반드시 한 노드 안에 있다. 쪼개지지 않는다.
  • Pod 는 일회용이다. IP 도 매번 바뀐다. 그래서 Pod 를 직접 가리키지 않고 Service 를 쓴다.
내 경우는 전부 1 Pod = 1 컨테이너

사이드카(로그 수집기, 프록시 등)를 붙이지 않았다. 필요가 없었기 때문이다.

“사이드카를 안 썼다” 가 흠이 아니다. 왜 안 썼는지 말할 수 있으면 된다.

strategy — 배포할 때 옛 파드를 언제 내리나

방식 동작 중단 쓰는 경우
RollingUpdate
(기본값)		 새 파드를 먼저 띄우고 준비되면 옛 파드를 내린다 없음 보통
Recreate 옛 파드를 먼저 내리고 그 다음 새 파드를 띄운다 순단 발생 동시에 못 잡는 자원이 있을 때
domain-service 를 왜 Recreate 로 했나 — 매니페스트 주석 그대로 
strategy:
  type: Recreate
# EBS(ReadWriteOnce)는 파드 1개에만 붙으므로
# RollingUpdate면 배포가 멈춘다

RollingUpdate 는 새 파드를 먼저 띄우려 한다. 그런데 옛 파드가 EBS 볼륨을 쥐고 있어서 새 파드가 볼륨을 못 잡고 영원히 Pending 에 머문다.

그러면 옛 파드도 안 내려가므로 배포가 교착 상태로 멈춘다. 순단을 받아들이고 Recreate 로 바꾼 게 맞는 선택이다.

RollingUpdate 의 두 숫자

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 25%   동시에 몇 개까지 없어도 되나
    maxSurge: 25%         정원보다 몇 개까지 더 띄워도 되나

replicas 4, 둘 다 25% 라면
  파드는 항상 3 ~ 5 개 사이를 유지하면서 교체된다

maxUnavailable 을 0 으로 두면 절대 줄지 않는다. 대신 maxSurge 만큼 여유 자원이 있어야 하므로, 노드가 꽉 차 있으면 배포가 진행되지 않는다.

#3 Service — 파드를 어떻게 부르나

5 — Pod 를 직접 부르지 않는 이유

Pod 의 IP 는 매번 바뀐다. 죽고 살아날 때마다 새 IP 를 받는다. 그래서 Pod 를 가리키는 고정된 이름이 필요하고, 그게 Service 다.

spec:
  selector:
    app: domain-service      ← 이 label 이 붙은 파드를 전부 찾는다
  ports:
    - port: 8080             ← Service 가 받는 포트
      targetPort: 8080       ← 파드로 넘길 포트

다른 파드에서는 이렇게 부른다
  http://domain-service:8080
label 과 selector 가 연결의 전부다

Service 는 파드 이름을 모른다. label 로만 찾는다. 그래서 selector 와 파드 labels 가 한 글자라도 다르면 Service 에 파드가 하나도 안 붙는다.

이 경우 에러가 안 난다. 조용히 연결이 안 된다. kubectl get endpoints 가 비어 있으면 이것이다.

타입 3가지 — 내가 쓴 것들

Headless 가 왜 필요한가 — 꼭 설명할 수 있어야

일반 Service 는 요청을 아무 파드에나 보낸다. 그런데 Kafka 설정에는 이런 값이 들어간다.

KAFKA_CONTROLLER_QUORUM_VOTERS:
  0@kafka-0.kafka-headless:9093

“0번 브로커” 를 지목해야 하는데 일반 Service 로는 그게 불가능하다. clusterIP: None 을 주면 로드밸런싱을 포기하고 파드마다 고유한 DNS 이름을 준다.

Headless 가 만들어주는 이름

kafka-0.kafka-headless.castlechat.svc.cluster.local
   |         |             |
파드이름   Service 이름   namespace

같은 namespace 안에서는 줄여 쓴다
  kafka-0.kafka-headless

그래서 내 매니페스트에는 Kafka Service 가 두 개다. 지목용 headless 하나와 평범하게 접속할 kafka:9092 하나.

타입 정리 — NodePort 까지

타입 어디서 닿나 내 경우
ClusterIP 클러스터 안에서만 domain-service · channel-engine · websocket-gateway · ai-assistant · redis · kafka
Headless 클러스터 안. 파드 지목 kafka-headless
NodePort 노드 IP:30000~32767 안 썼다. 노드 IP 가 바뀌면 끝이라 실제로는 LoadBalancer 를 쓴다
LoadBalancer 인터넷 frontend
LoadBalancer 를 여러 개 만들면 안 되는 이유

Service 하나당 ELB 하나가 생기고 각각 과금된다. 6개 서비스를 전부 LoadBalancer 로 열면 월 $100 가 ELB 비용이다.

그래서 frontend 만 외부에 열고 나머지는 ClusterIP 로 뒀다. 여러 경로를 하나의 입구로 받아야 하면 Ingress(= L7 라우팅, ELB 하나를 여러 Service 가 공유)를 쓴다. 내 구성에는 Ingress 가 없다. frontend 의 NGINX 가 그 역할을 했다.

6 — Deployment vs StatefulSet

항목 Deployment StatefulSet
파드 이름 frontend-7d9f-x2k 랜덤 kafka-0, kafka-1 고정
생성 · 삭제 순서 동시에 순차적으로 (0 → 1 → 2, 삭제는 역순)
볼륨 PVC 를 따로 만들어 공유 volumeClaimTemplates — 파드마다 자기 볼륨
DNS 없음 파드별 고정 이름 (headless Service 필요)
내가 쓴 곳 JVM 5개 + frontend Redis · Kafka

volumeClaimTemplates 가 핵심이다

volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: [ReadWriteOnce]
      resources:
        requests:
          storage: 10Gi

파드가 3개면 PVC 가 3개 생긴다. data-kafka-0, data-kafka-1 처럼 파드 번호가 붙는다.

그리고 파드가 죽었다 살아나도 같은 번호의 볼륨을 다시 잡는다. kafka-0 은 항상 data-kafka-0 을 쓴다. 데이터가 섞이지 않는다.

StatefulSet 을 지우면 PVC 는 안 지워진다

일부러 그렇게 되어 있다. 데이터를 보호하기 위해서다. 그래서 down.ps1 로 노드를 0으로 내려도 EBS 볼륨은 그대로 남아 과금된다.

월 $244 중 EBS gp3 115GB = $10.5 가 이것이다. “끌 수 있는 것” 과 “존재하는 한 과금되는 것” 의 경계가 여기다.

Redis 를 StatefulSet 으로 한 이유

--appendonly yes 로 AOF 파일을 디스크에 쓴다. 파드가 재시작될 때 그 파일을 다시 읽어야 한다.

세션과 읽음 위치가 Redis 에 있으므로 재시작마다 날아가면 전원이 로그아웃된다. 그래서 볼륨이 필요하고, 볼륨이 필요하면 StatefulSet 이다.

7 — PVC · PV · StorageClass

세 개가 역할이 다르다. 내가 쓰는 건 PVC 뿐이다.

PVC            "20Gi 짜리 디스크 하나 주세요"        개발자가 쓰는 것
  |
StorageClass   "gp3 로, 암호화해서, EBS CSI 로 만들어"  관리자가 정해두는 것
  |
PV             실제로 만들어진 EBS 볼륨               자동 생성 (동적 프로비저닝)

accessModes — 여기가 모든 제약의 출발점이다

모드 뜻 EBS EFS
RWO
ReadWriteOnce		 노드 하나에서만 읽기 / 쓰기 된다 된다
ROX
ReadOnlyMany		 여러 노드에서 읽기만 안 된다 된다
RWX
ReadWriteMany		 여러 노드에서 읽기 / 쓰기 안 된다 된다
한 줄로 이어지는 인과 — 이걸 말할 수 있으면 끝이다 
EBS 는 RWO 다           (노드 하나에만 붙는다)
   -> 파드 1개만 볼륨을 쓸 수 있다
      -> replicas: 1 로 고정해야 한다
         -> 배포 시 새 파드가 볼륨을 못 잡는다
            -> strategy: Recreate 로 바꿔야 한다
               -> 배포마다 순단이 생긴다

   근본 원인은 "첨부파일을 파드 로컬에 저장했다" 는 것.
   S3 로 옮기면 위 네 줄이 전부 사라진다.

이것이 “상태를 밖으로 빼야 스케일된다” 는 말의 구체적인 모습이다. 설정을 바꿔서 해결되는 게 아니라 설계를 바꿔야 풀린다.

실제로 걸렸던 것 세 개

1

default StorageClass 가 없었다

EKS 기본 gp2 에는 default 표시가 없다. storageClassName 을 안 적은 PVC 가 영원히 Pending 에 머문다.

annotations:
  storageclass.kubernetes.io/
    is-default-class: "true"
describe pvc 의 Events 로 발견

  WaitForFirstConsumer
파드가 스케줄된 AZ 에 만들게 바꿈
3

새 EBS 볼륨은 root:root 755 다. 이미지가 uid 10001 로 돌아서 업로드가 Permission denied 로 실패했다.

securityContext:
  fsGroup: 10001
kubelet 이 마운트 시 그룹을 바꿔준다

셋 다 로그에 직접 안 나오는 종류다. 1 과 2 는 파드가 Pending 으로 멈추기만 하고, 3 은 앱이 뜬 다음에야 터진다.
“kubectl describe 의 Events 를 읽는다” 가 실무의 절반이다.

Kafka 의 lost+found 문제 
KAFKA_LOG_DIRS: /var/lib/kafka/data/logs
# 마운트 루트를 그대로 쓰면
# ext4 가 만드는 lost+found 때문에 기동 실패

EBS 를 ext4 로 포맷하면 루트에 lost+found 디렉터리가 자동 생성된다. Kafka 는 로그 디렉터리 안의 모든 하위 디렉터리를 토픽 파티션으로 해석하려 들기 때문에 거기서 죽는다.

그래서 마운트 루트가 아니라 한 단계 아래를 쓴다. 볼륨을 쓰는 모든 미들웨어에서 같은 문제가 생긴다.

#5 살아있는지 보기 · 리소스 배분

8 — Probe 3종

k8s 는 컨테이너가 떠 있다는 것만 안다. 앱이 실제로 요청을 받을 수 있는지는 모른다. 그걸 알려주는 게 Probe 다.

Probe 실패하면 목적 내 설정
startupProbe 계속 기다린다. 나머지 둘을 보류시킨다 느린 기동 보호 failureThreshold 30 × periodSeconds 5 = 150초
readinessProbe Service 에서 제외. 재시작은 안 한다 트래픽 차단 /actuator/health/readiness 10초마다
livenessProbe 컨테이너 재시작 좀비 복구 /actuator/health/liveness 20초마다
startupProbe 가 없으면 생기는 일

JVM 은 기동에 수십 초가 걸린다. livenessProbe 만 두면 아직 뜨지도 않은 앱을 죽었다고 판단해 재시작한다.

기동 시작 -> liveness 실패 -> 재시작
   -> 기동 시작 -> liveness 실패 -> 재시작
      -> ... CrashLoopBackOff

영원히 못 뜬다. initialDelaySeconds 를 크게 주는 방법도 있지만, 그러면 기동이 빠를 때도 그만큼 기다린다. startupProbe 가 더 낫다.

readiness 와 liveness 를 왜 나누나

readiness 는 “지금 요청 받을 수 있나”, liveness 는 “살아 있나” 다.

DB 커넥션이 잠깐 끊겼을 때 재시작하면 더 나빠진다. 캐시가 날아가고, 커넥션 풀을 다시 만들고, 그 사이 요청은 전부 실패한다.

readiness 만 실패시켜 트래픽에서 빼놓고 회복되면 다시 넣는 게 맞다. Spring Boot 가 두 엔드포인트를 따로 주는 이유가 이것이다.

Probe 방식 3가지

httpGet      GET 요청. 200~399 면 성공          JVM 서비스 · frontend
tcpSocket    포트가 열려 있으면 성공            Redis · Kafka
exec         명령을 실행해 종료코드 0 이면 성공   (안 썼다)

Redis 와 Kafka 는 HTTP 를 말하지 않으므로 tcpSocket 을 썼다. 다만 tcpSocket 은 “포트가 열렸다” 까지만 본다. 앱이 실제로 정상인지는 모른다.

9 — requests 와 limits

resources:
  requests: { cpu: 150m, memory: 384Mi }   스케줄러가 보는 값
  limits:   { cpu: "1",  memory: 768Mi }   넘으면 제재받는 값

150m = 0.15 코어   (m = milli-core)
"1"  = 1 코어
CPU 와 memory 는 넘었을 때가 다르다

CPU 는 압축 가능한 자원이라 나눠 쓰면 된다. limits 를 넘으면 throttle — 느려지기만 한다.

memory 는 압축이 안 된다. 이미 쓴 메모리를 줄일 방법이 없으니 커널이 프로세스를 죽인다 (OOMKilled).

그래서 memory limits 를 짜게 주는 게 CPU 보다 위험하다.

JVM 과 memory limit — 반드시 알아야 
JAVA_TOOL_OPTIONS:
  -XX:MaxRAMPercentage=70
  -XX:+UseG1GC

JVM 은 원래 호스트 전체 메모리를 보고 힙을 정한다. 컨테이너 limit 이 768Mi 인데 노드의 4GB 를 기준으로 힙을 잡으면 바로 OOMKilled 다.

MaxRAMPercentage=70 은 컨테이너 limit 의 70% 를 힙으로 쓰라는 뜻이다. 나머지 30% 는 Metaspace · 스레드 스택 · 네이티브 메모리에 남긴다.

QoS 등급 — 노드가 모자랄 때 누가 먼저 죽나

등급 조건 퇴출 순서
Guaranteed 모든 컨테이너의 requests 와 limits 가 같다 마지막
Burstable requests 는 있지만 limits 와 다르다 두 번째
BestEffort requests 도 limits 도 없다 가장 먼저

내 파드는 전부 Burstable 이다 (requests 150m / limits 1). 중요한 워크로드를 Guaranteed 로 올리는 방법도 있지만, 그만큼 노드 자원을 묶어두므로 밀도가 떨어진다.

리소스는 k8s 밖에서도 계산해야 한다 — 내 ConfigMap 사례 
SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE: "5"

# RDS db.t4g.micro 의 max_connections 는 약 40 이다.
# DB 를 쓰는 서비스 5개가 Hikari 기본값(10)을 쓰면
# 50개가 필요해 "Too many connections" 가 난다.
# 5 x 5 = 25, 롤링 재시작 중 겹쳐도 한도 안이다.

“파드 개수 × 파드당 커넥션 ≤ DB 한도” 를 직접 계산해야 한다. k8s 는 DB 커넥션을 모른다. CPU 와 메모리만 본다.

그리고 롤링 재시작 중에는 옛 파드와 새 파드가 동시에 존재하므로 순간적으로 두 배가 필요할 수 있다. 그것까지 넣어 계산한 것이다.

replicas 를 올릴 때 이 계산을 다시 해야 한다. 안 하면 스케일을 늘린 순간 DB 가 먼저 터진다.

#6 스케일 — 여기가 핵심이다

10 — 오토스케일 3종을 구분하자

HPA 파드 개수 Horizontal Pod Autoscaler
보통 "오토스케일" 은 이것
VPA 파드 크기 Vertical Pod Autoscaler
requests 를 자동 조정. 거의 안 쓴다
CA 노드 개수 Cluster Autoscaler / Karpenter
EC2 를 늘린다
HPA 만 걸면 안 되는 이유

HPA 로 파드를 늘려도 노드에 자리가 없으면 Pending 이다. 파드가 늘어난 게 아니라 늘어나려다 멈춰 있는 것이다.

그래서 실무에서는 HPA + Cluster Autoscaler 를 같이 쓴다. HPA 가 파드를 요청하고, 자리가 없으면 CA 가 EC2 를 띄운다. 노드가 늘면 비용도 늘어난다.

HPA 의 “CPU 70%” 는 무엇의 70% 인가

틀린 이해

limits 대비 비율.

노드 전체 CPU 대비 비율.

실제 — requests 대비 비율이다 
requests.cpu = 150m
실제 사용     = 105m
  -> 105 / 150 = 70%   목표 도달

limits.cpu = 1000m 은 계산에 안 들어간다
그래서 생기는 두 가지 결과

requests 를 안 적으면 HPA 가 CPU 기준으로 동작하지 않는다. 분모가 없으니 비율을 낼 수 없다. HPA 가 <unknown> 만 띄운다.

metrics-server 가 설치돼 있어야 한다. 없으면 역시 <unknown> 이다. kubectl top pod 가 되는지로 확인한다.

내 매니페스트는 모든 파드에 requests 가 있다. HPA 를 걸 준비 자체는 되어 있다.

HPA 매니페스트는 이렇게 생겼다

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: frontend
spec:
  scaleTargetRef:                  누구를 늘릴지
    apiVersion: apps/v1
    kind: Deployment
    name: frontend
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   ← requests 대비 70%

11 — 내 서비스에 HPA 가 없는 이유

이게 이 문서에서 가장 중요한 부분이다. 기능을 몰라서 안 건 게 아니라 걸 수 있는 게 하나뿐이었다.

1

websocket-gateway

replicas: 1

WsGateSessionRegistry 가 JVM 메모리(ConcurrentHashMap) 라 브로드캐스트가 자기 파드에만 닿는다.

2개로 늘리면 다른 파드에 접속한 상대에게 메시지가 안 간다. 장애가 아니라 조용히 메시지가 사라진다.

Redis pub/sub 팬아웃이 선행돼야 한다
2

domain-service

replicas: 1

첨부파일이 그 파드의 EBS 볼륨에만 있다. EBS 는 RWO 라 두 번째 파드는 볼륨을 못 잡는다.

설령 붙었다 해도 파일을 올린 파드와 다른 파드로 요청이 가면 404 다.

S3 로 이전이 선행돼야 한다
3

frontend

replicas: 2

정적 파일을 NGINX 가 주는 것뿐이라 상태가 없다. 어느 파드가 받아도 같은 응답이다.

여기만 늘릴 수 있다. 실제로 2개로 뒀고, HPA 를 걸 수 있는 유일한 대상이다.

무상태 = 스케일 가능

차이는 설정이 아니라 상태를 어디에 두었느냐다.
1 은 세션을 메모리에, 2 는 파일을 로컬 디스크에 두었다. 3 은 아무것도 들고 있지 않다.
스케일은 설정 문제가 아니라 설계 문제다.

한 줄 정리 — 설명을 요구받을 때

“제 서비스는 지금 못 늘립니다.” 로 시작하는 게 맞다.

wsgate 는 세션 레지스트리가 JVM 메모리에 있어서 파드를 늘리면 브로드캐스트가 자기 파드에만 닿고, domain-service 는 첨부파일이 그 파드 EBS 에만 있어서 다른 파드가 파일을 못 찾는다.

늘리려면 세션을 Redis pub/sub 으로, 파일을 S3 로 빼는 게 먼저다. 그래서 replicas 를 1로 고정하고 그 이유를 매니페스트 주석에 적어뒀다.

“준비가 안 된 상태에서 HPA 를 거는 건 장애를 자동화하는 것” 이라는 게 결론이다.

무상태로 만드는 방법 — 무엇을 어디로 빼나

파드가 들고 있던 것 어디로 빼나 그러면
WS 세션 레지스트리 Redis pub/sub — wsgate 끼리 메시지를 팬아웃 wsgate 를 N개로
첨부파일 S3 (오브젝트 스토리지) domain-service 를 N개로. PVC 와 Recreate 가 통째로 사라진다
HTTP 세션 Redis (Spring Session) 어느 파드로 가도 로그인 유지
스케줄러 · 단일 작업 분산 락 또는 리더 선출 중복 실행 방지
Snowflake workerId — 늘릴 때 또 걸리는 것 
# ConfigMap 주석 중
# CHAT_SNOWFLAKE_WORKER_ID : 인스턴스마다 달라야 하는 값이라
#                            공용 ConfigMap 에 두면 안 된다.
#                            channel-engine Deployment 로 옮김.

Snowflake ID 는 timestamp | workerId | sequence 구조라 파드마다 workerId 가 달라야 ID 가 겹치지 않는다.

그런데 Deployment 의 파드는 전부 같은 환경변수를 받는다. 늘리면 workerId 가 같아져서 ID 중복이 난다.

해결은 StatefulSet 으로 바꿔 파드 번호(kafka-0 식)를 workerId 로 쓰는 것이다. “무상태로 보이는 서비스도 사실 상태를 들고 있을 수 있다” 는 좋은 예다.

HPA 말고 쓸 수 있는 것들

PodDisruptionBudget   노드 교체 중에도 최소 N개는 살려둬라
                      replicas 1 이면 쓸 수가 없다 (반드시 끊긴다)

PodAntiAffinity       같은 앱의 파드를 다른 노드에 분산해라
                      노드 하나가 죽어도 전멸하지 않는다

topologySpreadConstraints  AZ 별로 고르게 퍼뜨려라

   -> 셋 다 replicas 2 이상이어야 의미가 있다.
      내 구성에는 없다. 쓸 전제가 안 됐기 때문이다.

12 — ConfigMap 과 Secret

ConfigMap — 설정값

kind: ConfigMap
metadata:
  name: castlechat-config
data:
  SPRING_DATA_REDIS_HOST: "redis"
  SPRING_KAFKA_BOOTSTRAP_SERVERS: "kafka:9092"

파드에서는 envFrom 으로 통째로 받거나 valueFrom 으로 하나만 받는다.

이미지를 환경별로 따로 만들지 않아도 된다는 게 요점이다. 같은 이미지에 ConfigMap 만 갈아끼운다.

Secret 은 암호화가 아니다

base64 는 인코딩이지 암호화가 아니다. base64 -d 한 번으로 평문이 나온다.

기본 설정에서는 etcd 에도 평문으로 저장된다. 제대로 하려면 KMS 봉투 암호화를 켜거나 External Secrets 같은 걸 붙인다.

내가 한 것은 Git 에 올리지 않고 02-secret.example.yaml 로 형태만 남긴 것까지다. 거기까지라고 선을 긋고 말하는 게 맞다.

ConfigMap 을 바꿔도 파드는 안 바뀐다

환경변수로 주입한 값은 파드 생성 시점에 박힌다. ConfigMap 을 apply 해도 이미 뜬 파드에는 반영되지 않는다.

kubectl rollout restart deploy/... 로 다시 띄워야 한다. 볼륨으로 마운트한 경우는 파일이 갱신되지만, 앱이 그 파일을 다시 읽어야 의미가 있다.

13 — ServiceAccount 와 Pod Identity

파드가 AWS 자원(S3 등)에 접근해야 할 때 액세스 키를 컨테이너에 넣지 않는 방법이다.

# 03-service-account.yaml  — 파드의 "신분"
apiVersion: v1
kind: ServiceAccount
metadata:
  name: domain-service

# Deployment 에서 그 신분을 쓴다
spec:
  serviceAccountName: domain-service

# AWS 쪽에서 그 신분에 IAM Role 을 연결한다
aws eks create-pod-identity-association \
  --cluster-name castlechat \
  --namespace castlechat \
  --service-account domain-service \
  --role-arn arn:aws:iam::...:role/castlechat-domain-service-s3
왜 이게 중요한가

액세스 키를 쓰면 키가 이미지나 Secret 에 남고, 회전되지 않고, 유출되면 끝이다.

Pod Identity 를 쓰면 파드가 임시 자격증명을 자동으로 받고 자동으로 갱신된다. 키가 어디에도 저장되지 않는다.

IRSA 와 Pod Identity 차이

IRSA — 클러스터마다 OIDC 제공자를 설정해야 하고 IAM 신뢰 정책에 OIDC URL 이 박힌다. 클러스터를 다시 만들면 롤을 고쳐야 한다.

Pod Identity — EKS 에이전트가 처리해서 설정이 단순하고 롤을 여러 클러스터에서 재사용할 수 있다. 더 최근 방식이다.

14 — Namespace 와 Kustomize

Namespace

이름을 나누는 칸막이다. 다른 namespace 의 같은 이름과 충돌하지 않는다.

같은 namespace       http://domain-service:8080
다른 namespace       http://domain-service.other:8080

격리가 아니다. 기본적으로 namespace 간 통신은 막히지 않는다. 막으려면 NetworkPolicy 가 필요하다.

Kustomize

namespace: castlechat
resources:
  - 00-namespace.yaml
  - 01-config.yaml
  ...
images:
  - name: castlechat/domain-service
    newName: 256688076284.dkr.ecr.
             ap-northeast-2.amazonaws.com/
             castlechat/domain-service
    newTag: latest

매니페스트를 고치지 않고 이미지 주소만 바꿔 끼운다. 로컬에서는 짧은 이름, EKS 에서는 ECR 주소로. kubectl apply -k 로 한 번에 적용한다.

15 — 실전 명령어

# 보기
kubectl get pods -n castlechat -o wide        어느 노드에 떴나까지
kubectl get pvc,pv -n castlechat
kubectl get endpoints -n castlechat           ★ Service 에 파드가 붙었나

# 들어가기 · 뚫기
kubectl exec -it <파드> -n castlechat -- sh
kubectl port-forward svc/domain-service 8080:8080 -n castlechat

# 배포
kubectl kustomize deploy/k8s                  렌더링만. 적용 안 함
kubectl apply -k deploy/k8s
kubectl rollout status deploy/domain-service -n castlechat
kubectl rollout restart deploy/domain-service -n castlechat
kubectl rollout undo deploy/domain-service -n castlechat

# 스케일 · 자원
kubectl scale deploy/frontend --replicas=3 -n castlechat
kubectl top pod -n castlechat                 metrics-server 필요
kubectl describe node <노드>                  Allocated resources 확인
실무의 대부분은 세 개다

describe 의 Events — Pending, 스케줄 실패, 볼륨 바인딩 실패, 이미지 pull 실패가 전부 여기 나온다.

logs --previous — 재시작된 컨테이너는 현재 로그가 비어 있다. 죽은 이유는 직전 로그에 있다.

get endpoints — 비어 있으면 label 과 selector 가 안 맞는 것이다. 에러가 안 나는 종류의 고장이다.

증상별로 어디를 보나

상태 뜻 볼 곳
Pending 스케줄될 노드가 없거나 볼륨을 못 잡았다 describe pod 의 Events. 리소스 부족 / PVC Pending / AZ 불일치
ImagePullBackOff 이미지를 못 받았다 태그 오타, ECR 권한, imagePullSecrets
CrashLoopBackOff 떴다가 바로 죽는 걸 반복 logs --previous. 설정값 누락 / startupProbe 없음 / OOM
OOMKilled memory limits 초과 describe pod 의 Last State. JVM 힙 설정 확인
Running 인데 응답 없음 readiness 실패로 Service 에서 빠졌다 get endpoints · readinessProbe 경로
Terminating 에서 안 끝남 finalizer 또는 볼륨 분리 대기 PV/PVC 상태. terminationGracePeriodSeconds

16 — 비용 — EKS 가 비싼 이유

직접 쪼개본 값이다. 목적은 합계가 아니라 “끌 수 있는 것” 과 “존재하는 한 과금되는 것” 을 나누는 것이었다.

EKS 컨트롤플레인    $73.0   끌 수 없다
t3.medium 2대       $75.9   노드그룹 0 으로 가능
NAT 게이트웨이      $43.1   삭제 가능하나 영향 큼
RDS db.t4g.micro    $21.3   정지 가능 (최대 7일)
Classic ELB         $16.4   Service 지우면 사라진다
EBS gp3 115GB       $10.5   PVC 가 남으면 계속 과금
EIP                  $3.7
---------------------------------
월 $244  /  일 $8

노드그룹 0 + ELB 삭제 + RDS 정지로 $244 → $125. 컨트롤플레인 $73 은 클러스터가 존재하는 동안 무조건 나간다.

검증해서 사고를 막은 것

절감폭이 가장 큰 방법은 eksctl delete cluster 후 재생성이다. 그런데 리소스를 조회해보니 그 방식은 DB 를 파괴한다.

EKS VPC 와 RDS VPC 가 동일
RDS 보안그룹 인바운드가
  EKS 클러스터 SG 를 참조
eks-cluster.yaml 에 vpc: 블록이 없음
  -> eksctl 이 매번 새 VPC 를 만든다

삭제 시   RDS ENI 때문에 VPC 삭제 실패
재생성 시 RDS 가 옛 VPC 에 고아로 남는다

실행 전에 의존관계를 조회해 확인했고 그래서 채택하지 않았다. 검증 없이 돌렸으면 DB 접근 불가 사고였다.

그래서 내린 결론

개인 프로젝트에 EKS 는 과하다. 컨트롤플레인 $73 과 NAT $43 은 트래픽이 0 이어도 나가는 고정비다.

그래서 Lightsail 1대에 컨테이너 22개로 내렸다. “쓸 줄 안다” 가 아니라 “얼마 드는지 알고 판단했다” 가 남은 것이다.

17 — 자주 묻는 것과 답할 방향

k8s 를 왜 쓰셨나요?
  -> 프로세스가 6개라 compose 로도 됐지만 배포 단위를 분리하고
     선언형으로 관리해보고 싶었다. 결과적으로 비용 때문에 다시 내렸다

Deployment 와 StatefulSet 차이는?
  -> 이름 고정 · 순차 기동 · volumeClaimTemplates
     "Kafka 는 kafka-0 을 지목해야 해서 StatefulSet + Headless 를 썼다"

Service 타입은?
  -> ClusterIP / NodePort / LoadBalancer / ExternalName + Headless
     "frontend 만 LoadBalancer. ELB 가 Service 당 하나씩 과금되니까"

readiness 와 liveness 차이는?
  -> 트래픽 제외 vs 재시작
     "DB 가 잠깐 끊겼을 때 재시작하면 더 나빠진다"

startupProbe 는 왜?
  -> JVM 기동이 느려서 아직 안 뜬 앱을 죽이는 걸 막으려고. 30 x 5s = 150초

requests 와 limits 차이는?
  -> 예약 vs 상한. CPU 는 throttle, memory 는 OOMKilled

★ 오토스케일은 어떻게 하셨나요?
  -> "걸 수 있는 게 frontend 밖에 없었다"
     wsgate 는 세션이 JVM 메모리, domain-service 는 파일이 로컬 EBS
     Redis pub/sub · S3 이전이 선행돼야 한다
     준비 안 된 상태에서 HPA 를 걸면 장애를 자동화하는 것

파드가 Pending 이면?
  -> describe pod 의 Events
     "default StorageClass 가 없어서 PVC 가 Pending 이었던 적이 있다"

롤백은?
  -> kubectl rollout undo. 옛 ReplicaSet 이 남아 있어서 가능하다

Secret 은 안전한가요?
  -> base64 는 인코딩이지 암호화가 아니다. etcd 평문 저장이 기본
     "나는 Git 에 안 올리고 예제 파일만 뒀다" 까지가 내가 한 것

PV 를 직접 만드셨나요?
  -> 아니다. StorageClass 로 동적 프로비저닝. PVC 만 쓴다
공부 순서
  1. 내 매니페스트 19개를 주석까지 정독한다. 제일 중요하다. 반나절이면 된다
  2. 위 17번 질문들을 소리 내어 답해본다
  3. 막히는 것만 공식 문서를 찾는다

교재부터 보지 않는다. 내가 쓴 것에 이미 실전 함정이 다섯 개 들어 있다 — RWO 와 Recreate · AZ 와 volumeBindingMode · default StorageClass · fsGroup 권한 · lost+found.

이걸 설명할 수 있으면 “운영해봤다” 가 성립한다. 남이 쓴 책의 예제보다 내가 겪은 에러가 강하다.
