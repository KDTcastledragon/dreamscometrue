#1 서버를 분리하면 — 커널은 2개, 핸드셰이크는 누가 하나

먼저 — 도커 컨테이너는 커널을 공유한다

캐슬챗은 Lightsail 한 대에 컨테이너로 다 올려놨는데, 이때 커널은 하나다.

B 에 공인 IP 가 없는 것이 분리하는 가장 큰 이유다. 공격자가 Spring Boot 를 직접 때릴 경로가 물리적으로 존재하지 않고, 반드시 A 를 거쳐야 한다.

핸드셰이크는 커널이 한다 — nginx 가 아니다

흔한 오해

"nginx 가 SYN 을 받아서 SYN+ACK 를 보낸다" — 틀렸다. nginx 는 SYN 을 보지도 못한다. 커널이 핸드셰이크를 혼자 다 끝낸 뒤에 nginx 에게 넘긴다.

전화 비유

  • 커널 = 교환원. 벨이 울리면 받아서 통화를 성립시킨다.
  • nginx = 담당 직원. 교환원이 연결해준 통화를 건네받아 실제 대화를 한다.
  • 직원은 벨소리와 "연결 중" 신호에 참여하지 않는다. 수화기를 받았을 때 통화는 이미 성립돼 있다.

누가 보내고 누가 받나

# 패킷 / 동작 보내는 주체 받는 주체
1 SYN 클라이언트 PC 의 커널
(브라우저가 connect() 로 부탁)		 서버 A 의 리눅스 커널
2 SYN+ACK 서버 A 의 리눅스 커널 클라이언트 PC 의 커널
3 ACK 클라이언트 PC 의 커널 서버 A 의 리눅스 커널
4 연결 성립 커널 A 가 accept 큐에 적립 nginx 가 accept() 로 꺼냄
← nginx 첫 등장
5 GET / HTTP/1.1 브라우저 nginx
6 200 OK + html nginx 브라우저

1~3 번에 nginx 가 없다. TCP 핸드셰이크는 TCP 프로토콜의 일이고 TCP 구현체가 커널 안에 있기 때문이다. 유저랜드 프로그램이 매번 직접 악수하게 만들면 모든 서버 프로그램이 TCP 를 새로 구현해야 한다.

SYN 이 실제로 가는 경로

패킷은 층으로 포개져 있고, 중간 라우터는 봉투 안을 뜯어보지 않는다.

+- Ethernet frame (L2) ---------------------------+
|  dst MAC : 공유기 MAC      <-- ARP 로 알아냄      |
|  +- IP packet (L3) --------------------------+  |
|  |  src IP : 192.168.0.5    (내 PC 사설)      |  |
|  |  dst IP : 43.202.208.133                  |  |  <-- 라우터가 보는 건 이것만
|  |  +- TCP segment (L4) -----------------+   |  |
|  |  |  src port : 51234  (OS 가 임의 배정) |   |  |
|  |  |  dst port : 80                     |   |  |  <-- 최종 서버 커널만 본다
|  |  |  flags    : SYN                    |   |  |
|  |  +------------------------------------+   |  |
|  +-------------------------------------------+  |
+-------------------------------------------------+
  1. 브라우저 socket() + connect() 호출. 여기서 브라우저 역할은 끝이고 나머지는 커널이 한다.
  2. 내 PC 커널 "목적지가 내 서브넷에 없네" 판단 → 기본 게이트웨이(공유기)로 보내기로 결정. ARP 로 공유기 MAC 을 알아내 전송.
  3. 공유기 NAT. 출발지 IP 를 사설 → 공인으로 바꿔치기하고, 돌아올 응답을 누구에게 줄지 포트로 기억해둔다.
  4. 라우터들 ISP → 백본 → AWS. 수십 홉을 목적지 IP 만 보고 전달한다.
  5. 방화벽 보안그룹이 80 번 허용을 확인한다. 막혀 있으면 여기서 조용히 버려지고 브라우저는 타임아웃이 난다.
  6. 서버 커널 "80 번 듣는 소켓 있음(nginx)" → SYN+ACK 발사. 여기가 답이다.

로그인 화면이 뜨기까지 Spring Boot 는 전원만 켜져 있을 뿐이다. B 서버를 꺼놔도 로그인 화면은 똑같이 뜬다. React 빌드 산출물은 그냥 정적 파일이라 WAS 가 필요 없다. 이게 CSR 구조의 특징이다.

GET 이후 렌더링까지

location / 에는 proxy_pass 가 없다. 즉 "B 에게 물어볼 필요 없음" 이다.

location / {
    try_files $uri $uri/ /index.html;
}

# $uri = "/" 이므로 왼쪽부터 순서대로 시도한다
#   1차 $uri   -> /usr/share/nginx/html/   디렉토리라서 실패
#   2차 $uri/  -> 디렉토리 맞음 -> index 지시자 -> index.html 발견. 성공
#   3차 /index.html  -> 갈 필요 없었음
  1. nginx 자기 디스크에서 index.html 을 읽어 200 OK + 548 바이트 반환.
  2. 브라우저 Content-Type: text/html 을 보고 HTML 파서 가동. 확장자가 아니라 이 헤더가 기준이다.
  3. 브라우저 DOM 트리 구축. <div id="root"> 가 비어 있어 아직 흰 화면이다.
  4. 브라우저 CSS / JS 추가 GET. keep-alive 덕분에 같은 TCP 연결을 재사용하고 핸드셰이크를 다시 하지 않는다.
  5. 브라우저 DOM + CSSOM → 렌더트리 → Layout → Paint. 흰 화면이 실제로 모니터에 출력된다.
  6. 브라우저 defer 스크립트 실행. React 가 비어 있던 root 를 채운다. 네트워크가 아닌 순수 DOM 조작이다.
  7. 브라우저 DOM 이 바뀌었으니 Layout → Paint 를 다시 돈다. 로그인 화면이 보인다.

스크립트 두 종류의 차이

  • <script defer> — 다운로드는 즉시, 실행은 파싱이 끝난 뒤. HTML 파싱을 멈추지 않는다. 없으면 그만큼 화면이 늦게 뜬다.
  • <link rel="stylesheet"> — 반대로 렌더링을 막는다(render-blocking). CSS 없이 그리면 스타일 없는 날것이 번쩍 보였다가 바뀌므로 브라우저가 일부러 기다린다.

B 가 필요해지면 핸드셰이크가 한 번 더

location ~ ^/(user|friend|chat|room|uploads)/ {
    proxy_pass http://10.0.1.20:8080;      # 여기엔 proxy_pass 가 있다
}
  • ① 브라우저 → 커널 A 핸드셰이크  (클라이언트 ↔ A)
  • ② nginx → 커널 B 핸드셰이크  (A ↔ B) — 완전히 별개의 연결
역할이 뒤집힌다

nginx 는 브라우저에 대해서는 서버(SYN 을 받는 쪽), Spring Boot 에 대해서는 클라이언트(SYN 을 보내는 쪽)가 된다.

②의 SYN+ACK 를 보내는 건 커널 B 다. 이때도 톰캣은 악수에 참여하지 않고 accept() 로 완성된 연결만 받는다. A 에서 일어난 일이 B 에서 똑같이 반복된다.

그리고 B 가 보는 접속 IP 는 브라우저가 아니라 nginx 가 된다. 그래서 X-Forwarded-For 가 필요하다.

#2 공인 IP · 사설 IP · 도메인 — 배포 구성 두 가지

"백엔드에 IP 가 없다" 는 말의 정확한 뜻

IP 가 없는 게 아니라 공인 IP 가 없다.

B 서버 상태 뜻
사설 IP 10.0.1.20 있다 내부망에서는 이걸로 통신한다
공인 IP 없다 인터넷에서 닿을 경로가 없다
비유

사설 IP 는 집 안에서만 쓰는 호수, 공인 IP 는 전 세계에서 찾아올 수 있는 주소다. B 는 아파트 안의 1203 호인데 그 아파트 주소가 비공개인 상태다. 같은 아파트 사람(A 서버)은 1203 호를 찾아갈 수 있지만 외부인은 아파트 자체를 못 찾는다.

도메인은 프로세스에 붙는 게 아니다

흔한 오해

"Spring Boot 의 도메인" 이라는 말은 엄밀히는 성립하지 않는다. 정확히는 "Spring Boot 앞단에 노출된 공인 IP 의 도메인" 이다.

도메인  --DNS A 레코드-->  공인 IP 하나

castlechat.com  ->  203.0.113.10  ->  A 서버 (nginx)
                                          |
                                          +-> 10.0.1.20 (Spring Boot)
                                              도메인 불필요. 공인 IP 불필요

도메인을 산다는 건 외부 노출 지점 하나에 이름을 붙이는 것이고, 그 지점이 nginx 다.

구성 1 — 단일 출처 (리버스 프록시). 캐슬챗 방식

castlechat.com  ->  nginx  (공인 203.0.113.10)
   (도메인 1개)        |
                      |  /          -> 자기 디스크의 정적 파일
                      |  /user/...  -> 10.0.1.20:8080  --> Spring Boot
                      |  /chat/...  -> 10.0.1.20:8080  --> (도메인 없음)
  • 도메인 1 개로 끝난다. 백엔드는 공인 IP 도, 도메인도 필요 없다.
  • 브라우저 입장에서 출처가 하나뿐이라 CORS 가 발생하지 않는다.

캐슬챗 compose 파일 주석에 그대로 적혀 있는 내용이다.

# 브라우저 입장에서 출처가 nginx 하나뿐이라 CORS도 발생하지 않는다.
# 밖으로 여는 포트는 nginx의 80 하나뿐이다. 다른 컨테이너 포트를 publish 하면
# 출처가 늘어나면서 CORS가 되살아난다.

구성 2 — 분리 출처. "서버쪽 도메인" 이 필요한 경우

www.site.com  ->  프론트엔드   (S3 + CloudFront / Vercel / Netlify)
                   빌드된 html, js, css 만 올라감

api.site.com  ->  백엔드       <-- 여기에 공인 IP + 도메인이 필요하다
                   Spring Boot

프론트를 정적 호스팅에 올리고 백엔드를 따로 두는 구성이다. 브라우저의 JS 가 api.site.com 으로 직접 요청을 쏘기 때문에 백엔드도 외부 접근이 가능해야 한다.

대신 대가가 있다

출처가 2개 (www.site.com != api.site.com)
   -> 브라우저가 CORS 검사 발동
   -> 백엔드에 CORS 설정 필수
        @CrossOrigin / WebMvcConfigurer#addCorsMappings
        Access-Control-Allow-Origin 헤더
        preflight(OPTIONS) 요청 처리
        쿠키 쓰려면 allowCredentials + SameSite 까지

두 구성 비교

구성 1 (리버스 프록시) 구성 2 (분리 출처)
도메인 1 개 1 개 + 서브도메인
백엔드 공인 IP 불필요 필요
CORS 없음 설정 필수
인증서(HTTPS) 1 장 2 장 (또는 와일드카드 1 장)
백엔드 공격 노출 없음 있음 (방화벽으로 막아야)
프론트 배포 서버에 파일 올림 CDN 에 올림. 전송이 빠름
프론트/백 독립 배포 어려움 쉬움

캐슬챗의 현재 상태

구성 1 이고, 도메인을 사지도 않았다. 43.202.208.133 이라는 공인 IP 를 직접 쓰고 있다. nginx 설정에 증거가 있다.

server_name _;    # "도메인 안 가림. 뭐든 다 받음"

도메인을 사면 이 자리에 server_name castlechat.com; 을 적게 된다. nginx 설정 한 줄 + DNS A 레코드 하나가 끝이고, Spring Boot 는 한 글자도 안 고친다.

추가로 알아둘 것

서브도메인은 공짜다

api.site.com 을 위해 도메인을 또 살 필요가 없다. site.com 하나 사면 api., www., admin. 등을 무한히 만들 수 있다. DNS 레코드만 추가하면 된다.

구성 2 에서도 Spring Boot 를 맨몸으로 노출하지 않는다

api.site.com -> ALB (공인 IP) -> Spring Boot #1 (사설 IP)
                              -> Spring Boot #2 (사설 IP)
                              -> Spring Boot #3 (사설 IP)

즉 api.site.com 이 가리키는 건 톰캣이 아니라 로드밸런서의 공인 IP 다.

결론

어느 구성이든 Spring Boot 자체는 사설 IP 만 갖는다. 공인 IP 를 받는 건 항상 그 앞단(nginx 또는 로드밸런서)이다. 그래야 서버를 여러 대로 늘릴 수 있고, 도메인이 특정 인스턴스에 묶이지 않는다.

면접에서 쓸 한 줄

"도메인은 외부 노출 지점에 붙는다. 캐슬챗은 nginx 를 단일 출처로 두는 리버스 프록시 구성이라 도메인 하나로 충분하고, 그 덕에 CORS 설정이 아예 필요 없다."

HTTP 요청 헤더 — 개발자 필수 정리

요청 라인

GET / HTTP/1.1
  • GET — 메서드. GET, POST, PUT, PATCH, DELETE
  • / — 경로
  • HTTP/1.1 — 프로토콜 버전

1순위 모르면 안 되는 것

Host: 43.202.208.133

HTTP/1.1 에서 유일한 필수 헤더. IP 하나에 여러 사이트를 올릴 수 있게 해주는 헤더다.

nginx 가 server_name 으로 어느 사이트인지 가르는 기준이 이것이다.

server_name _;    # 지금은 "뭐든 다 받음". 도메인 사면 여기에 적는다
Cookie: JSESSIONID=...

HTTP 는 상태가 없다(stateless). 서버는 매 요청을 처음 보는 사람으로 취급한다.

그걸 뚫고 "나 아까 그 사람이야" 를 증명하는 수단이다. 브라우저가 자동으로 붙인다. 첫 방문이면 없다.

Content-Type: application/json

GET 에는 바디가 없어 안 붙지만 POST / PUT 에서는 필수다. 실무에서 가장 많이 깨지는 지점.

값 쓰임
application/json REST API 기본
multipart/form-data 파일 업로드
application/x-www-form-urlencoded HTML form 기본값

Spring 의 @RequestBody 가 안 먹는 사고 대부분이 이 헤더 문제다.

Content-Length: 348

바디의 바이트 길이. 서버가 어디까지 읽어야 하는지 아는 기준이다. GET 에는 없다.

Authorization: Bearer <token>

JWT 방식 인증. 쿠키(세션) 대신 쓰는 다른 축이다.

면접에서 "세션 vs JWT" 비교는 거의 반드시 나온다.

  • 세션 — 서버가 상태를 들고 있음(Redis 등). 강제 로그아웃이 쉽다.
  • JWT — 서버가 상태를 안 들고 있음. 확장이 쉽지만 즉시 폐기가 어렵다.
Origin: http://43.202.208.133

CORS 의 정체가 이 헤더다. 브라우저가 강제로 붙이고 JS 로 위조가 불가능하다. 서버는 이걸 보고 "허용된 출처냐" 를 판단한다.

캐슬챗에 CORS 설정이 없는 이유 — 모든 요청이 nginx 한 곳으로 가서 출처가 하나뿐이고, 출처가 같으면 브라우저가 CORS 검사 자체를 하지 않는다.

2순위 알아두면 실력 차이가 나는 것

If-None-Match / If-Modified-Since

캐시 재검증용. 응답의 ETag / Last-Modified 와 짝을 이룬다.

1회차 응답 : ETag: "6aa4110f-224"        + 본문 548 바이트
2회차 요청 : If-None-Match: "6aa4110f-224"
2회차 응답 : 304 Not Modified            + 본문 없음   <-- 전송량 절약

JS 번들이 수백 KB 일 때 효과가 크다.

Accept-Encoding: gzip, deflate

"압축해서 줘도 된다" 는 신고. 서버가 압축하면 응답에 Content-Encoding: gzip 이 붙는다.

현재 캐슬챗 서버는 안 붙여준다. nginx.conf 에 gzip on; 이 없어서다. 한 줄 추가로 체감 로딩이 줄어든다. "성능 개선 경험" 소재.

Connection: keep-alive

"응답 주고 연결 끊지 마." 3-way handshake 를 파일마다 반복하지 않게 해준다. HTTP/1.1 기본값.

Accept: text/html,application/xhtml+xml,*/*;q=0.8

"이런 형식으로 줘." 콘텐츠 협상에 쓴다. q=0.8 은 선호도 가중치(0~1)로, 숫자가 클수록 선호한다는 뜻이다.

X-Forwarded-For: 203.0.113.42

프록시를 거치면 뒷단 서버가 보는 접속 IP 는 nginx 의 IP 가 된다. 진짜 사용자 IP 를 알려주려고 nginx 가 끼워넣는 헤더다.

로그 분석, IP 차단에 필수. X- 접두사는 "표준이 아닌 관례" 라는 뜻이다.

proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
Cache-Control: no-cache

캐시 정책. 요청과 응답 양쪽에 다 붙을 수 있다. 요청에 붙으면 "캐시 쓰지 말고 새로 줘" 이고, 브라우저에서 Ctrl+Shift+R 이 이것이다.

3순위 존재만 알면 되는 것

User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131

절대 신뢰하면 안 된다. 누구나 조작한다. curl 로 크롬인 척하는 것도 한 줄이면 된다.

통계와 로그 용도로만 쓸 것. 인증이나 분기 판단에 쓰면 사고로 이어진다.

Referer: http://43.202.208.133/login

어디서 눌러서 왔는지. 스펠링이 틀린 게 표준이다(Referrer 가 맞는 철자). 초기 오타가 그대로 굳었다.

Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8

다국어 사이트의 기본 언어 결정용.

Range: bytes=1024-2047

파일의 일부만 요청한다. 동영상 중간으로 점프하는 기능이 이것이다. 응답의 Accept-Ranges: bytes 가 "나 이거 지원함" 표시다.

형식 규칙

  • 각 줄 끝은 \n 이 아니라 \r\n (CRLF) 다.
  • 헤더 블록 끝에 빈 줄 하나가 더 붙는다. 이게 "헤더 끝" 신호이고, 안 보내면 서버가 헤더가 더 올 줄 알고 영원히 기다린다.
  • 헤더 순서는 정해져 있지 않다. Host 만 필수다.
  • 헤더 이름은 대소문자를 구분하지 않는다.
  • http 는 전부 평문이다. 쿠키까지 중간에서 그대로 읽힌다. 실서비스는 HTTPS 필수.

실제로 소켓에 흘러가는 바이트

GET / HTTP/1.1\r\n
Host: 43.202.208.133\r\n
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131\r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Encoding: gzip, deflate\r\n
Accept-Language: ko-KR,ko;q=0.9\r\n
Connection: keep-alive\r\n
Cookie: JSESSIONID=...\r\n
\r\n                        <-- 이 빈 줄이 끝 신호
