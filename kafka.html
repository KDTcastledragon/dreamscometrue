토픽 Topic       castlechat.chat.message     이름일 뿐. 논리적 단위

파티션 하나는 끝에만 덧붙이는 로그 파일이다. 중간 수정도 삭제도 없다. 그래서 디스크를 순차로만 쓰고, 그래서 빠르다.

2 — Partitioner — 어디 있고 뭘 하나

어디 있나

org.apache.kafka.clients.producer
  .internals.BuiltInPartitioner

-> Kafka 클라이언트 라이브러리 안
-> channel-engine JVM 안에서 돈다
-> ★ 브로커가 아니다

파티션은 보내기 전에 프로듀서가 정한다. 내 코드에 Partitioner 클래스가 없다 — 기본 구현을 그대로 쓴다.

key 유무로 갈린다

key 가 있으면
  murmur2(직렬화된 key) % 파티션수
  roomId 5 -> 항상 같은 파티션
  ★ 순서 보장의 전부가 이것이다

key 가 null 이면
  sticky partitioning
  배치가 찰 때까지 한 파티션에 몰고
  차면 다음으로 옮긴다
  순서 보장 없음. 배치 효율은 좋다
kafkaTemplate.send(CHAT_MESSAGE_TOPIC, roomId, event);
//                                     ^^^^^^ 이 자리가 key

roomId 를 key 자리에 넣은 그 한 가지가 방 안의 순서를 만든다.

파티션 수를 함부로 못 늘리는 이유

파티션을 6개에서 12개로 늘리면 % 파티션수 의 결과가 전부 바뀐다. 방 5번이 파티션 2에서 5로 옮겨간다.

그러면 옛 메시지는 파티션 2에, 새 메시지는 파티션 5에 남는다. 두 파티션은 서로 순서를 모르므로 그 방의 순서가 깨진다.

그래서 파티션 수는 처음에 넉넉히 잡아두는 게 원칙이다. 내가 컨슈머 1개인데도 파티션을 6개로 만들어 둔 이유가 이것이다.

3 — 컨슈머와 컨슈머 그룹

Consumer 는 브로커에서 읽어가는 쪽이다. 내 경우 event-persist-worker 가 그것이다.

Consumer Group 은 같은 일을 나눠 하는 컨슈머들의 묶음이다. groupId 가 같으면 한 그룹이다.

@KafkaListener(topics = ChatKafkaTopics.CHAT_EVENT_TOPIC,
               groupId = "${chat.kafka.persist-group-id:event-persist-worker}")
//                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 이게 그룹 이름
그룹이 다르면 같은 메시지를 또 받는다

같은 그룹 안에서는 나눠 먹지만, 그룹이 다르면 각자 전부 받는다.

groupId = "event-persist-worker"  -> DB 저장
groupId = "search-indexer"        -> 검색 색인
  두 그룹이 같은 메시지를 각각 다 받는다

나중에 검색 색인이나 통계 집계를 붙일 때 기존 worker 를 건드리지 않아도 되는 이유다.

리밸런싱 — 중복 소비가 생기는 지점

파드가 늘거나 줄면 브로커가 파티션을 다시 나눠준다. 그 사이에 오프셋 커밋 전에 파드가 죽으면 새 담당 컨슈머가 같은 메시지를 다시 읽는다.

그래서 Kafka 는 최소 한 번(at-least-once) 전달이고, 소비 쪽이 멱등해야 한다. 내 worker 의 inserted == 0 처리가 그것이다.

4 — “안녕” 한 건을 따라가기

철수(userId 12)가 5번 방에서 “안녕” 을 보냈다. 그 한 건이 어떤 모습으로 바뀌며 DB 까지 가는지만 본다.

Kafka 가 “개입하는 순간” 은 두 번이다 
publishDurable() 호출
  -> Kafka 클라이언트 라이브러리

     ★ 전부 내 JVM 메모리 안에서 돈다

  -> 그제야 브로커가 개입
     ★ 네트워크를 넘어간다

.get() 이 깨어나기 전까지 내 메시지는 아직 아무 데도 안 갔다. 그때 JVM 이 죽으면 그냥 사라진다.

모습이 바뀌는 지점만 추리면 
"안녕"  (문자열)
  -> JSON  (ws 전송용)
  -> Command 객체  (wsgate)
  -> protobuf 바이너리  (gRPC)
  -> Command 객체  (cheg)
  -> EventDTO  (★ Kafka 용)
  -> JSON 바이트  (Serializer)
  -> 로그 파일의 한 줄  (브로커)
  -> EventDTO  (worker 역직렬화)
  -> DB 한 행

글자는 그대로고 껍데기만 9번 바뀐다. 경계를 넘을 때마다 그 경계가 아는 형식으로 갈아입는다.

5 — 그래서 Serializer · Partitioner · Accumulator · Sender 가 뭔데

전부 내가 만든 게 아니라 라이브러리에 들어 있는 자바 클래스다. 그리고 넷 다 KafkaProducer 객체 하나 안의 필드다. 그림의 네모들이 사실은 한 객체 안의 부품들이다.

build.gradle
  implementation 'org.springframework.kafka:spring-kafka'
        |  이게 kafka-clients.jar 를 끌어온다
        v
  org.apache.kafka.clients.producer.KafkaProducer      ★ 실체는 이 클래스 하나

public class KafkaProducer<K,V> implements Producer<K,V> {
    private final Serializer<K> keySerializer;        ①
    private final Serializer<V> valueSerializer;      ①
    private final Partitioner partitioner;            ②
    private final RecordAccumulator accumulator;      ③
    private final Sender sender;                      ④
    private final Thread ioThread;                    ④ 를 돌리는 전용 스레드
}

역할로 나누면 섞이지 않는다

역할 무엇 설명
변환기 Serializer 모습을 바꾼다. 아무것도 저장하지 않는다
계산기 Partitioner 숫자를 낸다. 저장소가 아니다
저장소 RecordAccumulator 메모리 임시 저장
파티션 2 디스크 영구 저장. 도구가 아니라 파일이다
일꾼 Sender 스레드 버퍼에서 꺼내 보낸다
리스너 컨테이너 스레드 브로커에서 가져와 DB 에 넣는다
주소 offset 4 “어디 있나” 를 가리키는 번호. 저장소가 아니다
offset 은 메모리의 “번지” 와 같다 
메모리    1번지 2번지 3번지 ...      번지가 "어느 칸" 인지 가리킨다
파티션    offset 0 1 2 3 4 ...     offset 이 "어느 칸" 인지 가리킨다

offset 은 상자가 아니라 상자에 붙은 번호표다. 그래서 컨슈머가 “나 4번까지 읽었다” 고 번호만 들고 다닐 수 있다.

① Serializer — 인터페이스. 구현체는 내가 골랐다

# application.properties — 이 두 줄이 Serializer 다
spring.kafka.producer.key-serializer=org.apache.kafka.common.serialization.LongSerializer
spring.kafka.producer.value-serializer=org.springframework.kafka.support.serializer.JsonSerializer

LongSerializer   roomId(Long 5) -> 8바이트          Kafka 가 기본 제공
JsonSerializer   EventDTO -> Jackson JSON -> UTF-8  Spring Kafka 가 제공 (Kafka 원본엔 없다)

public interface Serializer<T> {
    byte[] serialize(String topic, T data);     메서드 하나뿐이다
}

직접 만들 수도 있다. implements Serializer<T> 하고 properties 에 그 클래스 이름을 적으면 된다. 나는 기성품 두 개를 쓴 것이다.

소비 쪽도 짝이 있다 
spring.kafka.consumer.key-deserializer=...LongDeserializer
spring.kafka.consumer.value-deserializer=...ErrorHandlingDeserializer
spring.kafka.consumer.properties.spring.deserializer.value.delegate.class=...JsonDeserializer

ErrorHandlingDeserializer 로 한 번 더 감싼 게 중요하다. 역직렬화 자체가 실패하면 그 레코드는 영원히 처리되지 않고 컨슈머가 같은 자리에서 무한 재시도로 멈춘다(poison pill). 이 래퍼가 그걸 잡아서 DLT 로 보낸다.

② Partitioner — 기본 구현이 자동으로 붙는다

org.apache.kafka.clients.producer.internals.BuiltInPartitioner
                                   ^^^^^^^^^ internals 패키지 = 교체 전제가 아니다

int partition = Utils.toPositive(Utils.murmur2(serializedKey)) % numPartitions;
//                                     ^^^^^^^ 해시 함수 이름

내 properties 에 partitioner.class 가 없으므로 기본 그대로다. 같은 입력이면 항상 같은 숫자가 나오므로 roomId 5 는 언제나 파티션 2 로 간다.

③ RecordAccumulator — 그냥 Map 이다

public final class RecordAccumulator {
    private final ConcurrentMap<TopicPartition, Deque<ProducerBatch>> batches;
    //                          파티션마다         배치들의 큐
}

batches = {
  (castlechat.chat.message, 0) : [ 배치A ]
  (castlechat.chat.message, 2) : [ 배치B ]   <- "안녕" 이 여기 들어간다
  (castlechat.chat.message, 5) : [ 배치C ]
}

파티션별로 줄을 세워놓고 레코드를 쌓아두는 메모리 자료구조다. 그 이상이 아니다. 배치가 batch.size(기본 16KB)만큼 차거나 linger.ms 가 지나면 “보낼 준비됨” 으로 표시된다.

④ Sender — CPU 스레드가 아니라 자바 스레드 1개

CPU 코어     물리 연산 장치. t3.medium 은 2개
OS 스레드    커널이 스케줄링하는 단위
             코어보다 훨씬 많이 만들 수 있다
자바 스레드   JVM 의 Thread 객체
             OS 스레드와 1:1 로 붙는다

실행 중 스레드 목록을 찍으면
  main
  http-nio-8090-exec-1
  http-nio-8090-exec-2
  kafka-producer-network-thread | producer-1
  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 이게 Sender
public class Sender implements Runnable {
    public void run() {
        while (running) { runOnce(); }
    }
    void runOnce() {
        sendProducerData(now);  // 준비된 배치 -> ProduceRequest
        client.poll(...);       // 실제 네트워크 I/O
    }
}

// KafkaProducer 생성자
this.ioThread = new KafkaThread(
    "kafka-producer-network-thread | " + clientId,
    sender, true);
this.ioThread.start();          // ★ 여기서 시작

KafkaProducer 하나당 Sender 스레드도 하나다. 내 앱엔 KafkaTemplate 이 하나니까 스레드도 하나고, 그 하나가 모든 파티션으로의 전송을 담당한다. 처리량이 아주 커지면 여기도 병목이 될 수 있는 지점이다.

6 — send() 와 .get() — 누가, 무엇을, 어디에

send() — 누가 · 무엇을 · 어디에 
누가    exec-N (Tomcat 스레드)
        ★ Sender 가 아니다

무엇을  직렬화된 바이트 레코드
        key 8바이트 + value JSON 바이트
        + 타임스탬프 + 헤더

어디에  RecordAccumulator 안의
        "파티션 2 전용 큐" 맨 끝 배치

직렬화와 파티션 계산까지 전부 내 스레드가 한다. 그래서 fan-out 때처럼 여기도 내 스레드의 CPU 를 쓴다.

.get() — 누가 · 어디에 · 무엇이 
누가    exec-N

어디에  그 Future 안의 잠금 장치
        FutureRecordMetadata
          -> ProduceRequestResult
            -> CountDownLatch(1)

무엇이  latch.await()
          -> LockSupport.park()
          -> OS 에 "깨울 때까지 날 빼줘"
“잠든다” 의 물리적 의미
스레드 상태 RUNNABLE → WAITING
CPU 전혀 안 쓴다. 스케줄링 대상에서 빠진다
스택 · 레지스터 그대로 보존된다. 깨면 그 자리에서 이어간다
메모리 계속 차지한다 (스택 약 1MB)
Tomcat 스레드 풀 ★ 200자리 중 한 자리를 묶는다 — 이게 진짜 비용

CPU 입장에서는 손해가 없다. 그동안 다른 스레드를 돌린다. 문제는 그 스레드가 다른 요청을 처리할 수 없다는 것이다.

200개가 전부 .get() 에서 자고 있으면 CPU 는 한가한데 201번째 요청이 큐에서 대기한다. 처리량 = maxThreads ÷ 건당 지연 이 여기서 나온다.

8 — 보내는 쪽 — send() 와 .get() 은 다르다

send() — 즉시 반환한다 
kafkaTemplate.send(토픽, roomId, event)
  • Serializer 가 key · value 를 바이트로
  • Partitioner 가 파티션을 고름
  • RecordAccumulator 에 넣기만 하고 Future 를 돌려준다
  • 이 시점엔 브로커에 아무것도 안 갔다. 메모리에만 있다
.get() — 여기서 막힌다 
.get(sendTimeoutMs, TimeUnit.MILLISECONDS)
  • 그 Future 가 완료될 때까지 스레드를 재운다
  • CPU 는 안 쓴다. WAITING 상태로 내려간다
  • 대신 Tomcat 스레드 풀의 한 자리를 묶는다
  • 실패하면 예외 → 사용자에게 전송 실패 응답
그래서 생기는 비용 — 배치가 죽는다

Kafka 가 빠른 이유는 배치다. linger.ms 동안 모아 batch.size 만큼 한 번에 보낸다.

배치 전송        수십만 건/s
건당 .get()      수천 건/s      <- 10~100 배 차이

내 설정 : linger.ms 는 기본값 0  ->  모으지 않는다
          거기에 .get() 까지 겹쳐 배치 크기가 사실상 1

다만 이건 의도된 트레이드오프다. .get() 을 빼면 “성공했습니다” 라고 말한 뒤 유실될 수 있다. prpr 3번의 “durable save 후 response” 가 이 한 줄이다.

9 — 브로커에서 실제로 일어나는 일

파티션 2의 리더가 ProduceRequest 수신
  -> 로그 파일 끝에 append
  -> acks=all 이면 ISR(따라잡은 복제본들) 전부가 복제할 때까지 대기
  -> 응답에 partition, offset 을 담아 회신
정정할 것 — acks=all 이 fsync 를 뜻하지 않는다

내 ChatMessageEventPublisher 주석에 “브로커가 디스크에 기록을 마친 뒤에야 future 가 완료된다” 고 적혀 있는데, 엄밀히는 OS 페이지 캐시까지다.

fsync 는 별개 설정(log.flush.interval.messages 등)이고 기본값은 OS 에 맡긴다. Kafka 는 fsync 대신 “복제본 여러 개” 로 내구성을 확보하는 설계다.

acks=all + RF 3   3대에 복제. 1대 디스크가 날아가도 안전   <- 정상 구성
acks=all + RF 1   ★ 복제본이 없다. 그 1대가 날아가면 유실  <- 내 구성

주석을 “브로커가 로그에 기록하고 ISR 이 복제를 마친 뒤” 로 고치고, RF 가 1이라 ISR 도 1개 라는 걸 같이 적어두는 게 정확하다.

10 — 가져가는 쪽 — push 가 아니라 pull

cheg 는 worker 에게 아무것도 주지 않는다. 브로커에 쓰고 끝이다. worker 가 있는지조차 모른다.

@KafkaListener(topics = ..., groupId = "event-persist-worker")   클래스에 붙는다
public class ChatEventPersistWorker {

    @KafkaHandler                                                메서드에 붙는다
    public void persistChatMessage(ChatMessageCreatedEventDTO event) { ... }

    @KafkaHandler
    public void persistDeleteChatMessage(ChatMessageDeletedEventDTO event) { ... }

    @KafkaHandler
    public void persistReactChatMessage(ChatMessageReactedEventDTO event) { ... }
}

한 토픽에 Created · Deleted · Reacted 세 종류가 섞여 오므로 @KafkaHandler 가 타입을 보고 분기한다. 그래서 @KafkaListener 가 클래스에 붙어 있다.

멱등 소비 — 예외를 던지지 않는다 
int inserted = chatMapper.insertChatMessage(msg);

if (inserted == 0) {
    log.info("이미 저장된 메시지");
    return;        // ★ 예외를 던지지 않는다
}

리밸런싱이나 커밋 전 종료로 같은 메시지가 두 번 올 수 있다. messageId 가 PK 라 두 번째는 0행이 된다.

#3 짚을 점

11 — 왜 DB 를 끊어놨나

끊지 않았다면 
메시지 보내기
  -> DB INSERT 를 동기로 기다림
  -> 성공하면 응답

응답 속도가 DB 쓰기 속도에 그대로 묶인다. DB 가 느려지면 채팅이 전부 느려지고, DB 가 죽으면 메시지를 아예 못 보낸다.

끊어서 얻은 것

응답은 Kafka 가 받은 시점에 돌아간다. DB 쓰기는 worker 가 자기 속도로 처리한다.

DB 가 잠깐 죽어도 메시지는 계속 오간다. 쌓인 건 DB 가 살아나면 worker 가 밀린 만큼 따라잡는다.

대가도 있다 — 같이 말해야 한다 
화면에는 메시지가 보이는데 DB 에는 아직 없는 순간이 존재한다
  -> 그 순간 새로고침하면 메시지가 안 보일 수 있다
  -> 최종적 일관성(eventual consistency)

worker 가 밀리면 그 지연이 길어진다
  -> 지금은 모니터링이 없어서 얼마나 밀리는지 알 방법이 없다

이걸 먼저 말하는 게 낫다. 장점만 말하면 “그럼 단점은요” 가 바로 온다.

12 — 자주 묻는 것

Kafka 를 왜 쓰셨나요?
  -> 응답을 DB 쓰기 속도에서 떼어내려고.
     그리고 유실 없이 떼어내야 해서 acks=all 로 확인까지 기다린다

★ acks=all 이라는데 브로커가 몇 대죠?
  -> 1대다. ISR 도 1개라 사실상 acks=1 이다.
     설정은 맞지만 내구성 보장은 실질적으로 없다.
     운영이면 3대 + RF 3 + min.insync.replicas 2 여야 한다

key 를 roomId 로 한 이유는?
  -> 같은 방은 같은 파티션 -> 방 안의 순서 보장.
     파티션을 늘려도 그 성질이 유지된다

파티션을 6개로 한 이유는?
  -> 컨슈머는 1개지만 나중에 늘릴 때를 위해.
     파티션 수를 나중에 바꾸면 해시 결과가 달라져 순서가 깨진다

중복 소비는 어떻게 막나요?
  -> 못 막는다. Kafka 는 at-least-once 다.
     대신 소비 쪽을 멱등하게 만들었다. inserted == 0 이면 정상 종료

worker 가 죽으면 메시지가 사라지나요?
  -> 아니다. 브로커에 남아 있다.
     살아나면 커밋한 offset 부터 이어 읽는다. 유실이 아니라 반영이 늦는 것

.get() 때문에 느리지 않나요?
  -> 느리다. 배치가 죽는다.
     처리량 대신 "성공이라 말한 건 반드시 저장됐다" 를 택한 것

DLT 에 쌓이면 어떻게 하나요?
  -> 지금은 사람이 봐야 한다. 재처리 도구가 없다 (솔직하게)
