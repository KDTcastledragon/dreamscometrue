아래 캐시에서 못 찾았을 때만 DNS 질의가 랜선을 타고 나간다. 이때 첫 패킷은 TCP SYN 이 아니라 DNS 질의고, 엄연한 네트워크 패킷이라 Home Router 를 똑같이 거친다. 캐시에서 찾으면 DNS 패킷은 아예 나가지 않고 첫 패킷이 TCP SYN 이 된다.

① 캐시부터 뒤진다 (여기서 끝나는 경우가 대부분)

  1. 브라우저 캐시 크롬은 자체 DNS 캐시를 들고 있다. chrome://net-internals/#dns 에서 볼 수 있다. ipconfig /flushdns 로는 안 지워진다.
  2. DNS Resolver Cache Windows 11 의 DNS Client 서비스(Dnscache)가 메모리에 들고 있다. 커널이 아니라 svchost.exe 안에서 도는 유저 모드 서비스다. 명령 프롬프트에서 ipconfig /displaydns 를 치면 이 캐시에 들어 있는 도메인과 IP 목록이 출력되고, ipconfig /flushdns 를 치면 이 캐시가 전부 비워진다.
  3. hosts 파일 C:\Windows\System32\drivers\etc\hosts. 여기 적으면 DNS 서버보다 우선적으로 적용된다. 로컬 개발에서 자주 쓴다.

② 캐시에 없으면 밖으로 묻는다

  1. Stub Resolver 내 PC 안에 있다. 딱 한 번만 묻고 기다린다. Root 니 TLD 니 직접 돌지 않는다.
  2. Recursive Resolver 질의를 받아 대신 돌아다니는 쪽이다. Root → TLD → 권한 네임서버를 차례로 묻는다.
  3. 권한 네임서버 "43.202.208.133 이다." → TTL 만큼 ①의 캐시들에 저장된다.

순서를 틀리기 쉽다

첫 패킷은 SYN 이 아니다. 기본 게이트웨이 MAC 을 모르면 ARP 가 가장 먼저 나간다.

그래서 실제 순서는 ARP → DNS 질의 → TCP SYN 이고, Home Router 를 두 번 지난다.

랜선을 타고 나가는 순서 (DNS 캐시와 ARP 캐시가 둘 다 비어 있을 때)

[1차]  ARP        기본 게이트웨이 MAC 확보     (같은 랜 안에서만)
[2차]  DNS 질의   UDP 53  -> Home Router -> NAT -> Recursive Resolver
                  <- 응답 : 43.202.208.133
[3차]  TCP SYN    목적지 43.202.208.133:80 -> Home Router -> NAT -> 서버
왜 UDP 53 인가

응답이 작고 빨라야 하며, 실패하면 그냥 다시 물으면 되기 때문이다. 연결을 맺는 비용이 질의 자체보다 크다.

다만 응답이 512 바이트를 넘거나 영역 전송(zone transfer) 일 때는 TCP 로 넘어간다.

DoH 가 켜져 있으면 다르다

크롬의 "보안 DNS 사용"(chrome://settings/security) 이 켜져 있으면 질의가 UDP 53 이 아니라 TCP 443 위의 HTTPS 로 나간다.

즉 DNS 조회 자체가 또 하나의 TCP 연결과 TLS Handshake 를 끌고 온다.

  1. Network Service Process 가 socket() 호출. Kernel 이 TCB 생성, TCP State = CLOSED. 소켓 번호(fd) 반환.
  2. Web Browser의 Network Service Process가 그 socket 번호로 connect() 호출.
  3. Kernel 메모리에 있는 TCP/IP 스택의 Routing Table 조회. (참고:Windows는 tcpip.sys가 들고 있고 route print로 봄. Linux에서는 FIB(Forwarding Information Base)이고 ip route로 봄.)
  4. IP 계층의 경로 조회 함수(Linux기준 /boot/vmlinuz의 fib_table_lookup())가 Routing Table 전체에 longest prefix match 를 적용해 한 줄을 고른다. 그 줄에 next hop · 나갈 NIC 가 적혀 있고, Source IP 는 그 NIC 의 IP 로 정해진다. 더 구체적인 줄이 없다면 0.0.0.0/0(Default Gateway)이 남는다. (VPN, Docker, WSL이 있다면, 10.0.0.0/8 · 172.17.0.0/16 같은 추가 경로 있음.) NIC, Source IP 는 경로 조회 결과에 포함됨. 인터넷 주소는 보통 Default Gateway로 감.
  5. 출발지 Port 배정, 4-tuple 완성, ISN 결정. TCP State : CLOSED → SYN_SENT 변경.
  6. TCP/IP스택이 TCP segment , IP Packet 조립. (Linux 기준 tcp_connect() 과 ip_queue_xmit()이 TCP , IP 조립.)
  7. Kernel 메모리의 TCP/IP 스택에 있는 ARP Cache 조회. Cache에 값이 없을 경우, ARP로 next hop IP를 이용하여 MAC Address를 찾음. (같은 LAN · Docker · WSL 은 next hop = 목적지 자신. tun 방식 VPN 은 MAC 이 없어서 ARP 를 안 함.)
  8. Linux는 Kernel의 L2 Code의 eth_header()(net/ethernet/eth.c)가 14Byte Ethernet Header 생성. (dev_hard_header()는 이 함수를 부르는 입구다.) 그 다음 dev_queue_xmit() → qdisc(Kernel의 송신 대기열) → NIC Driver의 ndo_start_xmit() 호출. Windows 는 tcpip.sys 가 Frame 을 만들어 NDIS(ndis.sys)를 거쳐 NIC Driver(miniport, 내 PC 는 Intel 의 Netwtw10.sys)로 넘긴다.
  9. NIC Driver가 TX Ring 에 Frame 위치를 적고, NIC 의 레지스터를 써서 "가져가" 신호 (doorbell).
  10. NIC의 DMA(Direct Memory Access) 엔진이 PCIe를 통해 CPU를 거치지 않고 RAM 에서 Frame Byte를 직접 읽어 온다.
  11. MAC 블록에서 Preamble(+SFD) 과 FCS(CRC-32) 를 붙인다. PHY 에서 비트를 신호로 바꿔 내보낸다.
  12. NIC 가 Interrupt로 "보냈다" 를 알리고 드라이버가 버퍼를 정리.

connect() — 누구의 함수이고 누가 일하나

connect(소켓, 43.202.208.133:80) 은 브라우저가 만든 함수가 아니다. OS 가 프로그램에게 열어준 소켓 API 이고 브라우저는 그걸 부르기만 한다. SYN 을 실제로 만들어 보내는 건 Kernel 의 TCP/IP 스택 이다.

Client PC (Windows 11) 무엇 모드
브라우저 connect() 를 부른다 user mode
ws2_32.dll · mswsock.dll Winsock. 소켓 API 의 Windows 구현. connect() 라는 함수가 실제로 정의된 곳 user mode
(System32 의 일반 DLL)
afd.sys Ancillary Function Driver for Winsock. Winsock 이 Kernel 로 넘어가는 문 Kernel
tcpip.sys TCP/IP Protocol Driver. SYN 을 만들고 State 를 바꾼다 Kernel

Winsock 은 Kernel 이 아니다. Windows 프로그램이 네트워크를 쓰려고 부르는 user mode 라이브러리고, 그 안에서 afd.sys 로 요청을 넘겨야 Kernel 로 들어간다.
Linux 는 다르다. connect() 가 libc 를 거쳐 곧바로 System Call이 된다.

connect() 를 부르면 Kernel 이 하는 일

  1. 라우팅 테이블에서 경로를 고른다. Default Gateway 로 갈지, 어느 NIC 로, Source IP 는 무엇으로 할지가 정해진다.
  2. 내 쪽 포트를 배정한다(예 51234). 이제 4-tuple(출발지 IP:Port + 목적지 IP:Port)이 완성된다.
  3. socket() 때 이미 만들어진 TCB 에 4-tuple 과 ISN 을 기록한다.
  4. State 를 CLOSED → SYN_SENT 로 바꾸고, SYN 패킷을 만들어 Default Gateway 로 내보낸다.
  5. SYN+ACK 가 오면 ACK 를 보내고 ESTABLISHED 가 된다. connect() 가 리턴했다 = Handshake 가 끝났다.
    Chrome 은 non-blocking 으로 불러 연결이 완성되면 이벤트로 알림을 받는다. 기준은 같다.

SYN 의 TCP · IP · Frame 헤더를 만드는 세부 순서는 아래 ‘Kernel 이 패킷을 조립하는 순서’ 에 있다.

서버 쪽 짝은 listen() · accept()

NGINX 는 시작할 때 listen(80) 으로 소켓을 LISTEN 상태로 만들고, 연결이 하나 완성될 때마다 accept() 로 꺼낸다(실제로는 accept4()). 부르는 건 NGINX 프로세스고, 구현하는 건 N-Kernel(Linux) 이다.

accept() 는 Handshake 를 하지 않는다. Kernel 이 이미 끝낸 연결을 accept 큐에서 꺼내 새 fd(conn_fd = 9)로 돌려줄 뿐이다.

패킷이 실제로 가는 길

여기가 "네트워크를 아느냐" 를 가르는 지점이다. connect() 한 번에 패킷이 C-Kernel → Home Router(NAT) → 라우터들 → 방화벽 → N-Kernel 순서로 지나간다. 단계별 설명은 #2 의 ‘SYN 이 실제로 가는 경로’ 에 있다.

같은 길을 두 번 간다

이 경로는 TCP SYN 기준이지만, 위의 DNS 질의도 똑같은 길을 지난다. 목적지만 Recursive Resolver 로 바뀔 뿐 Kernel → Home Router NAT → 라우터 순서는 같다.

Kernel 이 패킷을 조립하는 순서

  1. 경로 선택 목적지 IP 를 라우팅 테이블에서 찾는다. 내 IP 192.168.0.5 와 서브넷 마스크 255.255.255.0 을 AND 해서 내 망은 192.168.0.0/24 임을 안다. 목적지 43.202.208.133 은 여기 없다 → Default Gateway 로 보낸다. 어느 NIC 로 나갈지와 Source IP 도 여기서 정해진다.
  2. 포트 · ISN · TCB 출발지 포트를 임시 포트(49152~65535) 중에서 하나 고른다. 응답이 어느 프로그램 것인지 구분하는 열쇠다. 그리고 ISN 을 정해 socket() 때 만들어진 TCB 에 기록하고, State 를 CLOSED → SYN_SENT 로 바꾼다.
  3. TCP 헤더 flag = SYN, Sequence Number = ISN, Options(MSS · Window Scale · SACK) 로 SYN 세그먼트를 만든다. Source IP 가 정해져야 체크섬도 계산할 수 있어서 위 단계가 먼저다.
  4. IP 헤더 Source IP · Destination IP, Protocol = 6(TCP), TTL 로 IP 패킷을 만든다.
  5. ARP Default Gateway 의 IP 는 아는데 MAC 을 모르면 "192.168.0.1 쓰는 사람 MAC 알려줘" 를 브로드캐스트로 뿌려 알아낸다. 이미 캐시에 있으면 생략한다. ARP 는 같은 랜 안에서만 동작한다.
  6. Ethernet 헤더 목적지 MAC = Default Gateway 의 MAC, 출발지 MAC = 내 NIC. Frame 이 완성되고 NIC 가 내보낸다.

위는 만드는 순서다(TCP → IP → Frame 으로 바깥을 감싼다). 랜선에 실제로 나가는 순서는 다르다. SYN 은 MAC 을 알아낼 때까지 대기하고 ARP 질의가 먼저 나간다.

계층별로 누가 무엇을 보는가

계층 헤더에 담기는 것 이걸 보는 장비 어디까지 유지되나
L2 Ethernet 출발지/목적지 MAC Switch, Home Router 홉마다 새로 쓰인다
L3 IP 출발지/목적지 IP, TTL 라우터 끝까지 유지 (NAT 구간 제외)
L4 TCP 포트, 플래그, 순서번호 최종 목적지 Kernel 만 끝까지 유지
L7 HTTP 메서드, 헤더, 바디 NGINX, Spring Boot 끝까지 유지
MAC 은 왜 홉마다 바뀌나

MAC 은 "옆집까지 가는 주소", IP 는 "최종 목적지 주소" 다. 택배로 치면 IP 는 받는 사람 주소, MAC 은 지금 이 트럭이 들를 다음 물류센터다.

그래서 라우터를 하나 지날 때마다 L2 헤더는 새로 쓰이고 L3 는 그대로다.

자주 틀리는 것

"라우터가 포트 80 을 보고 보낸다" — 틀렸다. 라우터는 L3 까지만 본다. 포트는 L4 라 최종 목적지 Kernel 에서야 읽힌다.

예외는 NAT 다. Home Router 는 세션을 구분해야 해서 포트까지 들여다본다.

돌아오는 길

응답은 같은 경로를 되짚어 온다. Home Router 가 나갈 때 기록해둔 NAT 테이블이 열쇠다. "공인 IP:51234 로 온 응답은 사설 192.168.0.5:51234 에게" 라는 기록이 없으면 Home Router 는 그 패킷을 누구에게 줘야 할지 몰라서 버린다.

  1. NIC가 수신한 Byte를 DMA로 RAM에 입력. N-Kernel이 sk_buff 구조체로 감싸고, sk_buff를 TCP/IP 스택의 ip_rcv() -> tcp_v4_rcv() 함수(입구 역할)로 넘김.
  2. TCP/IP 스택 내부의 established 표에서 4-tuple로 socket 찾음. 처음 오는 SYN 이라 established 표에 해당 4-tuple 이 없으니, listen 표에서 목적지 Port(현재는 80. NGINX 소프트웨어가 시작할 때 bind(80)으로 요청해서, N-Kernel이 listen socket에 묶어 둔 번호.)를 들고 있는 N-Kernel의 listen socket 으로 간다.
  3. SYN Queue 와 accept Queue가 꽉 찼는지 본다. SYN Queue가 찼다면, request_sock을 만들지 않고, SYN+ACK 패킷의 Sequence Number에 SYN Cookie를 넣는다. accept Queue가 찼다면, SYN이 담긴 sk_buff를 해제하고 응답자체를 보내지 않음. (C-Kernel은 SYN_SENT 상태에서 기다리다가 SYN을 재전송함.)
  4. TCP/IP 스택의 tcp_conn_request() 함수 내부의 inet_reqsk_alloc() 함수가 request_sock 생성. TCB 아님.
  5. request_sock에 4-tuple, Client의 ISN, N-Kernel의 ISN, SYN 옵션들 기록.
  6. request_sock의 state 칸에 TCP State = SYN_RECV 기록 후, request_sock 자체를 SYN Queue 에 삽입.
  7. SYN+ACK 에 답이 없을시 재전송 하기 위해, request_sock 내부의 재전송 타이머 시작.
  8. TCP/IP 스택의 tcp_v4_send_synack() 함수가 inet_csk_route_req() 로 Routing Table 조회. Client 쪽 주소(Home Router 의 공인 IP)는 서버와 같은 LAN 에 없으니 Default Gateway 줄이 골라지고, 나갈 NIC · Source IP 가 정해진다.
  9. tcp_make_synack() 함수가 request_sock 에 적힌 값을 읽어 새 sk_buff 에 TCP segment 조립. flag = SYN+ACK, Sequence Number = N-Kernel 의 ISN, Acknowledgment Number = Client 의 ISN + 1, Options(MSS · Window Scale · SACK)는 Client 가 SYN 에 실어 보낸 것 중 N-Kernel 도 쓰는 것만 넣는다. 이어서 __tcp_v4_send_check() 가 TCP 체크섬을 준비한다. (NIC 가 Checksum Offload 를 지원하면 마지막 계산은 NIC 가 한다.)
  10. ip_build_and_send_pkt() 함수가 IP Packet 조립. Source IP = N-Kernel 의 IP, Destination IP = Client 쪽 Home Router 의 공인 IP, Protocol = 6(TCP), TTL. (아직 TCB 가 없고 request_sock 뿐이라, C-Kernel 이 쓴 ip_queue_xmit() 대신 이 함수를 쓴다.) 그 다음 ip_local_out() → ip_output() → ip_finish_output2() 로 L2 에 넘긴다.
  11. Kernel 메모리의 TCP/IP 스택에 있는 ARP Cache 에서 Default Gateway 의 MAC Address 조회. 서버는 Default Gateway 와 계속 통신하니 보통 Cache 에 있다. 없으면 ARP 로 찾는 동안 SYN+ACK 은 대기한다.
  12. neigh_output() 함수가 14Byte Ethernet Header 를 붙인다. Cache 에 MAC 이 있으면 neigh_hh_output() 이 미리 만들어 둔 Header 를 복사하고, 없었으면 ARP 응답 후 dev_hard_header() → eth_header() 가 새로 만든다. 목적지 MAC = Default Gateway 의 MAC, 출발지 MAC = 서버 NIC. 그 다음 dev_queue_xmit() → qdisc(Kernel의 송신 대기열) → NIC Driver의 ndo_start_xmit() 호출.
  13. NIC Driver가 TX Ring 에 Frame 위치를 적고, NIC 의 레지스터를 써서 "가져가" 신호 (doorbell).
  14. NIC의 DMA(Direct Memory Access) 엔진이 PCIe를 통해 CPU를 거치지 않고 RAM 에서 Frame Byte를 직접 읽어 온다.
  15. MAC 블록에서 Preamble(+SFD) 과 FCS(CRC-32) 를 붙인다. PHY 에서 비트를 신호로 바꿔 내보낸다.
  16. NIC 가 Interrupt로 "보냈다" 를 알리고 드라이버가 SYN+ACK 의 sk_buff 를 해제. request_sock 은 SYN Queue 에 그대로 남아 N-Kernel 메모리에 존재한다. ACK 가 안 오면 7번의 재전송 타이머가 이 request_sock 값으로 SYN+ACK 을 다시 조립해 보낸다.
  1. NIC가 수신한 Byte를 DMA로 RAM에 입력. C-Kernel이 sk_buff 구조체로 감싸고, sk_buff를 TCP/IP 스택의 ip_rcv() -> tcp_v4_rcv() 함수(입구 역할)로 넘김. (Windows 는 NIC Driver(miniport) → NDIS → tcpip.sys 가 받는다.)
  2. TCP/IP 스택 내부의 established 표에서 4-tuple로 TCB 찾음. connect() 때 C-Kernel 이 이 4-tuple 의 TCB 를 established 표에 이미 넣어 두었으니 바로 찾는다. listen 표는 보지 않는다. 찾은 TCB 의 TCP State = SYN_SENT.
  3. TCB 의 State 가 SYN_SENT 라서 tcp_v4_do_rcv() → tcp_rcv_state_process() → tcp_rcv_synsent_state_process() 함수로 간다. SYN Queue · accept Queue · request_sock 은 listen socket 을 가진 N-Kernel 쪽 이야기라 C-Kernel 에는 없다.
  4. tcp_parse_options() 가 SYN+ACK 의 Options(MSS · Window Scale · SACK · Timestamp)를 먼저 읽는다. 그 다음 순서대로 검사한다. ① Acknowledgment Number 가 C-Kernel 의 ISN + 1 인지 본다. 틀리면 RST 를 보내고 버린다(TCB 는 SYN_SENT 그대로). ② Acknowledgment Number 가 맞는데 RST flag 가 켜져 있으면 연결 실패로 끝난다(connect() 가 "연결 거부" 오류를 받는다). ③ SYN flag 가 없으면 버린다.
  5. tcp_ack() 함수가 ACK 처리. 재전송 대기열에 있던 SYN 을 지우고, 남은 송신 패킷이 없으니 SYN 재전송 타이머를 멈춘다.
  6. TCB 에 다음에 받을 번호(rcv_nxt) = N-Kernel 의 ISN + 1 기록. (ISN 만 따로 적는 칸은 없다. N-Kernel 이 SYN Cookie 를 썼다면 그 값이 ISN 자리에 들어 있고, C-Kernel 은 구분하지 못하고 그냥 ISN 으로 받는다.) 상대의 Window 크기를 적고, 4번에서 읽은 Options 로 Window Scale · Timestamp · MSS 를 확정.
  7. tcp_finish_connect() 함수가 TCB 의 TCP State 를 SYN_SENT → ESTABLISHED 로 변경. 이어서 sk_state_change() 가 connect() 결과를 기다리던 Network Service Process 를 깨운다. C-Kernel 은 이 시점부터 데이터를 보낼 수 있고, N-Kernel 은 아직 SYN_RECV 다.
  8. tcp_send_ack() → __tcp_send_ack() 함수가 ACK segment 조립. flag = ACK, Sequence Number = C-Kernel 의 ISN + 1, Acknowledgment Number = N-Kernel 의 ISN + 1, 데이터 없음. 이번에는 TCB 가 있으니 __tcp_transmit_skb() → ip_queue_xmit() 가 TCP · IP 를 조립하고, 경로는 connect() 때 TCB 에 저장해 둔 것을 다시 쓴다. 목적지는 4-tuple 의 Destination IP:Port(서버 IP:80), 즉 그 IP 를 가진 N-Kernel 이다. NGINX 소프트웨어는 이 ACK 를 보지 못한다. (예외: 프로세스가 연결이 끝나기를 기다리며 write() 에 막혀 있었다면, ACK 를 따로 보내지 않고 delayed ACK 타이머를 걸어 곧 나갈 첫 데이터에 실어 보낸다.)
  9. ip_local_out() → ip_output() → ip_finish_output2() 로 L2 에 넘긴다. ARP Cache 에서 Default Gateway 의 MAC Address 조회. SYN 을 보낼 때 이미 알아냈으니 보통 Cache 에 있고, neigh_output() → neigh_hh_output() 이 미리 만들어 둔 14Byte Ethernet Header 를 복사한다. (Cache 항목이 오래돼 다시 확인해야 하는 상태면 neigh_resolve_output() → dev_hard_header() → eth_header() 로 간다.) 그 다음 dev_queue_xmit() → qdisc(Kernel의 송신 대기열) → NIC Driver의 ndo_start_xmit() 호출. (Windows 는 tcpip.sys → NDIS → miniport.)
  10. NIC Driver가 TX Ring 에 Frame 위치를 적고, NIC 의 레지스터를 써서 "가져가" 신호 (doorbell).
  11. NIC의 DMA(Direct Memory Access) 엔진이 PCIe를 통해 CPU를 거치지 않고 RAM 에서 Frame Byte를 직접 읽어 온다.
  12. MAC 블록에서 Preamble(+SFD) 과 FCS(CRC-32) 를 붙인다. PHY 에서 비트를 신호로 바꿔 내보낸다.
  13. NIC 가 Interrupt로 "보냈다" 를 알리고 드라이버가 ACK 의 sk_buff 를 해제. ACK 는 재전송 대기열에 들어가지 않아 재전송 타이머가 없다. 이 ACK 가 사라져도 두 길로 복구된다. ① C-Kernel 이 이어서 보내는 첫 데이터(HTTP 요청 등)에도 ACK flag 와 같은 Acknowledgment Number 가 실려 있어, N-Kernel 은 그걸로 연결을 완성한다. ② N-Kernel 이 SYN+ACK 을 재전송하면, 이미 ESTABLISHED 인 C-Kernel 은 tcp_validate_incoming() 에서 SYN 을 보고 challenge ACK 로 같은 번호의 ACK 를 다시 보낸다.

질문에 대한 답

  1. SYN+ACK 을 받으면 바로 ESTABLISHED? 아니다. 먼저 flag 와 Acknowledgment Number(C-Kernel 의 ISN + 1)를 검사한다(4번). 맞을 때 tcp_finish_connect() 가 바꾼다(7번). 바뀌는 곳은 socket 이 아니라 C-Kernel 의 TCB 다.
  2. C-Kernel 에도 SYN Queue · accept Queue · request_sock 이 있나? 없다. 셋 다 listen socket 을 가진 N-Kernel 쪽에만 있다. C-Kernel 은 connect() 때 TCB 를 established 표에 넣어 두었으니 2번에서 바로 자기 TCB 를 찾는다.
  3. ACK 는 누구에게 보내나? N-Kernel 이다. 목적지는 4-tuple 의 Destination IP:Port(서버 IP:80)이고, 그 IP 를 가진 N-Kernel 이 받는다. NGINX 소프트웨어는 이 ACK 를 보지 못하고, 나중에 accept() 로 완성된 연결만 꺼낸다.
  4. request_sock 은 C-Kernel 메모리에 남나? C-Kernel 에는 request_sock 이 처음부터 없다. 모든 값은 TCB 에 있다.

▶ 왜 2번이 아니라 3번인가

답은 양쪽 모두 "내 말이 상대에게 닿는다" 를 확인해야 하기 때문이다.

단계 이걸 받고 나면 확인되는 것
SYN 서버가 "클라이언트 → 나" 경로가 살아 있음을 안다.
SYN + ACK 클라이언트가 양방향이 모두 살아 있음을 안다.
ACK 서버도 "나 → 클라이언트" 경로가 살아 있음을 안다.

2번에서 멈추면 서버는 자기가 보낸 SYN+ACK 가 도착했는지 모른다. 그 상태로 데이터를 보내면 허공에 쏘는 꼴이 된다.

C-Kernel 의 TCP State

State 뜻 이 State 가 되는 순간
CLOSED 연결이 전혀 없다. 상대가 누군지 모른다 소켓이 만들어진 직후(socket())
SYN_SENT SYN 을 보냈고 SYN+ACK 를 기다리는 중. 답을 못 받은 SYN 이 하나 떠 있다 connect() 가 SYN 을 내보내는 순간
ESTABLISHED Handshake 완료. 데이터를 주고받을 수 있다 SYN+ACK 를 받고 ACK 를 보내는 순간
  • State 는 Kernel 의 TCB 에 적혀 있다. 브라우저는 State 를 보지 못하고 connect() 의 결과(성공 · 실패)만 안다.
  • SYN_SENT 에서 답이 없으면 Kernel 이 간격을 늘려가며 SYN 을 다시 보낸다. 끝내 없으면 connect() 가 실패하고 타임아웃이 난다. 방화벽이 조용히 버리는 경우가 바로 이 상태로 머문다.
  • 서버가 그 포트를 안 열었으면 RST 가 바로 돌아와 즉시 CLOSED 로 간다 (connection refused). 무응답(타임아웃)과 즉시 거절(refused)은 원인이 다르다.
  • 직접 보려면 명령 프롬프트에서 netstat -an | findstr SYN_SENT. 평소엔 거의 비어 있다. SYN_SENT 가 아주 짧게 지나가기 때문이다.

▶ socket 은 언제, 누가 만드나

socket() 은 소프트웨어가 Kernel 에게 부탁하는 System Call이다. Kernel 이 스스로 부르지 않는다. NGINX 소프트웨어도 브라우저처럼 socket() 을 부르지만, SYN 이 올 때가 아니라 서버가 시작할 때 한 번 부른다.

언제 누가 무엇을
서버 시작 때 · 한 번 NGINX 소프트웨어 socket() → bind(:80) → listen(). N-Kernel 이 자기 메모리에 listen socket 을 만들고 번호 fd 6 을 돌려준다
브라우저가 연결할 때 Network Service Process socket() → connect(). C-Kernel 이 socket 을 만들고(CLOSED) SYN 을 보낸다
SYN 도착 N-Kernel 혼자 request_sock 생성. socket() 호출 아님. NGINX 소프트웨어는 모른다
마지막 ACK 도착 N-Kernel 혼자 TCB 생성 → accept Queue. socket() 호출 아님. listen socket 을 복제해서 Kernel 안에서 직접 만든다 (Linux tcp_v4_syn_recv_sock())
그 다음 NGINX 소프트웨어 accept() 로 꺼내 새 번호 fd 9 를 받는다. NGINX 소프트웨어가 이 연결을 처음 만지는 순간

서버 쪽은 listen socket 하나 + 연결마다 socket 하나다. listen socket 은 연결을 받는 창구일 뿐 데이터는 주고받지 않고, 데이터는 연결마다 생긴 socket(fd 9 등)으로 오간다.

▶ Client 쪽 listen socket — 보통 없다

  • listen socket 은 연결을 받는 쪽만 만든다. 브라우저는 연결을 거는 쪽이라 socket() → connect() 만 하고 listen() 은 하지 않는다. 그래서 이 연결에서 Client 쪽 listen socket 은 없다.
  • Client socket 의 번호도 fd 6 이 아니다. 번호는 OS 가 그때 비어 있는 걸 주는 값이고, fd 6 은 NGINX 소프트웨어 쪽 예시값이다. Windows 는 fd 라는 작은 정수 대신 SOCKET 핸들(예 0x1A4)을 준다.
backlog 큐

Handshake 가 끝난 연결은 accept 큐에 쌓인다. NGINX 가 바쁘면 큐가 차고, 가득 차면 새 연결이 거절되거나 지연된다.

트래픽이 몰릴 때 "연결은 되는데 느리다" 가 여기서 나온다. somaxconn, backlog 튜닝 대상이다.

SYN Flood

SYN 만 잔뜩 보내고 ACK 를 안 보내면 서버의 SYN_RCVD 상태가 쌓여 정상 연결을 못 받는다. 고전적인 DoS 수법이다.

방어책이 SYN Cookie 다. 상태를 저장하지 않고 순서번호 자체에 정보를 인코딩해서, ACK 가 돌아올 때 복원한다.

연결을 끊을 때는 4번

종료는 FIN → ACK → FIN → ACK 로 4-way 다. TCP 는 양방향이 독립적이라 한쪽이 "나는 보낼 거 다 보냈다" 해도 반대쪽은 아직 보낼 게 남아 있을 수 있기 때문이다.

이때 먼저 닫은 쪽이 TIME_WAIT 로 한동안 남는다. 서버 재시작 직후 "Address already in use" 가 뜨는 이유가 이것이다.

Handshake는 Kernel이 한다 — NGINX 가 아니다

흔한 오해

"NGINX 가 SYN 을 받아서 SYN+ACK 를 보낸다" — 틀렸다. NGINX 는 SYN 을 보지도 못한다. Kernel이 Handshake를 혼자 다 끝낸 뒤에 NGINX 에게 넘긴다.

전화 비유

  • Kernel = 교환원. 벨이 울리면 받아서 통화를 성립시킨다.
  • NGINX = 담당 직원. 교환원이 연결해준 통화를 건네받아 실제 대화를 한다.
  • 직원은 벨소리와 "연결 중" 신호에 참여하지 않는다. 수화기를 받았을 때 통화는 이미 성립돼 있다.

1~3 번에 NGINX 가 없다. TCP Handshake는 TCP 프로토콜의 일이고 TCP 구현체가 Kernel 안에 있기 때문이다. 유저랜드 프로그램이 매번 직접 악수하게 만들면 모든 서버 프로그램이 TCP 를 새로 구현해야 한다.

패킷은 층으로 포개져 있고, 중간 라우터는 봉투 안을 뜯어보지 않는다.

|  |  src IP : 192.168.0.5    (내 PC 사설)      |  |
|  |  dst IP : 43.202.208.133                  |  |  <-- 라우터가 보는 건 이것만

|  |  |  dst port : 80                     |   |  |  <-- 최종 Server Kernel만 본다
|  |  |  flags    : SYN                    |   |  |

|  +-------------------------------------------+  |
+-------------------------------------------------+
  1. 브라우저 socket() + connect() 호출. 여기서 브라우저 역할은 끝이고 나머지는 Kernel이 한다.
  2. C-Kernel "목적지가 내 서브넷에 없네" 판단 → Default Gateway(= Home Router)로 보내기로 결정. ARP 로 Home Router 의 MAC 을 알아내 전송.
  3. Home Router NAT(NAPT). 출발지 IP 를 사설 → 공인으로 바꿔치기하고, 돌아올 응답을 누구에게 줄지 포트로 기억해둔다.
  4. 라우터들 ISP → 백본 → AWS. 수십 홉을 목적지 IP 만 보고 전달한다.
  5. 방화벽 보안그룹이 80 번 허용을 확인한다. 막혀 있으면 여기서 조용히 버려지고 브라우저는 타임아웃이 난다.
  6. N-Kernel "80 번 듣는 소켓 있음(NGINX)" → SYN+ACK 발사. 여기가 답이다. (캐슬챗처럼 Docker 컨테이너라면 이 앞에서 호스트 Kernel 의 iptables DNAT 가 컨테이너로 돌려준다.)

GET 이후 Rendering까지

location / 에는 proxy_pass 가 없다. 즉 "WAS 서버에게 물어볼 필요 없음" 이다.

location / {
    try_files $uri $uri/ /index.html;
}

# $uri = "/" 이므로 왼쪽부터 순서대로 시도한다
#   1차 $uri   -> /usr/share/nginx/html/   디렉토리라서 실패
#   2차 $uri/  -> 디렉토리 맞음 -> index 지시자 -> index.html 발견. 성공
#   3차 /index.html  -> 갈 필요 없었음
  1. NGINX 자기 디스크에서 index.html 을 읽어 200 OK + 548 바이트 반환.
  2. 브라우저 Content-Type: text/html 을 보고 HTML 파서 가동. 확장자가 아니라 이 헤더가 기준이다.
  3. 브라우저 DOM 트리 구축. <div id="root"> 가 비어 있어 아직 흰 화면이다.
  4. 브라우저 CSS / JS 추가 GET. keep-alive 덕분에 같은 TCP 연결을 재사용하고 Handshake를 다시 하지 않는다.
  5. 브라우저 DOM + CSSOM → Render Tree → Layout → Paint. 흰 화면이 실제로 모니터에 출력된다.
  6. 브라우저 defer 스크립트 실행. React 가 비어 있던 root 를 채운다. 네트워크가 아닌 순수 DOM 조작이다.
  7. 브라우저 DOM 이 바뀌었으니 Layout → Paint 를 다시 돈다. 로그인 화면이 보인다.

스크립트 두 종류의 차이

  • <script defer> — 다운로드는 즉시, 실행은 파싱이 끝난 뒤. HTML 파싱을 멈추지 않는다. 없으면 그만큼 화면이 늦게 뜬다.
  • <link rel="stylesheet"> — 반대로 Rendering을 막는다(render-blocking). CSS 없이 그리면 스타일 없는 날것이 번쩍 보였다가 바뀌므로 브라우저가 일부러 기다린다.

WAS 서버가 필요해지면 Handshake가 한 번 더

  • ① 브라우저 → N-Kernel Handshake  (클라이언트 ↔ Web 서버)
  • ② NGINX → S-Kernel Handshake  (Web 서버 ↔ WAS 서버) — 완전히 별개의 연결
역할이 뒤집힌다

NGINX 는 브라우저에 대해서는 서버(SYN 을 받는 쪽), Spring Boot 에 대해서는 클라이언트(SYN 을 보내는 쪽)가 된다.

②의 SYN+ACK 를 보내는 건 S-Kernel 이다. 이때도 톰캣은 악수에 참여하지 않고 accept() 로 완성된 연결만 받는다. Web 서버에서 일어난 일이 WAS 서버에서 똑같이 반복된다.

그리고 WAS 서버가 보는 접속 IP 는 브라우저가 아니라 NGINX 가 된다. 그래서 X-Forwarded-For 가 필요하다.

#3 공인 IP · 사설 IP · 도메인 — 배포 구성 두 가지

"백엔드에 IP 가 없다" 는 말의 정확한 뜻

IP 가 없는 게 아니라 공인 IP 가 없다.

WAS 서버 상태 뜻
사설 IP 10.0.1.20 있다 내부망에서는 이걸로 통신한다
공인 IP 없다 인터넷에서 닿을 경로가 없다
비유

사설 IP 는 집 안에서만 쓰는 호수, 공인 IP 는 전 세계에서 찾아올 수 있는 주소다. WAS 서버는 아파트 안의 1203 호인데 그 아파트 주소가 비공개인 상태다. 같은 아파트 사람(Web 서버)은 1203 호를 찾아갈 수 있지만 외부인은 아파트 자체를 못 찾는다.

도메인은 프로세스에 붙는 게 아니다

흔한 오해

"Spring Boot 의 도메인" 이라는 말은 엄밀히는 성립하지 않는다. 정확히는 "Spring Boot 앞단에 노출된 공인 IP 의 도메인" 이다.

도메인  --DNS A 레코드-->  공인 IP 하나

castlechat.com  ->  203.0.113.10  ->  Web 서버 (NGINX)
                                            |
                                            +-> 10.0.1.20 (Spring Boot)
                                                도메인 불필요. 공인 IP 불필요

도메인을 산다는 건 외부 노출 지점 하나에 이름을 붙이는 것이고, 그 지점이 NGINX 다.

구성 1 — 단일 출처 (리버스 프록시). 캐슬챗 방식

castlechat.com  ->  NGINX  (공인 203.0.113.10)
   (도메인 1개)        |
                      |  /          -> 자기 디스크의 정적 파일
                      |  /user/...  -> 10.0.1.20:8080  --> Spring Boot
                      |  /chat/...  -> 10.0.1.20:8080  --> (도메인 없음)
  • 도메인 1 개로 끝난다. 백엔드는 공인 IP 도, 도메인도 필요 없다.
  • 브라우저 입장에서 출처가 하나뿐이라 CORS 가 발생하지 않는다.

캐슬챗 compose 파일 주석에 그대로 적혀 있는 내용이다.

# 브라우저 입장에서 출처가 nginx 하나뿐이라 CORS도 발생하지 않는다.
# 밖으로 여는 포트는 nginx의 80 하나뿐이다. 다른 컨테이너 포트를 publish 하면
# 출처가 늘어나면서 CORS가 되살아난다.

구성 2 — 분리 출처. "서버쪽 도메인" 이 필요한 경우

www.site.com  ->  프론트엔드   (S3 + CloudFront / Vercel / Netlify)
                   빌드된 html, js, css 만 올라감

api.site.com  ->  백엔드       <-- 여기에 공인 IP + 도메인이 필요하다
                   Spring Boot

프론트를 정적 호스팅에 올리고 백엔드를 따로 두는 구성이다. 브라우저의 JS 가 api.site.com 으로 직접 요청을 쏘기 때문에 백엔드도 외부 접근이 가능해야 한다.

대신 대가가 있다

출처가 2개 (www.site.com != api.site.com)
   -> 브라우저가 CORS 검사 발동
   -> 백엔드에 CORS 설정 필수
        @CrossOrigin / WebMvcConfigurer#addCorsMappings
        Access-Control-Allow-Origin 헤더
        preflight(OPTIONS) 요청 처리
        쿠키 쓰려면 allowCredentials + SameSite 까지

두 구성 비교

구성 1 (리버스 프록시) 구성 2 (분리 출처)
도메인 1 개 1 개 + 서브도메인
백엔드 공인 IP 불필요 필요
CORS 없음 설정 필수
인증서(HTTPS) 1 장 2 장 (또는 와일드카드 1 장)
백엔드 공격 노출 없음 있음 (방화벽으로 막아야)
프론트 배포 서버에 파일 올림 CDN 에 올림. 전송이 빠름
프론트/백 독립 배포 어려움 쉬움

캐슬챗의 현재 상태

구성 1 이고, 도메인을 사지도 않았다. 43.202.208.133 이라는 공인 IP 를 직접 쓰고 있다. NGINX 설정에 증거가 있다.

server_name _;    # "도메인 안 가림. 뭐든 다 받음"

도메인을 사면 이 자리에 server_name castlechat.com; 을 적게 된다. NGINX 설정 한 줄 + DNS A 레코드 하나가 끝이고, Spring Boot 는 한 글자도 안 고친다.

추가로 알아둘 것

서브도메인은 공짜다

api.site.com 을 위해 도메인을 또 살 필요가 없다. site.com 하나 사면 api., www., admin. 등을 무한히 만들 수 있다. DNS 레코드만 추가하면 된다.

구성 2 에서도 Spring Boot 를 맨몸으로 노출하지 않는다

api.site.com -> ALB (공인 IP) -> Spring Boot #1 (사설 IP)
                              -> Spring Boot #2 (사설 IP)
                              -> Spring Boot #3 (사설 IP)

즉 api.site.com 이 가리키는 건 톰캣이 아니라 로드밸런서의 공인 IP 다.

결론

어느 구성이든 Spring Boot 자체는 사설 IP 만 갖는다. 공인 IP 를 받는 건 항상 그 앞단(NGINX 또는 로드밸런서)이다. 그래야 서버를 여러 대로 늘릴 수 있고, 도메인이 특정 인스턴스에 묶이지 않는다.

#2 브라우저에서 wsgate 까지

브라우저 · C-Kernel

  1. React JSON.stringify({wsType:"SEND_MESSAGE", payload:{roomId:5, messageText:"안녕"}}) → ws.send(문자열)
  2. 브라우저 내장 WebSocket 구현이 Frame 을 만든다. FIN=1 · opcode=0x1(text) · MASK=1 — 클라이언트가 보내는 프레임은 반드시 마스킹. 그리고 write() 로 커널 송신 버퍼에 복사
  3. C-Kernel TCP/IP 스택이 세그먼트 → IP 패킷으로 감싼다. 목적지 IP 는 끝까지 서버 IP, 바뀌는 건 MAC 뿐이다. 이미 연결된 상태라 DNS · ARP · Handshake 는 없다

N-Kernel · NGINX — 패킷이 아니라 바이트를 중계한다

NGINX 는 애플리케이션이라 패킷을 못 본다. 커널이 재조립한 바이트를 읽고 쓴다. 그래서 연결이 둘로 끊어져 있다.

소켓 어느 Kernel 누가 fd 로 쥐나 역할
A C-Kernel 브라우저 연결 1 의 클라이언트 끝
B N-Kernel NGINX fd 7 — downstream 연결 1 의 서버 끝
C N-Kernel NGINX fd 9 — upstream 연결 2 의 클라이언트 끝
D S-Kernel Tomcat 연결 2 의 서버 끝
  1. N-Kernel 패킷 수신 → TCP 재조립 → downstream 소켓(fd 7) 수신 버퍼에 바이트가 쌓인다
  2. NGINX read(fd 7) 로 유저 공간에 꺼내고 write(fd 9) 로 upstream 소켓에 넣는다. 프레임을 파싱하지 않는다. 그냥 바이트다
  3. N-Kernel upstream 소켓 송신 버퍼의 바이트를 8090 과의 별개 TCP 연결에 새 패킷으로 만들어 보낸다. 포트 · 시퀀스 번호가 전부 다른 새 패킷이다
연결이 둘이라서 생기는 설정 
location /ws {
    proxy_pass http://10.0.1.20:8090;            # 온프레미스면 WAS 서버 사설 IP
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Real-IP $remote_addr;     # wsgate 가 보는 출발지는 NGINX 다
    proxy_read_timeout 3600s;                    # 연결 2 에만 걸리는 타임아웃
}

NGINX 는 브라우저에게는 서버, wsgate 에게는 클라이언트다. 한 프로세스가 두 역할을 하므로 소켓이 2개 필요하다.

S-Kernel → Tomcat → Spring → Dispatcher

  1. S-Kernel 재조립한 바이트를 Tomcat 소켓(D) 수신 버퍼에 쌓는다
  2. Tomcat WsFrameServer 가 프레임 수신 · 언마스킹 · 조각(continuation) 재조립 → jakarta.websocket 표준 API 로 올린다. Tomcat 은 여기까지
  3. Spring StandardWebSocketHandlerAdapter 가 받아 handleMessage() → 타입 분기 → WsGateDispatcher.handleTextMessage(). Spring 은 여기부터. DispatcherServlet 은 안 탄다
  4. Dispatcher objectMapper.readValue() 로 WebSocketDTO 변환 → switch(wsType) → "SEND_MESSAGE" 면 WsGateChatHandler.handleSendMessage()
헷갈리는 지점

DispatcherServlet 을 타는 건 WS Handshake 한 번뿐이다. 그때 HttpSessionHandshakeInterceptor 가 HTTP 세션의 로그인 정보를 WS 세션으로 복사해 둔다. 그 뒤의 메시지 프레임은 전부 위 경로로 온다.

wsgate ChatHandler → gRPC

  1. ChatHandler wsGateAuth.requireLoginUser(session) — Handshake 때 복사해 둔 세션에서 userId · publicId 를 꺼낸다
  2. ChatHandler payload 변환 + 입구 필터 (roomId 없음 · 내용도 첨부도 없음 → 여기서 실패 응답). 깨진 요청을 내부 서비스까지 보내지 않는다
  3. ChatHandler new CreateChatMessageCommand(...) → wsGateChatClient.createChatMessage(cmd). 필드 타입이 인터페이스(WsGateChatClient)라 gRPC 를 모른다
  4. ClientGrpc WsGateChatClientGrpc 가 chEngineStub.createChatMessage(req) 호출. BlockingStub 이라 exec-N 이 여기서 잠든다

Kafka 발행 — 여기서 또 잠든다

  1. Publisher ChatMessageCreatedEventDTO 생성 → publishChatMessageCreated() → publishDurable()
  2. KafkaProducer send(토픽, roomId, event) — Serializer 로 바이트 변환, Partitioner 가 murmur2(roomId) % 6 으로 파티션 결정, RecordAccumulator 에 넣고 Future 만 반환. 아직 브로커에 안 갔다

  4. 브로커 파티션 2 로그 끝에 append → acks=all 이라 ISR 복제 대기(브로커 1대라 ISR 도 1개) → partition · offset 응답

#4 돌아가는 길과 비동기 저장

응답 복귀와 브로드캐스트

  1. Endpoint DTO → proto 로 바꿔 onNext() · onCompleted()
  2. wsgate 잠들어 있던 exec-N 이 깨어난다. GrpcToDtoConverter 로 다시 DTO
  3. Writer WsGateOutboundWriter 가 세 번 보낸다 — broadcastToRoom(지금 방을 보는 사람) · pushChatRoomUpdate(나머지 멤버의 방 목록) · pushChatMessageNotification(알림 대상). 보고 있는 사람을 빼서 세 집합이 겹치지 않게 했다
  4. Writer 세션마다 synchronized 로 락을 잡고 session.sendMessage(). 같은 exec-N 이 순차로 쓴다 = fan-out
  5. 브라우저 같은 경로를 거꾸로 타고 프레임 도착 (서버 → 클라이언트 프레임은 마스킹 안 함) → React 가 상태를 바꿔 “안녕” 이 화면에 뜬다

worker 가 가져가서 DB 에 넣는다

  1. worker @KafkaListener 컨테이너 스레드가 무한 루프로 consumer.poll(). push 가 아니라 pull 이다
  2. worker 역직렬화 → @KafkaHandler persistChatMessage() → insertChatMessage (INSERT IGNORE + messageId 명시)
  3. worker 0행이면 이미 저장된 것으로 보고 정상 종료(멱등). 첨부가 있으면 updateChatMessageAttachments 로 TEMP → ATTACHED
  4. worker 실패하면 500ms × 10회 재시도 → castlechat.chat.message.dlt 로 격리. 버리지 않는다

읽음 위치는 다른 길이다 — Kafka 를 안 탄다

[ 메시지 본문 ]  channel-engine -> Kafka -> event-persist-worker -> DB     별도 프로세스
[ 읽음 위치   ]  channel-engine -> Redis -> ReadPositionFlushWorker -> DB  같은 프로세스 @Scheduled

chat:room:{roomId}:read-position   실제 읽음 위치 (Lua 로 더 클 때만 올림)
chat:dirty:read-position           "아직 DB 에 안 쓴 것" 목록  <- dirty 표시
-> 5초마다 dirty 목록만 긁어 updateLastReadMessageId -> 목록에서 지움

메시지는 유실되면 안 되고 순서가 중요해서 Kafka, 읽음 위치는 최댓값만 맞으면 되고 중간값을 버려도 돼서 Redis. 성질에 맞춰 길을 나눴다.

비동기로 뺀 건 DB 쓰기뿐이다

gRPC 도 Kafka 도 동기로 기다린다. 사용자 경로는 전부 동기고 비동기인 건 worker 쪽 INSERT 와 읽음 위치 flush 뿐이다.

  -> 로그 파일의 한 줄        브로커 파티션 2, offset 4

  -> DB 한 행               chat_messages

글자는 끝까지 그대로고, 경계를 넘을 때마다 그 경계가 아는 형식으로 갈아입는다.

TCP/IP 스택 함수 — 무엇이 무엇을 부르나

Linux Kernel 기준이다. 아래 함수는 전부 Kernel 안의 함수이고, 서로 일반 함수 호출로 이어진다.

▶ Kernel 로 들어오는 입구는 두 종류다

입구 누가 여나 이 흐름에서
System Call 소프트웨어가 Kernel 에 부탁한다. C-Kernel 쪽 connect() (Network Service Process), N-Kernel 쪽 accept4() (NGINX 소프트웨어). 아래 그림에 나오는 System Call은 이 둘이다. 그림 밖에서는 socket()(양쪽), bind() · listen()(NGINX 시작 때), epoll_wait()(NGINX 가 기다릴 때)도 System Call이다.
Interrupt 하드웨어(NIC)가 알린다. SYN · ACK 가 도착하면 NIC 가 Interrupt를 걸고, Driver 가 받아 ip_rcv() 로 넘긴다. 소프트웨어는 전혀 관여하지 않는다. 그래서 Handshake 를 Kernel 혼자 끝낸다. 
System Call 하나가 Kernel 로 들어가는 길 (Linux x86-64, connect 기준)

Network Service Process         connect(fd, 43.202.208.133:80)    libc 함수
  -> syscall 명령어             CPU 가 user mode 에서 Kernel mode 로 바뀐다
  -> entry_SYSCALL_64           Kernel 의 System Call 입구 (어셈블리)
  -> do_syscall_64()            System Call 표에서 42 번(connect) 을 찾는다
  -> __x64_sys_connect()
  -> __sys_connect()            아래 C-Kernel 그림의 첫 Kernel 함수

이 PC 의 C-Kernel 은 실제로 Windows 라 connect() 가 Winsock → afd.sys 로 들어간다. 아래 C-Kernel 그림은 Client 가 Linux 일 때의 길이다.

▶ 상하관계 — 무엇이 무엇 안에 있고, TCB 는 어디인가

  • 초록 상자 두 개가 TCB 다. listen socket 도 TCB(struct tcp_sock)이고, 데이터를 주고받지 않을 뿐이다.
  • SYN Queue 와 accept Queue 는 listen socket 구조체 안의 칸(icsk_accept_queue)이다. SYN Queue 에는 request_sock(TCB 아님)이, accept Queue 에는 TCB 를 가리키는 칸이 줄 선다.
  • established 표와 listen 표는 이 구조체들의 주소를 들고 있는 해시 표다.
  • 용어 — Kernel 안에서 연결의 상태와 구조를 말할 때는 TCB, 소프트웨어 쪽(fd · accept() · 데이터 송수신)에서 볼 때는 Socket 이라고 쓴다. 같은 연결을 어느 쪽에서 보느냐의 차이다.

▶ TCB 구조체는 이렇게 겹쳐 있다

▶ C-Kernel — connect() 부터 SYN 이 나가기까지

TCB 는 socket() 때 이미 있다. connect() 는 초록 줄에서 그 TCB 에 값을 기록한다.

▶ N-Kernel — SYN 을 받고 SYN+ACK 를 보내기까지

System Call이 아니라 NIC Interrupt로 시작한다. 오른쪽 번호는 박스 3 의 8단계 정리 번호다. 이 단계에서는 TCB 를 만들지 않는다.

▶ N-Kernel — ACK 를 받고 accept() 로 fd 9 가 되기까지

이 연결의 TCB 는 여기서, ACK 가 맞을 때 처음 만들어진다.

▶ sk_buff 의 이동 경로

sk_buff 생성 지나가는 곳 해제
C-Kernel 의 SYN tcp_connect() TCP 헤더 → IP 헤더 → ARP → Ethernet 헤더 → Driver → NIC. 헤더는 skb_push 로 앞에 붙는다. NIC 가 보낸 뒤 Driver 가 해제한다(송신 완료 Interrupt). TCP 는 재전송용 사본을 따로 들고 있다.
N-Kernel 이 받은 SYN Driver (NIC 의 DMA 버퍼를 감싼다) ip_rcv() → tcp_v4_rcv() → tcp_conn_request(). 계층을 지날 때 skb_pull 로 헤더를 벗긴다. request_sock 에 필요한 값만 옮겨 적고 바로 해제한다.
N-Kernel 의 SYN+ACK tcp_make_synack() C-Kernel 의 SYN 과 같은 송신 길. NIC 가 보낸 뒤 해제한다. 재전송은 타이머가 request_sock 을 보고 새로 만든다.

함수 이름은 Linux 커널 소스 기준이다. 버전에 따라 중간 단계 이름이 조금씩 다르다. 오른쪽 번호는 박스 3 의 8단계 정리 번호다.

sk_buff — Linux Kernel 안에서 패킷 하나를 담는 구조체

무엇인가

struct sk_buff(줄여서 skb)는 Linux Kernel 이 패킷 하나를 담는 C 구조체다. 받는 패킷이든 보내는 패킷이든 Kernel 안에서는 전부 skb 하나로 함수에서 함수로 넘어간다. 소스는 include/linux/skbuff.h.

  • NIC Driver · IP 계층 · TCP 계층 · 방화벽(iptables / netfilter) · tcpdump 가 전부 skb 를 주고받는다. Linux 네트워크 코드의 중심 구조체다.
  • 서버를 쓰고 운영하는 동안에는 직접 보이지 않는다. Kernel 네트워크 코드 · 드라이버 · eBPF · 네트워크 성능 튜닝을 볼 때 반드시 나온다.
  • Windows 에서 같은 역할을 하는 건 NET_BUFFER_LIST(NDIS)다.

구조 — 메타데이터 + 바이트 버퍼

struct sk_buff (메타데이터)              데이터 버퍼 (실제 바이트)

  head  ----------------------------->  +-- headroom    헤더를 앞에 붙일 빈 공간
  data  ----------------------------->  +-- Ethernet 14 B   <- mac_header
                                        +-- IP 20 B         <- network_header
                                        +-- TCP 32 B        <- transport_header
                                        +-- payload         SYN 은 0 B
  tail  ----------------------------->  +-- tailroom
  end   ----------------------------->  +

  len       지금 data ~ tail 사이 바이트 수
  dev       어느 NIC 로 들어왔나 / 나가나
  sk        어느 socket 소속인가
  protocol  0x0800 = IPv4  (Frame 의 EtherType 값)
  next/prev 큐(SYN Queue 등이 아니라 송수신 대기열)에 줄 세우는 연결 고리

위 수신 패킷 기준이다. 칸 이름(head · data · tail · end · *_header · dev · sk · len)은 실제 소스 그대로다.

핵심 — 계층을 지날 때 바이트를 복사하지 않는다

받을 때 (N-Kernel)

NIC 가 DMA 로 버퍼에 바이트를 넣고, Driver 가 skb 로 감싼다. data 는 Ethernet 헤더 시작을 가리킨다.

IP 계층으로 넘길 때 data 를 14 B 앞으로(skb_pull), TCP 계층으로 넘길 때 20 B 더 앞으로. 포인터만 옮긴다.

보낼 때 (C-Kernel 이 Linux 라면)

tcp_connect() 가 headroom 을 넉넉히 둔 skb 를 만들고 TCP 헤더를 쓴다. ip_queue_xmit() 가 그 앞에 IP 헤더를, eth_header() 가 Ethernet 헤더를 skb_push 로 붙인다.

12단계의 5 ~ 8 번이 이 skb 하나 위에서 일어난다.

Java 로 치면

ByteBuffer 에 메타데이터를 붙인 것과 비슷하다. ByteBuffer 가 position · limit 을 옮기며 읽듯 skb 는 data · tail 을 옮기며 헤더를 벗기고 붙인다.

SYN Cookie — 저장하지 않고 상대에게 맡겨 두는 증표

SYN Queue 가 꽉 찼을 때 N-Kernel 이 쓰는 방법이다. request_sock 을 만들지 않고, 기억해야 할 정보를 SYN+ACK 의 Sequence Number 칸(= N-Kernel 의 ISN) 에 숫자로 새겨 보낸다. 이 32bit 숫자가 쿠키다. 브라우저 쿠키와는 무관하고, “상대에게 맡겨 둔 작은 증표” 라는 뜻이다.

쿠키는 이렇게 만든다 (Linux)

cookie (32bit) =  해시(4-tuple, 비밀키1)
               +  Client 의 ISN
               +  시간 카운터 (약 1분 단위)                       -> 맨 위 8bit
               +  해시(4-tuple, 시간, 비밀키2) + MSS 번호          -> 아래 24bit
                  MSS 번호 = 536 / 1300 / 1440 / 1460 중 몇 번째인지

secure_tcp_syn_cookie() 의 구조다. 비밀키는 부팅 때 정해지고 밖에서 알 수 없다.

흐름

SYN       C-Kernel -> N-Kernel    SYN Queue 꽉 참 -> request_sock 안 만듦. 메모리 0
SYN+ACK   N-Kernel -> C-Kernel    seq = cookie
ACK       C-Kernel -> N-Kernel    ack = cookie + 1
          N-Kernel : 1 을 빼서 cookie 복원 -> 같은 계산을 거꾸로 해서 확인
            - 해시가 맞나        내가 발급한 게 맞나
            - 시간이 2분 이내인가
            - MSS 는 무엇이었나
          맞으면 그때 TCB 생성 -> accept Queue
얻는 것

SYN Flood 로 SYN 이 쏟아져도 연결 후보에 메모리를 한 바이트도 안 쓴다. 정상 사용자는 ACK 를 보내므로 그대로 연결된다.

잃는 것

MSS 를 4가지 값으로만 표현한다. Window Scale · SACK 은 TCP Timestamp 옵션이 있을 때만 살린다. 상태가 없으니 SYN+ACK 를 재전송하지 않는다.

Linux 는 net.ipv4.tcp_syncookies = 1 이 기본값이다. 평소엔 request_sock 을 쓰고, SYN Queue 가 넘칠 때만 쿠키로 바뀐다.

C 구조체 — request_sock 은 무엇인가

구조체 = 이름 붙은 칸 여러 개를 한 덩어리로 묶은 타입

구조체(struct)는 C 에서 타입이 다른 값 여러 개를 이름 붙은 칸으로 묶어 새 타입 하나로 만든 것이다. 메서드 없이 필드만 있는 Java 클래스(DTO, record) 와 거의 같다.

// Java 로 쓰면
class TcpRequestSock {
    int     clientIp;      // 4-tuple
    short   clientPort;
    int     serverIp;
    short   serverPort;
    byte    state;         // SYN_RECV
    int     rcvIsn;        // C-Kernel 의 ISN
    int     sntIsn;        // N-Kernel 의 ISN
    short   mss;           // 1460
    byte    sndWscale;     // 8
    boolean sackOk;        // true
    Timer   rskTimer;      // 재전송 타이머
}
/* C 로 쓰면 (같은 뜻) */
struct tcp_request_sock {
    __be32 rmt_addr;       /* 4-tuple */
    __be16 rmt_port;
    __be32 loc_addr;
    __u16  loc_port;
    u8     state;          /* SYN_RECV */
    u32    rcv_isn;        /* C-Kernel 의 ISN */
    u32    snt_isn;        /* N-Kernel 의 ISN */
    u16    mss;
    u8     snd_wscale;
    u8     sack_ok;
    struct timer_list rsk_timer;
};

오른쪽은 이해하기 쉽게 칸 이름을 모아 줄인 것이다. 실제 커널 소스는 request_sock → inet_request_sock → tcp_request_sock 세 구조체를 겹쳐서 이 칸들을 나눠 담는다(rcv_isn · snt_isn · rsk_timer · mss 는 실제 칸 이름 그대로).

Map · HashSet 같은 자료구조가 아니다

C 구조체 Map · HashSet
칸(키) 컴파일할 때 정해진다. 실행 중에 칸을 늘리거나 뺄 수 없다 실행 중에 마음대로 넣고 뺀다
메모리 칸들이 한 덩어리로 붙어 있다 버킷 배열과 엔트리들이 흩어져 있다
칸 찾기 시작 주소 + 고정 거리(offset). 메모리 한 번 읽으면 끝 키 해시 계산 → 버킷 → 비교
역할 값 하나 (연결 후보 1개) 값 여러 개를 담는 그릇
Map 에 해당하는 건 따로 있다

SYN Queue 와 established 표가 그릇(해시 표) 이고, request_sock 은 그 안에 담기는 원소 하나다. Java 로 치면 Map<FourTuple, TcpRequestSock> 의 value 가 구조체다.

메모리에서는 이렇게 생겼다

N-Kernel 의 RAM (Kernel 영역)

  +0        4-tuple, state = SYN_RECV
  ...       mss = 1460
  ...       rsk_timer (재전송 타이머)

  • N-Kernel 은 request_sock 전용 메모리 창고(slab cache, 이름 request_sock_TCP) 에서 같은 크기의 칸 하나를 꺼내 쓴다. Linux 서버에서 sudo grep request_sock_TCP /proc/slabinfo 로 지금 몇 개가 쓰이는지 볼 수 있다.

ISN · SYN 옵션

ISN (Initial Sequence Number)

Sequence Number 는 보내는 바이트에 붙이는 번호고, ISN 은 그 시작 번호다. 32bit 이고 C-Kernel 과 N-Kernel 이 각자 하나씩 정한다. SYN 은 데이터가 없어도 번호 1 개를 쓴 것으로 치기 때문에, 상대는 ISN + 1 로 답한다.

C-Kernel -> N-Kernel   SYN       seq = 3097674671  (C-Kernel 의 ISN)
N-Kernel -> C-Kernel   SYN+ACK   seq = 1405063271  (N-Kernel 의 ISN)
                                 ack = 3097674672  (C-Kernel ISN + 1)
C-Kernel -> N-Kernel   ACK       seq = 3097674672
                                 ack = 1405063272  (N-Kernel ISN + 1)

C-Kernel 쪽 값은 TCP/IP/Frame 그림과 같은 예시값이고, N-Kernel 쪽 값은 예시다.

왜 0 부터 안 하고 랜덤으로 시작하나

  • 옛 연결의 늦은 패킷이 섞이지 않게. 같은 4-tuple 로 끊었다 다시 붙으면, 네트워크를 떠돌던 이전 연결의 패킷이 새 연결의 번호 범위에 끼어들 수 있다.
  • 번호를 맞혀서 가짜 패킷을 끼워넣는 공격을 막으려고. 번호를 예측할 수 있으면 남이 내 연결에 위조 패킷을 넣을 수 있다.

Linux 는 secure_tcp_seq() 에서 4-tuple 과 부팅 때 정한 비밀키를 섞은 해시 + 현재 시각으로 ISN 을 만든다. 연결마다 다르고 남이 예측할 수 없다(RFC 6528).

SYN 옵션 — 이 SYN 에 실제로 실린 12 바이트

옵션은 [종류 1B][길이 1B][값] 형식이다. NOP 만 1 바이트 단독이다.

바이트 옵션 뜻
02 04 05 B4 MSS = 1460 Maximum Segment Size. “나는 세그먼트 하나에 데이터를 최대 1460 B 까지 받을 수 있다”. 1460 = Ethernet 1500 − IP 헤더 20 − TCP 헤더 20
01 NOP 아무 뜻 없는 1 바이트. 다음 옵션을 4 바이트 경계에 맞추는 채움
03 03 08 Window Scale = 8 TCP 헤더의 Window 칸은 16bit 라 최대 65535 B 밖에 못 적는다. “Window 값에 28 = 256 을 곱해서 읽어라” 는 배율 약속. 고속 회선에서 한 번에 더 많이 보내려고 쓴다
01 01 NOP NOP 채움
04 02 SACK Permitted Selective ACK 허락. 중간이 빠졌을 때 “이 구간들은 받았다” 를 골라서 알려도 되냐는 허락

옵션 말고 헤더에 같이 실리는 것 — Window Size

이 SYN 의 Window Size 는 64240(0xFAF0)이다. “지금 내 수신 버퍼에 이만큼 여유가 있다” 는 뜻이다. 상대는 ACK 를 받기 전까지 이 양을 넘게 보내지 않는다. 이것이 흐름 제어의 기준이다.

Window Scale 이 합의되면 이후 패킷의 Window 값은 배율(×256)을 곱해서 읽는다. 단 SYN · SYN+ACK 자신의 Window 값에는 배율을 적용하지 않는다.

양쪽이 다 보내야 켜진다

Window Scale 과 SACK 은 SYN 과 SYN+ACK 양쪽에 다 실려야 쓴다. 그래서 N-Kernel 이 SYN 의 옵션을 request_sock 에 적어 두고, SYN+ACK 에 자기 값을 실어 보낸다. MSS 는 각자 “나는 이만큼 받는다” 를 알리는 것이라 서로 달라도 된다.

SACK 이 있고 없고

세그먼트 1~9 중 4 만 빠졌다고 하자.

SACK 없음 — ACK 는 “4 부터 줘” 밖에 못 말한다. 보내는 쪽은 5~9 도 다시 보낼 수 있다.

SACK 있음 — “4 부터 줘. 5~9 는 받았다” 를 같이 알린다. 4 만 다시 보낸다.

TCP / IP / Frame — SYN 패킷

헤더만 그렸다. TCP segment 가 IP packet 의 payload 로 들어가고, IP packet 이 다시 Frame 의 Payload 로 들어간다. SYN 은 데이터가 없다. 분홍색은 2번 박스 문장의 ‘목적지 IP’ 와 ‘SYN 플래그’, 초록색은 그 밖의 핵심 칸이다.
값은 예시지만 체크섬 두 개는 이 헤더 바이트로 실제 계산했다(헤더를 다시 더하면 0 이 된다). Sequence Number 와 Identification 은 연결 · 패킷마다 달라지는 값이다.
MAC 주소 두 개는 예시고, FCS 는 위 Frame 바이트로 실제 계산한 CRC-32 다.

렌더링 — 어디까지가 렌더링인가

흐름 요약

이 파일 3개로 화면을 만드는 전 과정  ===  Critical Rendering Path (중요 렌더링 경로)

  1. node_modules 에서 필요한 (13개) 패키지 + 컴포넌트 .jsx + hooks 등 .js → build/static/js/main.e83d3066.js
  2. 모든 .css → build/static/css/main.0bd4de65.css

이 파일 3개로 화면을 만드는 전 과정을 "렌더링" 이라 부르는 건 넓은 의미로만 맞다. 좁은 의미의 Rendering 은 그중 마지막 단계만 가리킨다.

Parsing · 파싱

렌더링 아님

React → DOM 조작, root 채움

→ Layout → Paint → Composite

좁은 의미의 렌더링은 이것만

①②는 렌더링이 아니다.
파싱이고 실행이다.

실제 순서

① Parsing index.html 받음 파싱 → DOM 트리
① Parsing main.css 받음 파싱 → CSSOM 트리
③ Rendering Render Tree → Layout → Paint DOM + CSSOM 합성
흰 화면 출력
② JS 실행 main.js 실행 React 가 root 를 채움
③ Rendering Layout → Paint 다시 DOM 이 바뀌었으므로
실제 화면 출력

3번과 5번만 렌더링이다. 4번은 렌더링이 아니라 JS 실행이고, 그 결과로 렌더링이 다시 일어난다. 아래 6 — Rendering 파이프라인 과 7 — JS 실행, React 등장 을 따로 나눠둔 이유다.

CSR 의 '렌더링' 은 또 다른 뜻이다

용어 여기서 '렌더링' 의 뜻 층위
Rendering 파이프라인 Layout → Paint → Composite 브라우저 내부 동작
CSR (Client Side Rendering) HTML 을 누가 만드느냐 아키텍처
SSR (Server Side Rendering) HTML 을 누가 만드느냐 아키텍처

CSR · SSR 의 '렌더링' 은 "화면을 그린다" 가 아니라 "HTML 을 만들어낸다" 는 뜻이다.

SSR = 서버가 HTML 을 만든다       <-- 네이버
CSR = 브라우저가 HTML 을 만든다   <-- 캐슬챗

[ SSR ]  서버가 완성 HTML --> 브라우저  파싱 --------> Rendering 파이프라인
[ CSR ]  서버가 껍데기만   --> 브라우저  파싱 + JS 실행 --> Rendering 파이프라인
                                                            ^ 둘 다 여기는 같다
그래서

SSR 이든 CSR 이든 마지막에 픽셀을 찍는 건 항상 브라우저의 Rendering 파이프라인이다. SSR 이라고 브라우저가 Layout · Paint 를 안 하는 게 아니다.

결론

넓은 의미 — 맞다

파일 3개로 화면을 만드는 전 과정을 "브라우저가 렌더링한다" 고 흔히 말한다. 정식 명칭은 Critical Rendering Path 다.

좁은 의미 — 일부만

렌더링은 Render Tree → Layout → Paint → Composite 만 가리킨다. 그 앞의 파싱과 JS 실행은 별개 단계다.

일상적으로는 넓은 의미로 써도 통하지만, "JS 실행도 렌더링이냐" 는 질문에는 아니라고 답하는 게 맞다.

  • 요즘은 섞어 쓴다 — Next.js 처럼 첫 화면만 서버에서 조립하고 그 다음부터 브라우저가 조립하는 방식. 캐슬챗은 create-react-app 기반이라 순수 CSR 이다.

네이버는 캐슬챗과 달리 첫 HTML 을 서버에서 조립한다. 그래서 첫 요청부터 백엔드가 관여한다.

캐슬챗도 백엔드는 있다. 다만 조립을 브라우저에 미뤘기 때문에 첫 HTML 을 정적 파일로 둘 수 있었던 것이다.

HTTP 요청 헤더 — 개발자 필수 정리

요청 라인

GET / HTTP/1.1
  • GET — 메서드. GET, POST, PUT, PATCH, DELETE
  • / — 경로
  • HTTP/1.1 — 프로토콜 버전

1순위 모르면 안 되는 것

Host: 43.202.208.133

HTTP/1.1 에서 유일한 필수 헤더. IP 하나에 여러 사이트를 올릴 수 있게 해주는 헤더다.

NGINX 가 server_name 으로 어느 사이트인지 가르는 기준이 이것이다.

server_name _;    # 지금은 "뭐든 다 받음". 도메인 사면 여기에 적는다
Cookie: JSESSIONID=...

HTTP 는 상태가 없다(stateless). 서버는 매 요청을 처음 보는 사람으로 취급한다.

그걸 뚫고 "나 아까 그 사람이야" 를 증명하는 수단이다. 브라우저가 자동으로 붙인다. 첫 방문이면 없다.

Content-Type: application/json

GET 에는 바디가 없어 안 붙지만 POST / PUT 에서는 필수다. 실무에서 가장 많이 깨지는 지점.

값 쓰임
application/json REST API 기본
multipart/form-data 파일 업로드
application/x-www-form-urlencoded HTML form 기본값

Spring 의 @RequestBody 가 안 먹는 사고 대부분이 이 헤더 문제다.

Content-Length: 348

바디의 바이트 길이. 서버가 어디까지 읽어야 하는지 아는 기준이다. GET 에는 없다.

Authorization: Bearer <token>

JWT 방식 인증. 쿠키(세션) 대신 쓰는 다른 축이다.

세션 방식과 JWT 방식의 차이.

  • 세션 — 서버가 상태를 들고 있음(Redis 등). 강제 로그아웃이 쉽다.
  • JWT — 서버가 상태를 안 들고 있음. 확장이 쉽지만 즉시 폐기가 어렵다.
Origin: http://43.202.208.133

CORS 의 정체가 이 헤더다. 브라우저가 강제로 붙이고 JS 로 위조가 불가능하다. 서버는 이걸 보고 "허용된 출처냐" 를 판단한다.

캐슬챗에 CORS 설정이 없는 이유 — 모든 요청이 NGINX 한 곳으로 가서 출처가 하나뿐이고, 출처가 같으면 브라우저가 CORS 검사 자체를 하지 않는다.

2순위 알아두면 실력 차이가 나는 것

If-None-Match / If-Modified-Since

캐시 재검증용. 응답의 ETag / Last-Modified 와 짝을 이룬다.

1회차 응답 : ETag: "6aa4110f-224"        + 본문 548 바이트
2회차 요청 : If-None-Match: "6aa4110f-224"
2회차 응답 : 304 Not Modified            + 본문 없음   <-- 전송량 절약

JS 번들이 수백 KB 일 때 효과가 크다.

Accept-Encoding: gzip, deflate

"압축해서 줘도 된다" 는 신고. 서버가 압축하면 응답에 Content-Encoding: gzip 이 붙는다.

현재 캐슬챗 서버는 안 붙여준다. nginx.conf 에 gzip on; 이 없어서다. 한 줄 추가로 체감 로딩이 줄어든다. "성능 개선 경험" 소재.

Connection: keep-alive

"응답 주고 연결 끊지 마." 3-way handshake 를 파일마다 반복하지 않게 해준다. HTTP/1.1 기본값.

Accept: text/html,application/xhtml+xml,*/*;q=0.8

"이런 형식으로 줘." 콘텐츠 협상에 쓴다. q=0.8 은 선호도 가중치(0~1)로, 숫자가 클수록 선호한다는 뜻이다.

X-Forwarded-For: 203.0.113.42

프록시를 거치면 뒷단 서버가 보는 접속 IP 는 NGINX 의 IP 가 된다. 진짜 사용자 IP 를 알려주려고 NGINX 가 끼워넣는 헤더다.

로그 분석, IP 차단에 필수. X- 접두사는 "표준이 아닌 관례" 라는 뜻이다.

proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
Cache-Control: no-cache

캐시 정책. 요청과 응답 양쪽에 다 붙을 수 있다. 요청에 붙으면 "캐시 쓰지 말고 새로 줘" 이고, 브라우저에서 Ctrl+Shift+R 이 이것이다.

3순위 존재만 알면 되는 것

User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131

절대 신뢰하면 안 된다. 누구나 조작한다. curl 로 크롬인 척하는 것도 한 줄이면 된다.

통계와 로그 용도로만 쓸 것. 인증이나 분기 판단에 쓰면 사고로 이어진다.

Referer: http://43.202.208.133/login

어디서 눌러서 왔는지. 스펠링이 틀린 게 표준이다(Referrer 가 맞는 철자). 초기 오타가 그대로 굳었다.

Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8

다국어 사이트의 기본 언어 결정용.

Range: bytes=1024-2047

파일의 일부만 요청한다. 동영상 중간으로 점프하는 기능이 이것이다. 응답의 Accept-Ranges: bytes 가 "나 이거 지원함" 표시다.

형식 규칙

  • 각 줄 끝은 \n 이 아니라 \r\n (CRLF) 다.
  • 헤더 블록 끝에 빈 줄 하나가 더 붙는다. 이게 "헤더 끝" 신호이고, 안 보내면 서버가 헤더가 더 올 줄 알고 영원히 기다린다.
  • 헤더 순서는 정해져 있지 않다. Host 만 필수다.
  • 헤더 이름은 대소문자를 구분하지 않는다.
  • http 는 전부 평문이다. 쿠키까지 중간에서 그대로 읽힌다. 실서비스는 HTTPS 필수.

실제로 소켓에 흘러가는 바이트

GET / HTTP/1.1\r\n
Host: 43.202.208.133\r\n
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131\r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Encoding: gzip, deflate\r\n
Accept-Language: ko-KR,ko;q=0.9\r\n
Connection: keep-alive\r\n
Cookie: JSESSIONID=...\r\n
\r\n                        <-- 이 빈 줄이 끝 신호
