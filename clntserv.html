① HTTP 보다 TCP 3-way Handshake 가 먼저다.

아래 캐시에서 못 찾았을 때만 DNS 질의가 랜선을 타고 나간다. 이때 첫 패킷은 TCP SYN 이 아니라 DNS 질의고, 엄연한 네트워크 패킷이라 Home Router 를 똑같이 거친다. 캐시에서 찾으면 DNS 패킷은 아예 나가지 않고 첫 패킷이 TCP SYN 이 된다.

① 캐시부터 뒤진다 (여기서 끝나는 경우가 대부분)

  1. 브라우저 캐시 크롬은 자체 DNS 캐시를 들고 있다. chrome://net-internals/#dns 에서 볼 수 있다. ipconfig /flushdns 로는 안 지워진다.
  2. DNS Resolver Cache Windows 11 의 DNS Client 서비스(Dnscache)가 메모리에 들고 있다. 커널이 아니라 svchost.exe 안에서 도는 유저 모드 서비스다. 명령 프롬프트에서 ipconfig /displaydns 를 치면 이 캐시에 들어 있는 도메인과 IP 목록이 출력되고, ipconfig /flushdns 를 치면 이 캐시가 전부 비워진다.
  3. hosts 파일 C:\Windows\System32\drivers\etc\hosts. 여기 적으면 DNS 서버보다 우선적으로 적용된다. 로컬 개발에서 자주 쓴다.

② 캐시에 없으면 밖으로 묻는다

  1. Stub Resolver 내 PC 안에 있다. 딱 한 번만 묻고 기다린다. Root 니 TLD 니 직접 돌지 않는다.
  2. Recursive Resolver 질의를 받아 대신 돌아다니는 쪽이다. Root → TLD → 권한 네임서버를 차례로 묻는다.
  3. 권한 네임서버 "43.202.208.133 이다." → TTL 만큼 ①의 캐시들에 저장된다.

이 경우 질의는 라우터에서 끝나고 라우터가 ISP DNS 로 대신 물어본다. ipconfig /all 의 DNS Servers 에서 확인할 수 있다.

순서를 틀리기 쉽다

첫 패킷은 SYN 이 아니다. 기본 게이트웨이 MAC 을 모르면 ARP 가 가장 먼저 나간다.

그래서 실제 순서는 ARP → DNS 질의 → TCP SYN 이고, Home Router 를 두 번 지난다.

랜선을 타고 나가는 순서 (DNS 캐시와 ARP 캐시가 둘 다 비어 있을 때)

[1차]  ARP        기본 게이트웨이 MAC 확보     (같은 랜 안에서만)
[2차]  DNS 질의   UDP 53  -> Home Router -> NAT -> Recursive Resolver
                  <- 응답 : 43.202.208.133
[3차]  TCP SYN    목적지 43.202.208.133:80 -> Home Router -> NAT -> 서버
왜 UDP 53 인가

응답이 작고 빨라야 하며, 실패하면 그냥 다시 물으면 되기 때문이다. 연결을 맺는 비용이 질의 자체보다 크다.

다만 응답이 512 바이트를 넘거나 영역 전송(zone transfer) 일 때는 TCP 로 넘어간다.

DoH 가 켜져 있으면 다르다

크롬의 "보안 DNS 사용"(chrome://settings/security) 이 켜져 있으면 질의가 UDP 53 이 아니라 TCP 443 위의 HTTPS 로 나간다.

즉 DNS 조회 자체가 또 하나의 TCP 연결과 TLS Handshake 를 끌고 온다.

connect() — 누구의 함수이고 누가 일하나

connect(소켓, 43.202.208.133:80) 은 브라우저가 만든 함수가 아니다. OS 가 프로그램에게 열어준 소켓 API 이고 브라우저는 그걸 부르기만 한다. SYN 을 실제로 만들어 보내는 건 Kernel 의 TCP/IP 스택 이다.

Client PC (Windows 11) 무엇 모드
브라우저 connect() 를 부른다 user mode
ws2_32.dll · mswsock.dll Winsock. 소켓 API 의 Windows 구현. connect() 라는 함수가 실제로 정의된 곳 user mode
(System32 의 일반 DLL)
afd.sys Ancillary Function Driver for Winsock. Winsock 이 Kernel 로 넘어가는 문 Kernel
tcpip.sys TCP/IP Protocol Driver. SYN 을 만들고 State 를 바꾼다 Kernel

Winsock 은 Kernel 이 아니다. Windows 프로그램이 네트워크를 쓰려고 부르는 user mode 라이브러리고, 그 안에서 afd.sys 로 요청을 넘겨야 Kernel 로 들어간다. Linux 는 다르다. connect() 가 libc 를 거쳐 곧바로 시스템 콜이 된다.

connect() 를 부르면 Kernel 이 하는 일

  1. 내 쪽 포트를 배정한다(예 51234). 이제 4-tuple(출발지 IP:Port + 목적지 IP:Port)이 완성된다.
  2. 이 연결의 TCB 를 만든다.
  3. State 를 CLOSED → SYN_SENT 로 바꾸고, SYN 패킷을 만들어 Default Gateway 로 내보낸다.
  4. SYN+ACK 가 오면 ACK 를 보내고 ESTABLISHED 가 된다. connect() 가 리턴했다 = Handshake 가 끝났다.
    Chrome 은 non-blocking 으로 불러 연결이 완성되면 이벤트로 알림을 받는다. 기준은 같다.

서버 쪽 짝은 listen() · accept()

NGINX 는 시작할 때 listen(80) 으로 소켓을 LISTEN 상태로 만들고, 연결이 하나 완성될 때마다 accept() 로 꺼낸다(실제로는 accept4()). 부르는 건 NGINX 프로세스고, 구현하는 건 N-Kernel(Linux) 이다.

accept() 는 Handshake 를 하지 않는다. Kernel 이 이미 끝낸 연결을 accept 큐에서 꺼내 새 fd(conn_fd = 9)로 돌려줄 뿐이다.

패킷이 실제로 가는 길

여기가 "네트워크를 아느냐" 를 가르는 지점이다. connect() 한 번에 패킷이 Client Kernel → Home Router(NAT) → 라우터들 → 방화벽 → N-Kernel 순서로 지나간다. 단계별 설명은 #2 의 ‘SYN 이 실제로 가는 경로’ 에 있다.

같은 길을 두 번 간다

이 경로는 TCP SYN 기준이지만, 위의 DNS 질의도 똑같은 길을 지난다. 목적지만 Recursive Resolver 로 바뀔 뿐 Kernel → Home Router NAT → 라우터 순서는 같다.

Kernel 이 패킷을 조립하는 순서

  1. 서브넷 판단 내 IP 192.168.0.5 와 서브넷 마스크 255.255.255.0 을 AND 해서 내 망은 192.168.0.0/24 임을 안다. 목적지 43.202.208.133 은 여기 없다 → 기본 게이트웨이로 보낸다.
  2. ARP 기본 게이트웨이의 IP 는 아는데 MAC 을 모른다. "192.168.0.1 쓰는 사람 MAC 알려줘" 를 브로드캐스트로 뿌려 알아낸다. ARP 는 같은 랜 안에서만 동작한다.
  3. 포트 배정 출발지 포트를 임시 포트(49152~65535) 중에서 하나 고른다. 응답이 어느 프로그램 것인지 구분하는 열쇠다.
  4. 캡슐화 TCP 헤더 → IP 헤더 → Ethernet 헤더 순으로 감싼다.

계층별로 누가 무엇을 보는가

계층 헤더에 담기는 것 이걸 보는 장비 어디까지 유지되나
L2 Ethernet 출발지/목적지 MAC Switch, Home Router 홉마다 새로 쓰인다
L3 IP 출발지/목적지 IP, TTL 라우터 끝까지 유지 (NAT 구간 제외)
L4 TCP 포트, 플래그, 순서번호 최종 목적지 Kernel 만 끝까지 유지
L7 HTTP 메서드, 헤더, 바디 NGINX, Spring Boot 끝까지 유지
MAC 은 왜 홉마다 바뀌나

MAC 은 "옆집까지 가는 주소", IP 는 "최종 목적지 주소" 다. 택배로 치면 IP 는 받는 사람 주소, MAC 은 지금 이 트럭이 들를 다음 물류센터다.

그래서 라우터를 하나 지날 때마다 L2 헤더는 새로 쓰이고 L3 는 그대로다.

자주 틀리는 것

"라우터가 포트 80 을 보고 보낸다" — 틀렸다. 라우터는 L3 까지만 본다. 포트는 L4 라 최종 목적지 Kernel 에서야 읽힌다.

예외는 NAT 다. Home Router 는 세션을 구분해야 해서 포트까지 들여다본다.

돌아오는 길

응답은 같은 경로를 되짚어 온다. Home Router 가 나갈 때 기록해둔 NAT 테이블이 열쇠다. "공인 IP:51234 로 온 응답은 사설 192.168.0.5:51234 에게" 라는 기록이 없으면 Home Router 는 그 패킷을 누구에게 줘야 할지 몰라서 버린다.

SYN+ACK 를 보내는 건 서버의 Linux Kernel이다. NGINX 도 Spring Boot 도 아니다.

NGINX 는 accept() 로 완성된 연결만 건네받는다. 자세한 건 #2 참고.

왜 2번이 아니라 3번인가

답은 양쪽 모두 "내 말이 상대에게 닿는다" 를 확인해야 하기 때문이다.

단계 이걸 받고 나면 확인되는 것
SYN 서버가 "클라이언트 → 나" 경로가 살아 있음을 안다
SYN + ACK 클라이언트가 양방향이 모두 살아 있음을 안다
ACK 서버도 "나 → 클라이언트" 경로가 살아 있음을 안다

2번에서 멈추면 서버는 자기가 보낸 SYN+ACK 가 도착했는지 모른다. 그 상태로 데이터를 보내면 허공에 쏘는 꼴이 된다.

Client Kernel 의 TCP State

State 뜻 이 State 가 되는 순간
CLOSED 연결이 전혀 없다. 상대가 누군지 모른다 소켓이 만들어진 직후(socket())
SYN_SENT SYN 을 보냈고 SYN+ACK 를 기다리는 중. 답을 못 받은 SYN 이 하나 떠 있다 connect() 가 SYN 을 내보내는 순간
ESTABLISHED Handshake 완료. 데이터를 주고받을 수 있다 SYN+ACK 를 받고 ACK 를 보내는 순간
  • State 는 Kernel 의 TCB 에 적혀 있다. 브라우저는 State 를 보지 못하고 connect() 의 결과(성공 · 실패)만 안다.
  • SYN_SENT 에서 답이 없으면 Kernel 이 간격을 늘려가며 SYN 을 다시 보낸다. 끝내 없으면 connect() 가 실패하고 타임아웃이 난다. 방화벽이 조용히 버리는 경우가 바로 이 상태로 머문다.
  • 서버가 그 포트를 안 열었으면 RST 가 바로 돌아와 즉시 CLOSED 로 간다 (connection refused). 무응답(타임아웃)과 즉시 거절(refused)은 원인이 다르다.
  • 직접 보려면 명령 프롬프트에서 netstat -an | findstr SYN_SENT. 평소엔 거의 비어 있다. SYN_SENT 가 아주 짧게 지나가기 때문이다.

SYN 에 실제로 실리는 것

  • 순서번호(ISN) — 임의의 값으로 시작한다. 0 부터 시작하면 예전 연결의 패킷과 섞이거나 위조가 쉬워진다.
  • MSS — 한 번에 받을 수 있는 최대 조각 크기. 보통 1460 바이트다.
  • Window Size — 버퍼 여유. 흐름 제어의 기준이 된다.
  • Window Scale, SACK — 고속 회선용 확장 옵션.

Handshake 가 끝난 연결은 accept 큐에 쌓인다. NGINX 가 바쁘면 큐가 차고, 가득 차면 새 연결이 거절되거나 지연된다.

트래픽이 몰릴 때 "연결은 되는데 느리다" 가 여기서 나온다. somaxconn, backlog 튜닝 대상이다.

SYN Flood

SYN 만 잔뜩 보내고 ACK 를 안 보내면 서버의 SYN_RCVD 상태가 쌓여 정상 연결을 못 받는다. 고전적인 DoS 수법이다.

방어책이 SYN Cookie 다. 상태를 저장하지 않고 순서번호 자체에 정보를 인코딩해서, ACK 가 돌아올 때 복원한다.

연결을 끊을 때는 4번

종료는 FIN → ACK → FIN → ACK 로 4-way 다. TCP 는 양방향이 독립적이라 한쪽이 "나는 보낼 거 다 보냈다" 해도 반대쪽은 아직 보낼 게 남아 있을 수 있기 때문이다.

이때 먼저 닫은 쪽이 TIME_WAIT 로 한동안 남는다. 서버 재시작 직후 "Address already in use" 가 뜨는 이유가 이것이다.

Handshake는 Kernel이 한다 — NGINX 가 아니다

흔한 오해

"NGINX 가 SYN 을 받아서 SYN+ACK 를 보낸다" — 틀렸다. NGINX 는 SYN 을 보지도 못한다. Kernel이 Handshake를 혼자 다 끝낸 뒤에 NGINX 에게 넘긴다.

전화 비유

  • Kernel = 교환원. 벨이 울리면 받아서 통화를 성립시킨다.
  • NGINX = 담당 직원. 교환원이 연결해준 통화를 건네받아 실제 대화를 한다.
  • 직원은 벨소리와 "연결 중" 신호에 참여하지 않는다. 수화기를 받았을 때 통화는 이미 성립돼 있다.

1~3 번에 NGINX 가 없다. TCP Handshake는 TCP 프로토콜의 일이고 TCP 구현체가 Kernel 안에 있기 때문이다. 유저랜드 프로그램이 매번 직접 악수하게 만들면 모든 서버 프로그램이 TCP 를 새로 구현해야 한다.

SYN 이 실제로 가는 경로

패킷은 층으로 포개져 있고, 중간 라우터는 봉투 안을 뜯어보지 않는다.

|  dst MAC : Home Router MAC <-- ARP 로 알아냄      |
|  +- IP packet (L3) --------------------------+  |
|  |  src IP : 192.168.0.5    (내 PC 사설)      |  |
|  |  dst IP : 43.202.208.133                  |  |  <-- 라우터가 보는 건 이것만
|  |  +- TCP segment (L4) -----------------+   |  |
|  |  |  src port : 51234  (OS 가 임의 배정) |   |  |
|  |  |  dst port : 80                     |   |  |  <-- 최종 Server Kernel만 본다
|  |  |  flags    : SYN                    |   |  |
|  |  +------------------------------------+   |  |
|  +-------------------------------------------+  |
+-------------------------------------------------+
  1. 브라우저 socket() + connect() 호출. 여기서 브라우저 역할은 끝이고 나머지는 Kernel이 한다.
  2. Client Kernel "목적지가 내 서브넷에 없네" 판단 → Default Gateway(= Home Router)로 보내기로 결정. ARP 로 Home Router 의 MAC 을 알아내 전송.
  3. Home Router NAT(NAPT). 출발지 IP 를 사설 → 공인으로 바꿔치기하고, 돌아올 응답을 누구에게 줄지 포트로 기억해둔다.
  4. 라우터들 ISP → 백본 → AWS. 수십 홉을 목적지 IP 만 보고 전달한다.
  5. 방화벽 보안그룹이 80 번 허용을 확인한다. 막혀 있으면 여기서 조용히 버려지고 브라우저는 타임아웃이 난다.
  6. N-Kernel "80 번 듣는 소켓 있음(NGINX)" → SYN+ACK 발사. 여기가 답이다. (캐슬챗처럼 Docker 컨테이너라면 이 앞에서 호스트 Kernel 의 iptables DNAT 가 컨테이너로 돌려준다.)

  2. 브라우저 Content-Type: text/html 을 보고 HTML 파서 가동. 확장자가 아니라 이 헤더가 기준이다.
  3. 브라우저 DOM 트리 구축. <div id="root"> 가 비어 있어 아직 흰 화면이다.
  4. 브라우저 CSS / JS 추가 GET. keep-alive 덕분에 같은 TCP 연결을 재사용하고 Handshake를 다시 하지 않는다.
  5. 브라우저 DOM + CSSOM → Render Tree → Layout → Paint. 흰 화면이 실제로 모니터에 출력된다.
  6. 브라우저 defer 스크립트 실행. React 가 비어 있던 root 를 채운다. 네트워크가 아닌 순수 DOM 조작이다.
  7. 브라우저 DOM 이 바뀌었으니 Layout → Paint 를 다시 돈다. 로그인 화면이 보인다.

스크립트 두 종류의 차이

  • <script defer> — 다운로드는 즉시, 실행은 파싱이 끝난 뒤. HTML 파싱을 멈추지 않는다. 없으면 그만큼 화면이 늦게 뜬다.
  • <link rel="stylesheet"> — 반대로 Rendering을 막는다(render-blocking). CSS 없이 그리면 스타일 없는 날것이 번쩍 보였다가 바뀌므로 브라우저가 일부러 기다린다.

WAS 서버가 필요해지면 Handshake가 한 번 더

location ~ ^/(user|friend|chat|room|uploads)/ {
    proxy_pass http://10.0.1.20:8080;      # 여기엔 proxy_pass 가 있다
}
  • ① 브라우저 → N-Kernel Handshake  (클라이언트 ↔ Web 서버)
  • ② NGINX → S-Kernel Handshake  (Web 서버 ↔ WAS 서버) — 완전히 별개의 연결
역할이 뒤집힌다

NGINX 는 브라우저에 대해서는 서버(SYN 을 받는 쪽), Spring Boot 에 대해서는 클라이언트(SYN 을 보내는 쪽)가 된다.

②의 SYN+ACK 를 보내는 건 S-Kernel 이다. 이때도 톰캣은 악수에 참여하지 않고 accept() 로 완성된 연결만 받는다. Web 서버에서 일어난 일이 WAS 서버에서 똑같이 반복된다.

그리고 WAS 서버가 보는 접속 IP 는 브라우저가 아니라 NGINX 가 된다. 그래서 X-Forwarded-For 가 필요하다.

#3 공인 IP · 사설 IP · 도메인 — 배포 구성 두 가지

"백엔드에 IP 가 없다" 는 말의 정확한 뜻

IP 가 없는 게 아니라 공인 IP 가 없다.

WAS 서버 상태 뜻
사설 IP 10.0.1.20 있다 내부망에서는 이걸로 통신한다
공인 IP 없다 인터넷에서 닿을 경로가 없다
비유

사설 IP 는 집 안에서만 쓰는 호수, 공인 IP 는 전 세계에서 찾아올 수 있는 주소다. WAS 서버는 아파트 안의 1203 호인데 그 아파트 주소가 비공개인 상태다. 같은 아파트 사람(Web 서버)은 1203 호를 찾아갈 수 있지만 외부인은 아파트 자체를 못 찾는다.

도메인은 프로세스에 붙는 게 아니다

흔한 오해

"Spring Boot 의 도메인" 이라는 말은 엄밀히는 성립하지 않는다. 정확히는 "Spring Boot 앞단에 노출된 공인 IP 의 도메인" 이다.

도메인  --DNS A 레코드-->  공인 IP 하나

castlechat.com  ->  203.0.113.10  ->  Web 서버 (NGINX)
                                            |
                                            +-> 10.0.1.20 (Spring Boot)
                                                도메인 불필요. 공인 IP 불필요

도메인을 산다는 건 외부 노출 지점 하나에 이름을 붙이는 것이고, 그 지점이 NGINX 다.

구성 1 — 단일 출처 (리버스 프록시). 캐슬챗 방식

castlechat.com  ->  NGINX  (공인 203.0.113.10)
   (도메인 1개)        |
                      |  /          -> 자기 디스크의 정적 파일
                      |  /user/...  -> 10.0.1.20:8080  --> Spring Boot
                      |  /chat/...  -> 10.0.1.20:8080  --> (도메인 없음)
  • 도메인 1 개로 끝난다. 백엔드는 공인 IP 도, 도메인도 필요 없다.
  • 브라우저 입장에서 출처가 하나뿐이라 CORS 가 발생하지 않는다.

캐슬챗 compose 파일 주석에 그대로 적혀 있는 내용이다.

# 브라우저 입장에서 출처가 nginx 하나뿐이라 CORS도 발생하지 않는다.
# 밖으로 여는 포트는 nginx의 80 하나뿐이다. 다른 컨테이너 포트를 publish 하면
# 출처가 늘어나면서 CORS가 되살아난다.

구성 2 — 분리 출처. "서버쪽 도메인" 이 필요한 경우

www.site.com  ->  프론트엔드   (S3 + CloudFront / Vercel / Netlify)
                   빌드된 html, js, css 만 올라감

api.site.com  ->  백엔드       <-- 여기에 공인 IP + 도메인이 필요하다
                   Spring Boot

프론트를 정적 호스팅에 올리고 백엔드를 따로 두는 구성이다. 브라우저의 JS 가 api.site.com 으로 직접 요청을 쏘기 때문에 백엔드도 외부 접근이 가능해야 한다.

대신 대가가 있다

출처가 2개 (www.site.com != api.site.com)
   -> 브라우저가 CORS 검사 발동
   -> 백엔드에 CORS 설정 필수
        @CrossOrigin / WebMvcConfigurer#addCorsMappings
        Access-Control-Allow-Origin 헤더
        preflight(OPTIONS) 요청 처리
        쿠키 쓰려면 allowCredentials + SameSite 까지

두 구성 비교

구성 1 (리버스 프록시) 구성 2 (분리 출처)
도메인 1 개 1 개 + 서브도메인
백엔드 공인 IP 불필요 필요
CORS 없음 설정 필수
인증서(HTTPS) 1 장 2 장 (또는 와일드카드 1 장)
백엔드 공격 노출 없음 있음 (방화벽으로 막아야)
프론트 배포 서버에 파일 올림 CDN 에 올림. 전송이 빠름
프론트/백 독립 배포 어려움 쉬움

캐슬챗의 현재 상태

구성 1 이고, 도메인을 사지도 않았다. 43.202.208.133 이라는 공인 IP 를 직접 쓰고 있다. NGINX 설정에 증거가 있다.

server_name _;    # "도메인 안 가림. 뭐든 다 받음"

도메인을 사면 이 자리에 server_name castlechat.com; 을 적게 된다. NGINX 설정 한 줄 + DNS A 레코드 하나가 끝이고, Spring Boot 는 한 글자도 안 고친다.

추가로 알아둘 것

서브도메인은 공짜다

api.site.com 을 위해 도메인을 또 살 필요가 없다. site.com 하나 사면 api., www., admin. 등을 무한히 만들 수 있다. DNS 레코드만 추가하면 된다.

구성 2 에서도 Spring Boot 를 맨몸으로 노출하지 않는다

api.site.com -> ALB (공인 IP) -> Spring Boot #1 (사설 IP)
                              -> Spring Boot #2 (사설 IP)
                              -> Spring Boot #3 (사설 IP)

즉 api.site.com 이 가리키는 건 톰캣이 아니라 로드밸런서의 공인 IP 다.

결론

어느 구성이든 Spring Boot 자체는 사설 IP 만 갖는다. 공인 IP 를 받는 건 항상 그 앞단(NGINX 또는 로드밸런서)이다. 그래야 서버를 여러 대로 늘릴 수 있고, 도메인이 특정 인스턴스에 묶이지 않는다.

#2 브라우저에서 wsgate 까지

브라우저 · Client Kernel

  1. React JSON.stringify({wsType:"SEND_MESSAGE", payload:{roomId:5, messageText:"안녕"}}) → ws.send(문자열)
  2. 브라우저 내장 WebSocket 구현이 Frame 을 만든다. FIN=1 · opcode=0x1(text) · MASK=1 — 클라이언트가 보내는 프레임은 반드시 마스킹. 그리고 write() 로 커널 송신 버퍼에 복사
  3. Client Kernel TCP/IP 스택이 세그먼트 → IP 패킷으로 감싼다. 목적지 IP 는 끝까지 서버 IP, 바뀌는 건 MAC 뿐이다. 이미 연결된 상태라 DNS · ARP · Handshake 는 없다

N-Kernel · NGINX — 패킷이 아니라 바이트를 중계한다

NGINX 는 애플리케이션이라 패킷을 못 본다. 커널이 재조립한 바이트를 읽고 쓴다. 그래서 연결이 둘로 끊어져 있다.

소켓 어느 Kernel 누가 fd 로 쥐나 역할
A Client Kernel 브라우저 연결 1 의 클라이언트 끝
B N-Kernel NGINX fd 7 — downstream 연결 1 의 서버 끝
C N-Kernel NGINX fd 9 — upstream 연결 2 의 클라이언트 끝
D S-Kernel Tomcat 연결 2 의 서버 끝
  1. N-Kernel 패킷 수신 → TCP 재조립 → downstream 소켓(fd 7) 수신 버퍼에 바이트가 쌓인다
  2. NGINX read(fd 7) 로 유저 공간에 꺼내고 write(fd 9) 로 upstream 소켓에 넣는다. 프레임을 파싱하지 않는다. 그냥 바이트다
  3. N-Kernel upstream 소켓 송신 버퍼의 바이트를 8090 과의 별개 TCP 연결에 새 패킷으로 만들어 보낸다. 포트 · 시퀀스 번호가 전부 다른 새 패킷이다
연결이 둘이라서 생기는 설정 
location /ws {
    proxy_pass http://10.0.1.20:8090;            # 온프레미스면 WAS 서버 사설 IP
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Real-IP $remote_addr;     # wsgate 가 보는 출발지는 NGINX 다
    proxy_read_timeout 3600s;                    # 연결 2 에만 걸리는 타임아웃
}

NGINX 는 브라우저에게는 서버, wsgate 에게는 클라이언트다. 한 프로세스가 두 역할을 하므로 소켓이 2개 필요하다.

S-Kernel → Tomcat → Spring → Dispatcher

  1. S-Kernel 재조립한 바이트를 Tomcat 소켓(D) 수신 버퍼에 쌓는다
  2. Tomcat WsFrameServer 가 프레임 수신 · 언마스킹 · 조각(continuation) 재조립 → jakarta.websocket 표준 API 로 올린다. Tomcat 은 여기까지
  3. Spring StandardWebSocketHandlerAdapter 가 받아 handleMessage() → 타입 분기 → WsGateDispatcher.handleTextMessage(). Spring 은 여기부터. DispatcherServlet 은 안 탄다
  4. Dispatcher objectMapper.readValue() 로 WebSocketDTO 변환 → switch(wsType) → "SEND_MESSAGE" 면 WsGateChatHandler.handleSendMessage()
헷갈리는 지점

DispatcherServlet 을 타는 건 WS Handshake 한 번뿐이다. 그때 HttpSessionHandshakeInterceptor 가 HTTP 세션의 로그인 정보를 WS 세션으로 복사해 둔다. 그 뒤의 메시지 프레임은 전부 위 경로로 온다.

wsgate ChatHandler → gRPC

  1. ChatHandler wsGateAuth.requireLoginUser(session) — Handshake 때 복사해 둔 세션에서 userId · publicId 를 꺼낸다
  2. ChatHandler payload 변환 + 입구 필터 (roomId 없음 · 내용도 첨부도 없음 → 여기서 실패 응답). 깨진 요청을 내부 서비스까지 보내지 않는다
  3. ChatHandler new CreateChatMessageCommand(...) → wsGateChatClient.createChatMessage(cmd). 필드 타입이 인터페이스(WsGateChatClient)라 gRPC 를 모른다
  4. ClientGrpc WsGateChatClientGrpc 가 chEngineStub.createChatMessage(req) 호출. BlockingStub 이라 exec-N 이 여기서 잠든다

#3 channel-engine 안에서

검증 · 인가 · ID 확정

  4. Service ChatMessageIdGenerator.nextMessageId() — Snowflake 53bit. DB 에 넣기 전에 PK 가 확정된다. synchronized 라 단일 직렬화 지점이다
  5. Service 첨부가 있으면 findChatAttachmentsByIds() 로 읽기만 한다(응답용). 쓰기는 여기서 안 한다

Kafka 발행 — 여기서 또 잠든다

  1. Publisher ChatMessageCreatedEventDTO 생성 → publishChatMessageCreated() → publishDurable()
  2. KafkaProducer send(토픽, roomId, event) — Serializer 로 바이트 변환, Partitioner 가 murmur2(roomId) % 6 으로 파티션 결정, RecordAccumulator 에 넣고 Future 만 반환. 아직 브로커에 안 갔다
  3. Publisher .get(timeout) — 스레드가 잠든다. 별도의 Sender 스레드가 배치를 꺼내 브로커로 보낸다
  4. 브로커 파티션 2 로그 끝에 append → acks=all 이라 ISR 복제 대기(브로커 1대라 ISR 도 1개) → partition · offset 응답
  5. Publisher Future 완료 → 깨어남. 실패했으면 예외 → 사용자에게 전송 실패 응답

#4 돌아가는 길과 비동기 저장

응답 복귀와 브로드캐스트

  1. Endpoint DTO → proto 로 바꿔 onNext() · onCompleted()
  2. wsgate 잠들어 있던 exec-N 이 깨어난다. GrpcToDtoConverter 로 다시 DTO
  3. Writer WsGateOutboundWriter 가 세 번 보낸다 — broadcastToRoom(지금 방을 보는 사람) · pushChatRoomUpdate(나머지 멤버의 방 목록) · pushChatMessageNotification(알림 대상). 보고 있는 사람을 빼서 세 집합이 겹치지 않게 했다
  4. Writer 세션마다 synchronized 로 락을 잡고 session.sendMessage(). 같은 exec-N 이 순차로 쓴다 = fan-out
  5. 브라우저 같은 경로를 거꾸로 타고 프레임 도착 (서버 → 클라이언트 프레임은 마스킹 안 함) → React 가 상태를 바꿔 “안녕” 이 화면에 뜬다

worker 가 가져가서 DB 에 넣는다

  1. worker @KafkaListener 컨테이너 스레드가 무한 루프로 consumer.poll(). push 가 아니라 pull 이다

TCP / IP 헤더 — SYN 패킷

헤더만 그렸다. TCP segment 가 IP packet 의 payload 로 들어가고, SYN 은 데이터가 없다. 분홍색은 2번 박스 문장의 ‘목적지 IP’ 와 ‘SYN 플래그’, 초록색은 그 밖의 핵심 칸이다.
값은 예시지만 체크섬 두 개는 이 헤더 바이트로 실제 계산했다(헤더를 다시 더하면 0 이 된다). Sequence Number 와 Identification 은 연결 · 패킷마다 달라지는 값이다.

용어 설명

TCB
Transmission Control Block. 연결 하나의 state · 순서번호 · 윈도우를 적어두는 자료구조
4-tuple
출발지 IP:Port + 목적지 IP:Port. 연결의 신분증
Default Gateway
PC 에 설정된, 랜 밖으로 나가는 패킷이 제일 먼저 가는 곳의 IP 주소(next hop). 내 PC 라면 192.168.4.1. 캐슬챗의 wsgate(websocket-gateway) 와는 전혀 다른 것이다
Home Router
공유기. Default Gateway 주소를 LAN 쪽에 달고 있는 장비다. 라우팅 · NAT(NAPT) · DHCP · 방화벽 · Wi-Fi 를 한 박스에 겸한다. Default Gateway 는 “주소(설정값)”, Home Router 는 “그 주소를 가진 장비”다. NAPT 는 여러 사설 IP 를 공인 IP 하나로 합치고 포트 번호로 누구의 응답인지 구분하는 NAT 다
fd
File Descriptor. 프로세스가 커널 자원을 가리키는 번호. 소켓 실체는 커널 안에 있다
Send / Receive Buffer
write() 한 데이터가 ACK 올 때까지 머무는 곳 / 도착한 데이터가 read() 될 때까지 쌓이는 곳

렌더링 — 어디까지가 렌더링인가

흐름 요약

이 파일 3개로 화면을 만드는 전 과정  ===  Critical Rendering Path (중요 렌더링 경로)

  1. node_modules 에서 필요한 (13개) 패키지 + 컴포넌트 .jsx + hooks 등 .js → build/static/js/main.e83d3066.js
  2. 모든 .css → build/static/css/main.0bd4de65.css
  3. index.html   빈 껍데기. <div id="root"></div>

이 파일 3개로 화면을 만드는 전 과정을 "렌더링" 이라 부르는 건 넓은 의미로만 맞다. 좁은 의미의 Rendering 은 그중 마지막 단계만 가리킨다.

브라우저가 하는 일은 세 종류다

1

Parsing · 파싱

HTML → DOM 트리
CSS → CSSOM 트리

텍스트를 구조로 바꾸는 일

렌더링 아님
2

Script Execution · JS 실행

V8 엔진 → main.e83d3066.js 실행
React → DOM 조작, root 채움

코드를 돌리는 일

렌더링 아님
3

Rendering · 렌더링

DOM + CSSOM → Render Tree
→ Layout → Paint → Composite

구조를 실제 픽셀로 바꾸는 일

좁은 의미의 렌더링은 이것만

①②는 렌더링이 아니다.
파싱이고 실행이다.

실제 순서

① Parsing index.html 받음 파싱 → DOM 트리
① Parsing main.css 받음 파싱 → CSSOM 트리
③ Rendering Render Tree → Layout → Paint DOM + CSSOM 합성
흰 화면 출력
② JS 실행 main.js 실행 React 가 root 를 채움
③ Rendering Layout → Paint 다시 DOM 이 바뀌었으므로
실제 화면 출력

3번과 5번만 렌더링이다. 4번은 렌더링이 아니라 JS 실행이고, 그 결과로 렌더링이 다시 일어난다. 아래 6 — Rendering 파이프라인 과 7 — JS 실행, React 등장 을 따로 나눠둔 이유다.

CSR 의 '렌더링' 은 또 다른 뜻이다

용어 여기서 '렌더링' 의 뜻 층위
Rendering 파이프라인 Layout → Paint → Composite 브라우저 내부 동작
CSR (Client Side Rendering) HTML 을 누가 만드느냐 아키텍처
SSR (Server Side Rendering) HTML 을 누가 만드느냐 아키텍처

CSR · SSR 의 '렌더링' 은 "화면을 그린다" 가 아니라 "HTML 을 만들어낸다" 는 뜻이다.

SSR = 서버가 HTML 을 만든다       <-- 네이버
CSR = 브라우저가 HTML 을 만든다   <-- 캐슬챗

[ SSR ]  서버가 완성 HTML --> 브라우저  파싱 --------> Rendering 파이프라인
[ CSR ]  서버가 껍데기만   --> 브라우저  파싱 + JS 실행 --> Rendering 파이프라인
                                                            ^ 둘 다 여기는 같다
그래서

SSR 이든 CSR 이든 마지막에 픽셀을 찍는 건 항상 브라우저의 Rendering 파이프라인이다. SSR 이라고 브라우저가 Layout · Paint 를 안 하는 게 아니다.

결론

넓은 의미 — 맞다

파일 3개로 화면을 만드는 전 과정을 "브라우저가 렌더링한다" 고 흔히 말한다. 정식 명칭은 Critical Rendering Path 다.

좁은 의미 — 일부만

렌더링은 Render Tree → Layout → Paint → Composite 만 가리킨다. 그 앞의 파싱과 JS 실행은 별개 단계다.

일상적으로는 넓은 의미로 써도 통하지만, "JS 실행도 렌더링이냐" 는 질문에는 아니라고 답하는 게 맞다.

참고 1 — 파일명의 해시는 왜 붙나

main.0bd4de65.css 의 가운데 토막은 파일 내용으로 만든 지문이다.

왜 이렇게 하나 — 캐시 때문이다

브라우저는 CSS · JS 를 한 번 받으면 캐시에 저장하고 다시 안 받는다. 빠르니까. 그런데 문제가 생긴다.

해시가 없다면 
1일차  main.css 받음 -> 캐시 저장
2일차  내가 CSS 수정 후 배포
3일차  재방문 -> "main.css? 캐시에 있네"
       -> 옛날 걸 씀. 수정이 반영 안 됨

파일명이 같으니 브라우저가 바뀐 줄 모른다. “Ctrl+Shift+R 하세요” 라고 안내해야 하는 상황이 이것이다.

해시가 있으면 
1일차  main.0bd4de65.css 받음 -> 캐시 저장
2일차  수정 -> 배포 -> main.a7f2c391.css 로 바뀜
3일차  재방문 -> index.html 이 새 이름을 달라고 함
       -> 캐시에 없는 이름 -> 무조건 새로 받음

이름을 바꿔서 캐시를 무력화하는 기법이고, cache busting 이라고 부른다.

참고 2 — 기본 게이트웨이 자리에 실제로 뭐가 있나

Default Gateway 는 장비 이름이 아니라 역할 · 설정 이름이라 어디서나 맞는 표현이다. 그 자리에 꽂혀 있는 물건만 환경마다 다르다.

환경 기본 게이트웨이 자리의 실제 장비
집 Home Router (공유기)
회사 L3 스위치 또는 방화벽. 라우터인 경우도 있음

회사에서는 보통 라우터가 아니다

집에서는 Home Router(공유기) 하나가 스위치 · 게이트웨이 · NAT · 방화벽 역할을 다 겸한다. 그래서 구분이 무의미했던 것이다.

회사 경로는 보통 이렇게 쪼개져 있다.

Home Router 는 소비자 장비 용어라 회사 환경 설명에 쓰면 안 된다. 글로 적을 때는 “기본 게이트웨이로 보낸다” 가 가장 안전하다.

  • 요즘은 섞어 쓴다 — Next.js 처럼 첫 화면만 서버에서 조립하고 그 다음부터 브라우저가 조립하는 방식. 캐슬챗은 create-react-app 기반이라 순수 CSR 이다.
고쳐 쓴 문장

네이버는 캐슬챗과 달리 첫 HTML 을 서버에서 조립한다. 그래서 첫 요청부터 백엔드가 관여한다.

캐슬챗도 백엔드는 있다. 다만 조립을 브라우저에 미뤘기 때문에 첫 HTML 을 정적 파일로 둘 수 있었던 것이다.

HTTP 요청 헤더 — 개발자 필수 정리

요청 라인

GET / HTTP/1.1
  • GET — 메서드. GET, POST, PUT, PATCH, DELETE
  • / — 경로
  • HTTP/1.1 — 프로토콜 버전

1순위 모르면 안 되는 것

Host: 43.202.208.133

HTTP/1.1 에서 유일한 필수 헤더. IP 하나에 여러 사이트를 올릴 수 있게 해주는 헤더다.

NGINX 가 server_name 으로 어느 사이트인지 가르는 기준이 이것이다.

server_name _;    # 지금은 "뭐든 다 받음". 도메인 사면 여기에 적는다
Cookie: JSESSIONID=...

HTTP 는 상태가 없다(stateless). 서버는 매 요청을 처음 보는 사람으로 취급한다.

그걸 뚫고 "나 아까 그 사람이야" 를 증명하는 수단이다. 브라우저가 자동으로 붙인다. 첫 방문이면 없다.

Content-Type: application/json

GET 에는 바디가 없어 안 붙지만 POST / PUT 에서는 필수다. 실무에서 가장 많이 깨지는 지점.

값 쓰임
application/json REST API 기본
multipart/form-data 파일 업로드
application/x-www-form-urlencoded HTML form 기본값

Spring 의 @RequestBody 가 안 먹는 사고 대부분이 이 헤더 문제다.

Content-Length: 348

바디의 바이트 길이. 서버가 어디까지 읽어야 하는지 아는 기준이다. GET 에는 없다.

Authorization: Bearer <token>

JWT 방식 인증. 쿠키(세션) 대신 쓰는 다른 축이다.

세션 방식과 JWT 방식의 차이.

  • 세션 — 서버가 상태를 들고 있음(Redis 등). 강제 로그아웃이 쉽다.
  • JWT — 서버가 상태를 안 들고 있음. 확장이 쉽지만 즉시 폐기가 어렵다.
Origin: http://43.202.208.133

CORS 의 정체가 이 헤더다. 브라우저가 강제로 붙이고 JS 로 위조가 불가능하다. 서버는 이걸 보고 "허용된 출처냐" 를 판단한다.

캐슬챗에 CORS 설정이 없는 이유 — 모든 요청이 NGINX 한 곳으로 가서 출처가 하나뿐이고, 출처가 같으면 브라우저가 CORS 검사 자체를 하지 않는다.

2순위 알아두면 실력 차이가 나는 것

If-None-Match / If-Modified-Since

캐시 재검증용. 응답의 ETag / Last-Modified 와 짝을 이룬다.

1회차 응답 : ETag: "6aa4110f-224"        + 본문 548 바이트
2회차 요청 : If-None-Match: "6aa4110f-224"
2회차 응답 : 304 Not Modified            + 본문 없음   <-- 전송량 절약

JS 번들이 수백 KB 일 때 효과가 크다.

Accept-Encoding: gzip, deflate

"압축해서 줘도 된다" 는 신고. 서버가 압축하면 응답에 Content-Encoding: gzip 이 붙는다.

현재 캐슬챗 서버는 안 붙여준다. nginx.conf 에 gzip on; 이 없어서다. 한 줄 추가로 체감 로딩이 줄어든다. "성능 개선 경험" 소재.

Connection: keep-alive

"응답 주고 연결 끊지 마." 3-way handshake 를 파일마다 반복하지 않게 해준다. HTTP/1.1 기본값.

Accept: text/html,application/xhtml+xml,*/*;q=0.8

"이런 형식으로 줘." 콘텐츠 협상에 쓴다. q=0.8 은 선호도 가중치(0~1)로, 숫자가 클수록 선호한다는 뜻이다.

X-Forwarded-For: 203.0.113.42

프록시를 거치면 뒷단 서버가 보는 접속 IP 는 NGINX 의 IP 가 된다. 진짜 사용자 IP 를 알려주려고 NGINX 가 끼워넣는 헤더다.

로그 분석, IP 차단에 필수. X- 접두사는 "표준이 아닌 관례" 라는 뜻이다.

proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
Cache-Control: no-cache

캐시 정책. 요청과 응답 양쪽에 다 붙을 수 있다. 요청에 붙으면 "캐시 쓰지 말고 새로 줘" 이고, 브라우저에서 Ctrl+Shift+R 이 이것이다.

3순위 존재만 알면 되는 것

User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131

절대 신뢰하면 안 된다. 누구나 조작한다. curl 로 크롬인 척하는 것도 한 줄이면 된다.

통계와 로그 용도로만 쓸 것. 인증이나 분기 판단에 쓰면 사고로 이어진다.

Referer: http://43.202.208.133/login

어디서 눌러서 왔는지. 스펠링이 틀린 게 표준이다(Referrer 가 맞는 철자). 초기 오타가 그대로 굳었다.

Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8

다국어 사이트의 기본 언어 결정용.

Range: bytes=1024-2047

파일의 일부만 요청한다. 동영상 중간으로 점프하는 기능이 이것이다. 응답의 Accept-Ranges: bytes 가 "나 이거 지원함" 표시다.

형식 규칙

  • 각 줄 끝은 \n 이 아니라 \r\n (CRLF) 다.
  • 헤더 블록 끝에 빈 줄 하나가 더 붙는다. 이게 "헤더 끝" 신호이고, 안 보내면 서버가 헤더가 더 올 줄 알고 영원히 기다린다.
  • 헤더 순서는 정해져 있지 않다. Host 만 필수다.
  • 헤더 이름은 대소문자를 구분하지 않는다.
  • http 는 전부 평문이다. 쿠키까지 중간에서 그대로 읽힌다. 실서비스는 HTTPS 필수.

실제로 소켓에 흘러가는 바이트

GET / HTTP/1.1\r\n
Host: 43.202.208.133\r\n
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/131\r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Encoding: gzip, deflate\r\n
Accept-Language: ko-KR,ko;q=0.9\r\n
Connection: keep-alive\r\n
Cookie: JSESSIONID=...\r\n
\r\n                        <-- 이 빈 줄이 끝 신호
